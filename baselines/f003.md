# フォームのアクセシビリティを直した

問い合わせフォームの改修を頼まれたとき、最初に渡された要望は「入力エラーがわかりにくいので直してほしい」という一行だけだった。実際に触ってみると、エラーメッセージは赤い文字で入力欄の下に出るだけで、視覚的には赤字で十分伝わる。だがスクリーンリーダーで読み上げさせてみると、フォーカスが当たっている入力欄の名前だけが読まれ、その下に赤字で表示されているはずのエラー内容は一切読み上げられなかった。晴眼者には見えている情報が、スクリーンリーダー利用者にはまるごと欠落していたということになる。この体験の差が、今回直したかった本丸だった。

## まず label の対応関係を疑う

エラー表示を直す前に、そもそも入力欄とラベルの対応が取れているかを確認した。見た目には「お名前」という文字が入力欄の上に置かれていたが、実際のマークアップはただの div とテキストで、input との紐付けがどこにもなかった。これだとスクリーンリーダーはラベルの文字列を読み上げず、フォーカスが当たった瞬間に「編集、テキスト」としか案内されない。何を入力すればいいのか、音声だけでは判断できない状態だった。

対応としては、ラベル要素の for 属性と入力欄の id を一致させ、確実に紐付ける形に統一した。デザイン上ラベルを画面に出したくない項目については、視覚的に隠しつつスクリーンリーダーには読ませる手法を使い、必ずラベルテキスト自体は存在させるようにした。placeholder だけを名前代わりにしている項目もいくつかあったが、入力が始まると placeholder は消えてしまうため、何を書いていたか忘れたときに手がかりが失われる。placeholder は補足のヒントにとどめ、ラベルの代わりにはしない方針に決めた。

## aria-describedby でエラーを入力欄に結びつける

ラベルの対応が取れても、エラーメッセージ自体が入力欄と結びついていなければ状況は変わらない。ここで使ったのが aria-describedby だ。入力欄に aria-describedby でエラーメッセージ要素の id を指定しておくと、スクリーンリーダーがその入力欄にフォーカスしたときに、ラベルに続けてエラーの説明文も読み上げてくれるようになる。

実装で気をつけたのは、エラーが出ていない状態でも aria-describedby の値を固定にしておくかどうかだった。エラーが発生したときだけ属性を動的に追加する実装と、常に説明用の要素を用意しておいて中身だけ切り替える実装を比較し、今回は後者を選んだ。属性の有無を都度切り替えるより、要素自体は常に存在させて表示・非表示と読み上げ内容を制御するほうが、実装のバグで属性が抜け落ちるリスクが小さいと判断したからだ。加えて、入力の説明文とエラーメッセージの両方を同じ入力欄に紐付けたい項目があったため、aria-describedby には空白区切りで複数の id を指定できることを利用し、通常時の説明文用 id とエラー用 id を並べて指定する形にした。

エラーメッセージを入れる要素には role を alert 相当のものにするかどうかでも迷った。常時レンダリングされている要素の中身を書き換える形にしたので、あとから見た目の変化に気づかれないまま読み上げられない、という事態は避けたかった。最終的には、エラー文言が動的に差し替わったタイミングでスクリーンリーダーが変化を検知して読み上げる仕組みを持たせることにした。これにより、フォーカスを移動させなくても、送信直後にどの項目でエラーが出たかが音声でも伝わるようになった。

## エラー通知のタイミングと出し方

もう一つの問題は、エラーの出し方そのものだった。改修前は、送信ボタンを押した瞬間にページ上部へ赤いバナーが一つだけ表示され、「入力内容に誤りがあります」とだけ書かれていた。どの項目が悪いのかはユーザーが自分でフォームを上から目で追って探すしかない構造で、視覚的に問題を探すコストが前提になっていた。

これを、送信時に各入力欄ごとのエラーメッセージを個別に出す形に変更した上で、ページ上部にはエラーが何件あり、それぞれどの項目に対応するかをまとめたサマリーを置いた。このサマリー内の各項目をリンクにして、クリックすると該当の入力欄にフォーカスが移る作りにしている。晴眼者はざっと一覧を見てどこが悪いか把握できるし、スクリーンリーダー利用者もサマリーを読み上げさせるだけで、修正すべき項目の全体像を先に把握できる。個別のエラーメッセージと合わせて二重に情報を出す形になるが、片方だけでは伝わり方に偏りが出てしまうため、両方を残すことにした。

エラーの通知タイミングについても調整した。改修前は、入力欄からフォーカスが外れるたびに即座にエラー判定を行っていた。これは一見親切に見えるが、まだ入力の途中で他のことを考えながらタブキーで次の項目に移っただけのユーザーにまでエラー音声を浴びせることになり、かえって混乱を招いていた。今回は、初回の判定は送信時にまとめて行い、一度エラーが出た項目については、その後の入力中にリアルタイムで判定してエラーが解消され次第すぐに知らせる、という二段構えにした。最初から粗探しをせず、直そうとしている項目だけを積極的にフォローする形に落ち着いている。

## フォーカス管理をやり直す

エラー通知の作り込みと並行して、フォーカスの移動先も見直した。送信後にエラーが出た場合、改修前はフォーカスがどこにも移動せず、送信ボタンにとどまったままだった。画面を見ている人はページ上部のエラー表示に気づけるが、スクリーンリーダー利用者は次に何が読み上げられるかの手がかりを失う。そこで、送信に失敗した際は、先ほど触れたエラーサマリーの見出しへ自動的にフォーカスを移すようにした。フォーカスが移動すれば、スクリーンリーダーはその位置から読み上げを再開するため、結果として「送信に失敗しました。エラーが何件あります」という文脈がまず耳に入り、その後に各項目の内容へと進める流れになる。

モーダルで確認画面を出す部分にも同じ考え方を適用した。確認モーダルを開いたときにフォーカスがモーダル内の先頭要素に移らず、背後のページに残ったままになっていたため、モーダルを閉じるまでのあいだフォーカスがモーダルの外に出ないように閉じ込める処理を加えた。閉じたときには、モーダルを開く前に操作していたボタンへフォーカスを戻すようにしている。これを怠ると、モーダルを閉じたあとにフォーカスがページの先頭やどこか予期しない場所に飛んでしまい、直前まで自分がどこを操作していたのか見失う原因になる。

## スクリーンリーダーで実機確認する

コードを直しただけで安心せず、実際にスクリーンリーダーを立ち上げてフォーム全体を一通り操作した。キーボードだけで全項目にタブ移動でき、ラベルとエラーメッセージが期待通りに読み上げられるか、送信に失敗したときにエラーサマリーへ正しくフォーカスが移るか、モーダルを開閉したときにフォーカスの迷子が起きないかを確認した。目視のレビューだけでは気づけない箇所がいくつもあり、たとえば必須項目を示すアスタリスクの記号が読み上げられずに視覚的な印だけになっていた点も、実際に音声を聞いて初めて気づけた。

こうした確認は自動テストだけでは代替しきれない。属性の有無やロールの指定は静的にチェックできても、読み上げられる順序や文脈のつながりは、実際に耳で聞かないと判断が難しい。今回の改修を通じて、アクセシビリティの不備は見た目のレビューをいくら重ねても発見できず、支援技術を実際に動かして確認する工程を作業の中に組み込むことの重要性を改めて意識した。

## まとめ

今回の改修は、label と入力欄の対応、aria-describedby によるエラーの紐付け、エラー通知のタイミングと出し方、そしてフォーカス管理という、一見別々に見える項目が実はすべてつながっていることを実感させるものだった。どれか一つだけを直しても体験はさほど改善せず、ラベルが読めてもエラーが読めなければ意味がなく、エラーが読めてもフォーカスが正しい位置に移らなければ気づかれない。地道ではあるが、この一連のつながりを一つずつ潰していく作業こそが、フォームのアクセシビリティを底上げする近道だと感じている。
