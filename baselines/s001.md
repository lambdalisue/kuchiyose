# 脆弱性スキャンを CI に入れた

コンテナイメージの脆弱性スキャンを CI パイプラインに組み込んだ。きっかけは特別な事件があったわけではなく、依存パッケージの脆弱性が本番稼働後にしか発覚しない状態を、そろそろ終わらせたいと思っただけだった。導入自体は数時間で終わったが、運用に乗せるまでにはそれなりの試行錯誤があったので、記録として残しておく。

## なぜ Trivy を選んだか

スキャナはいくつか候補があったが、最終的に Trivy を選んだ。理由は単純で、単体のバイナリとして動き、追加のサーバーやデータベースを別途構築する必要がないからだ。コンテナイメージだけでなく、ファイルシステムや Git リポジトリ、さらには Infrastructure as Code の設定ファイルまで一つのツールでスキャンできる点も魅力だった。CI の実行環境に組み込むハードルが低く、既存のワークフローに差し込むだけで動き始めるのは大きい。

スキャン対象は大きく分けて二つある。一つはアプリケーションが利用しているパッケージやライブラリの依存関係、もう一つはベースイメージに含まれる OS パッケージだ。どちらも放置すると既知の脆弱性が静かに積み上がっていくという点では変わらない。

## SBOM を生成する意味

スキャンを回すだけでなく、SBOM(ソフトウェア部品表)を同時に生成するようにした。SBOM とは、そのソフトウェアがどのライブラリやパッケージにどのバージョンで依存しているかを一覧化したものだ。スキャンの結果だけを保存していると、後になって「このイメージには具体的に何が入っていたのか」を追跡できなくなる。SBOM を成果物として残しておけば、新しい CVE が公表されたときに過去にビルドしたイメージのどれが影響を受けるかを、スキャンをやり直さなくても照合できる。

これは地味だが効果が大きい。脆弱性は日々新しく公表されるので、ビルド時点では安全だったイメージが、数か月後に振り返ると危険だったと判明することは珍しくない。SBOM を資産として蓄積しておくことで、そのときに慌てて過去のビルドログを漁る必要がなくなった。

## CVE の重大度をどう扱うか

Trivy はスキャン結果として CVE 番号と重大度(Critical、High、Medium、Low など)を返してくる。最初は「Critical と High が一件でもあればビルドを失敗させる」という単純なルールで始めた。しかし、これはすぐに機能しなくなった。理由は二つある。

- 修正版が存在しない CVE が一定数混ざっており、いつまで経ってもビルドが通らない
- 実際には自分たちの使い方では到達しないコードパスの脆弱性まで一律に扱われてしまう

そこで、修正パッチが存在する脆弱性に限ってビルドを止めるという条件に変更した。パッチが存在しないものは記録だけ残し、ブロックはしない。これだけでゲートとしての実用性がかなり改善した。脆弱性そのものをゼロにすることは目指さず、「対処可能なものを見逃さない」ことを目標に据え直したのが効いたと思う。

## 誤検知との付き合い方

運用を始めてすぐに直面したのが誤検知の扱いだった。パッケージのバージョン文字列の解釈違いや、実際には該当しない条件下でのみ有効な脆弱性が検出されることがある。これを放置すると、CI の失敗が「またいつものやつか」という感覚に変わり、本当に重大な検出まで見過ごされるようになる。いわゆるアラート疲れだ。

対策として、無視リストの仕組みを使った。特定の CVE 番号を無視対象として登録できる機能があり、これに「無視する理由」と「再確認する期限」を必ずセットで記録するようにした。理由のない無視は、後から見たときにそれが正当な判断だったのか単なる放置だったのか区別がつかなくなる。期限を設けているのは、無視した時点では妥当だった判断が、時間の経過とともに妥当でなくなる可能性があるからだ。半年に一度、無視リストの棚卸しを行い、期限切れのエントリを再評価する運用にしている。

## 運用に乗せてから見えたこと

導入してから数か月経って感じるのは、脆弱性スキャンは「入れて終わり」ではなく継続的な手入れが必要な仕組みだということだ。CVE データベースは日々更新されるので、同じイメージでも昨日は通っていたスキャンが今日は失敗することがある。これは Trivy や CI の不具合ではなく、正しく機能している証拠でもあるのだが、最初にこの挙動を知らないチームメンバーは戸惑う。導入時にこの前提を共有しておくことは重要だった。

また、ベースイメージの更新頻度がそのまま脆弱性対応のしやすさに直結することも実感した。ベースイメージが古いまま放置されていると、パッチが存在しても適用できず、無視リストが膨れ上がる一方になる。スキャンの導入と並行して、ベースイメージを定期的に更新する仕組みも整えたことで、無視リストの増加をある程度抑えられている。

脆弱性スキャンは、それ単体では守りを固める道具ではなく、気づくための道具だ。気づいた後にどう対処するかの運用を合わせて設計しなければ、通知が積み上がるだけの仕組みになってしまう。今回の導入を通じて、スキャンツールの選定よりも、検出後の運用フローの設計に時間をかけるべきだったと感じている。
