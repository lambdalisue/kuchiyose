# CSS 設計を破棄して書き直した話

数年前に組んだ CSS 設計を、最近ようやく壊した。BEM で書いていたコンポーネント群を Tailwind に置き換える作業を終えて、感じたことを書いておく。

## BEM が重くなっていった経緯

最初に BEM を選んだ理由は単純で、クラス名を見れば構造がわかるからだった。ブロックとエレメントと修飾子の組み合わせで、どのコンポーネントのどの部分かが一目でわかる。命名規則さえ守れば詳細度の衝突も起きにくいし、チームで書いていても迷いが少ない。導入した当初はこれで十分だと思っていた。

ところが画面数が増えるにつれて、命名の負担が目立つようになった。新しいコンポーネントを作るたびに、ブロック名とエレメント名を考え、既存の命名と衝突しないか確認し、修飾子を増やすかバリアントを分けるか判断する。この判断コストが、実装そのものよりも時間を食うようになっていった。加えて、CSS ファイルとコンポーネントファイルが別々に存在するせいで、あるクラスがどこで使われているか追いにくい。使われなくなったクラスが CSS に残り続け、消していいのか判断できないまま放置される。いわゆる CSS の墓場ができあがっていた。

## CSS Modules で解決しなかったもの

途中で CSS Modules を試した時期もある。クラス名の衝突をビルド時に解決してくれるので、BEM のような命名規則を人間が守る必要がなくなる。これは確かに助けになった。

ただし CSS Modules が解決するのはスコープの問題であって、設計の問題ではない。ファイルはコンポーネントごとに分かれても、その中に書くスタイルの粒度や、共通化すべき値をどこまで共有するかという判断は結局チームに委ねられたままだった。余白の数値がファイルごとに微妙にずれていく、似たようなカードコンポーネントが少しずつ違うスタイルで量産される、といった問題は変わらず起きた。詳細度の衝突は減ったが、一貫性のなさは減らなかった。

## ユーティリティに寄せた理由

最終的に Tailwind に寄せたのは、スタイルの置き場所をコンポーネントの外に作らないという判断を徹底したかったからだ。ユーティリティクラスは基本的に単一の宣言に対応するので、詳細度がほぼ均一になる。クラスの並び順で見た目が決まらず、後から書いたクラスが勝つといった事故も起きにくい。命名という工程そのものがなくなるので、新しいコンポーネントを作るたびに名前を考えて議論する時間が消えた。

何より効いたのは、マークアップを見ればスタイルがそのまま見える点だった。BEM のときはクラス名から CSS ファイルを探しに行く一手間があったが、その一手間がなくなるだけで実装のリズムが変わった。設定ファイルで余白やフォントサイズの刻み幅を決めておけば、数値のばらつきも自然と収まる。

## 書き直して見えてきた代償

もちろん失ったものもある。クラスの羅列は見た目が煩雑で、長くなると何のコンポーネントかぱっと読み取りにくい。意味のあるまとまりを表現したいときに、結局はコンポーネント単位で切り出す設計力が要求される。ユーティリティは詳細度の問題を避けてくれるだけで、コンポーネント分割の判断そのものを肩代わりしてはくれない。BEM が担っていた「命名によって構造を強制する」役割は失われたので、その代わりにコンポーネント分割の規律を別の形で持たせる必要がある。

## 振り返って思うこと

今回の書き直しで一番大きかったのは、ツールを変えたことよりも、スタイルの置き場所を一箇所に決め切ったことだった。BEM も CSS Modules も、命名やスコープという個別の問題は解決してくれたが、スタイルとマークアップが分離しているという構造そのものは変わらなかった。その分離をやめたことが、結局のところ一番効いた変更だったと思う。
