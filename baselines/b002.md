# 非同期処理をキューに逃がした話

リクエストを受けてから応答を返すまでの処理に、時間のかかる後続処理を同期で混ぜ込んでいた時期がある。画像のリサイズ、外部 API への通知、集計データの更新。どれも「応答を返した後にやればいい」処理なのに、同じリクエストハンドラの中で順番にこなしていた。結果として、外部 API が少し遅くなるだけでユーザー側のレスポンスタイムが悪化し、外部サービスが落ちれば自分たちのエンドポイントまで巻き添えでタイムアウトするようになった。原因は明確で、本来分離できるはずの処理が同期処理の中に閉じ込められていたことだった。

## キューに逃がすという選択

この手の問題への定番の解決策は、時間のかかる処理をリクエストの外に追い出し、非同期のワーカーに任せることだ。リクエストハンドラは「処理してほしい内容」をキューに積むだけで応答を返し、実際の処理は別プロセスのワーカーが後から拾って実行する。

キューには SQS を選んだ。自前でメッセージブローカーを運用する余裕がなかったこと、可視性タイムアウトやデッドレターキューといった非同期処理に必要な仕組みが最初から用意されていたことが理由だ。似たような処理は他にもいくつかあるが、まずは一番効果が大きそうな外部通知の処理から手をつけることにした。

構成はシンプルで、リクエストハンドラはメッセージを SQS に送るだけの薄い処理になり、それを取り出して実際の処理を行うワーカーを別のプロセスとして常駐させた。ワーカーはキューをポーリングし、メッセージが届いたら処理し、成功したらキューから削除する。失敗したら削除しない、というのが基本の流れになる。

## 冪等性という前提条件

キューを使った非同期処理に手を出すとき、最初に理解しておくべきなのは「メッセージは複数回届くことがある」という前提だ。SQS は標準キューを使う限り、少なくとも 1 回の配信は保証するが、ちょうど 1 回の配信は保証しない。ネットワークの揺らぎやワーカー側の処理タイムアウトなど、様々な理由で同じメッセージが二度届くことがある。

これを知らずに実装すると、通知が二重に飛んだり、集計値が二重に加算されたりする不具合が起きる。実際、最初の実装ではこの点を軽視していて、リトライのたびに外部 API への通知が重複するという問題を本番で踏んだ。

対策として、処理対象のメッセージには一意な識別子を持たせ、その識別子をキーにして「すでに処理済みかどうか」を判定できるようにした。処理の前に識別子を記録し、すでに記録があれば処理をスキップする。データベースの更新であれば、加算ではなく特定の値に上書きする形に変えるだけで二重実行に強くなる場合もある。どの方法を取るにせよ、ワーカー側のロジックは「同じメッセージが何度来ても結果が変わらない」ことを前提に設計する必要がある。これが冪等性で、非同期処理をキューに任せる以上は避けて通れない設計要件になる。

## リトライと失敗の扱い

ワーカーの処理が失敗したとき、そのメッセージをどう扱うかも重要な設計ポイントだった。SQS では、ワーカーがメッセージを受け取ってから可視性タイムアウトの間は他のワーカーからそのメッセージが見えなくなる。処理中に例外が起きてメッセージを削除しなければ、タイムアウト後に再びキューに現れ、別のワーカーがもう一度処理を試みる。これが自然なリトライの仕組みになる。

ただし、何度リトライしても成功しない種類の失敗もある。メッセージの形式が壊れている、参照先のリソースがすでに存在しないなど、リトライで解決しない不具合を延々とリトライさせると、キューがそのメッセージで詰まり、後続の正常なメッセージの処理まで遅延する。

そこで、最大受信回数を超えたメッセージは自動的にデッドレターキューに移動するように設定した。デッドレターキューは、通常のキューとは別に用意した「処理に失敗し続けたメッセージの置き場」で、ここに移動したメッセージは通常のワーカーの処理対象から外れる。代わりに、デッドレターキューに何か溜まっていないかを監視し、一定数を超えたら通知が飛ぶようにしておいた。中身を見て原因を調べ、コードの不具合であれば直してから手動で元のキューに戻す、データが壊れているだけなら破棄する、といった判断を人間が行う運用にしている。

## 運用に入ってから見えたこと

移行してからしばらく経って感じたのは、非同期化そのものよりも、リトライとデッドレターキューの設計にどれだけ時間をかけたかが後々の安定運用を左右したということだ。最初の実装ではリトライ回数の上限を設定しておらず、外部 API 側の障害が長引いたときにキューがひたすら同じメッセージを処理し続け、他の処理を圧迫したことがあった。上限を設けてデッドレターキューに逃がす仕組みを入れてからは、一部の処理が詰まっても全体には影響しなくなった。

また、ワーカーの台数を増やせば処理速度が上がるという単純なスケールのしやすさも、キューに逃がしたことで得られた利点だった。リクエストを受ける側とそれを処理する側が分離されているため、処理が遅れているときはワーカーの数を増やすだけで対応でき、リクエストハンドラ側のコードには一切手を入れずに済む。

同期処理の中に押し込めていたときには見えなかった、各処理の負荷や失敗率も、キューの滞留状況やデッドレターキューへの流入数という形で可視化できるようになった。結果として、どの処理がボトルネックになっているかを個別に把握できるようになり、次に手を入れるべき箇所の優先順位もつけやすくなった。非同期処理をキューに逃がすというのは、単に応答速度を改善する手段であると同時に、システムの一部分を独立して観測し、改善できる単位に切り出す作業でもあったと感じている。
