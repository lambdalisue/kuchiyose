# Terraform の状態管理で事故った話

## 何が起きたか

ある週末、ステージング環境の Terraform を久しぶりに触ったところ、`plan` の結果が想定と大きくずれていました。既存のリソースがことごとく「作成」として表示され、実際には稼働しているはずのネットワークやデータベースが tfstate 上に存在しないかのような差分が出てきたのです。原因を辿ると、直前に別のメンバーが手元の環境から `apply` を実行し、リモートの tfstate を上書きしてしまっていたことが分かりました。

Terraform はコードと実インフラの対応関係を tfstate というファイルで管理しています。この対応関係が壊れると、Terraform は「今何が存在しているか」を正しく認識できなくなり、既存リソースを重複して作ろうとしたり、逆に稼働中のリソースを削除しようとしたりします。今回のケースはまさにこれで、复数人が同じ状態ファイルに対して同時に近いタイミングで書き込みを行ったことが引き金でした。

## ロックが機能していなかった

Terraform には、複数人が同時に `apply` を実行して状態ファイルを壊さないよう、ロック機構が用意されています。リモートバックエンドを使っていれば、誰かが `apply` を実行している間は他のメンバーの操作がロックされ、待たされるか失敗する仕組みです。

ところが今回、ロック用のテーブルに古いロック情報が残ったままになっていました。以前 `apply` を強制終了させた際に、ロックの解放処理が走らずそのまま残留していたのです。その状態を見たメンバーが「ロックがおかしいから消してしまおう」と判断し、ロックを手動で解除した上で `apply` を実行しました。しかしそのタイミングで、実は別の環境からも同じ tfstate に対する操作が走っており、結果として片方の変更がもう片方を上書きする形になってしまいました。

ロックが「今誰かが作業中である」という事実を示すためのものである以上、それを安易に解除する判断は非常に危険です。ロックが解除できない場合は、まず本当に誰も作業していないかを確認すべきで、疑わしいときは触らずに関係者へ確認するのが筋でした。

## 差分の読み違いが被害を広げた

さらに厄介だったのは、状態が壊れた後の `plan` の差分を正しく読み取れなかったことです。差分には大量の「作成」「削除」が並び、パッと見ただけでは何が本当に危険な変更なのかが判断できませんでした。焦って `apply` を実行しかけたメンバーもいましたが、幸い実行前に気づいて止めることができました。

差分を読むときは、変更の理由に心当たりがあるかどうかを一つずつ確認する必要があります。特に、削除を伴う差分は必ず立ち止まるべきで、状態ファイルの不整合が疑われる状況では、なおさら `apply` を急いではいけません。今回は差分の量に圧倒されて判断が鈍りかけた場面があり、これは仕組みよりも運用の問題として反省すべき点でした。

## 復旧の手順

復旧にあたっては、まず現在の tfstate のバックアップを別の場所に退避しました。何か操作を誤ってもやり直せるようにするための、最初の一手です。バックエンドがバージョニング付きのストレージを使っていたため、直前のバージョンに巻き戻すことも選択肢にありましたが、その間に加えられた正当な変更まで失われる恐れがあったため、単純な巻き戻しは避けることにしました。

代わりに採った方法は、実際のクラウド上のリソースを正として、tfstate を手動で組み立て直すというものでした。具体的には、コンソールや API で実在するリソースの識別子を一つずつ確認し、それらを Terraform の管理下に戻す作業を行いました。ここで活躍したのが import の機能です。すでに存在しているリソースをコードと紐付け直し、状態ファイルに正しい情報として登録し直すことができます。

import 作業は地道な作業でした。リソースの種類ごとに必要な識別子の形式が異なり、一つ間違えると全く別のリソースを紐付けてしまう危険もあります。そのため、一つ import するたびに `plan` を実行して差分がゼロになることを確認し、想定外の差分が出た場合はすぐに調査するというサイクルを繰り返しました。数十個あったリソースをすべて import し終えるまでには半日近くかかりましたが、最終的には `plan` が差分なしを返すところまで持っていくことができました。

## 振り返って分かったこと

今回の一件で痛感したのは、tfstate は単なる内部ファイルではなく、インフラの信頼できる唯一の情報源だという認識を全員で共有できていなかったことです。ロックが働いているという表示を見たときに、それを疑って解除するのではなく、まず状況を確認する習慣が必要でした。

また、複数人がインフラを触る体制である以上、誰かが作業を始める前に一声かける、あるいは作業ログを残すといった、仕組みだけに頼らない運用上の工夫も欠かせないと感じました。ロックはあくまで最後の砦であり、それに頼り切った運用は今回のような事故を防ぎきれません。

もう一つの学びは、tfstate が壊れたときに焦って `apply` を打たないことの重要性です。壊れた状態のまま操作を続けると、被害はどんどん広がっていきます。今回は import による地道な復旧という選択肢を取れましたが、これはリソースの数が現実的な範囲に収まっていたからこそ成立した方法でもあります。今後は定期的に tfstate のバックアップを取得する仕組みを整え、万が一の際に復旧の起点を確保しておくことも検討したいと考えています。

Terraform は強力な分、状態管理を誤ったときの影響範囲も大きくなります。ロック、差分、import といった一つひとつの機能の意味を正しく理解し、焦らず手順を踏むことが、結局のところ一番の事故防止策なのだと今回の件で改めて学びました。
