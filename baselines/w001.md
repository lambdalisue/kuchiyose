# 設計ドキュメントの型を決めた

## 背景

kakiburi のリポジトリには、仕様の検討経緯や実装の分割案、保留になった提案などが積み重なっている。これらは日々の作業の中で自然に発生するもので、内容自体は消えているわけではない。むしろ扱いに困っていたのは形式のほうだった。ある日はコードコメントの延長で書き、ある日は README に追記し、ある日は会話のログだけに残していた。結果として、後から「あの判断はどこに書いてあったか」を探すのに毎回手間がかかっていた。

特に困っていたのは、決定そのものと、決定に至る過程の区別がつかない書き方だった。選択肢を検討した痕跡と、最終的にどれを選んだかが同じ段落に混在していると、後から読む側はどこまでが確定していてどこからが検討中なのかを毎回判断し直す必要がある。これは書く側の負担というより、後で読む側の負担として蓄積していく問題だった。

## 選択肢

書き方を決めるにあたって、いくつかの方向を比較した。

一つ目は、既存のツールが用意している定型フォーマットをそのまま採用する案だった。汎用的な項目立てがすでに広く使われているため、迷う余地が少ないという利点がある。ただし、汎用フォーマットは汎用であるがゆえに、このプロジェクト特有の事情——たとえば仕様が実装より先行して変わっていく進め方や、保留にした提案を後から拾い直す運用——にはうまく馴染まない部分があった。項目を埋めることが目的化してしまい、本当に残したい判断の理由が埋もれる懸念もあった。

二つ目は、形式を決めずに、その都度読みやすいと思う書き方で残す案だった。柔軟性は高いが、これはこれまでの延長線上であり、まさに今回困っていたことの再現になる。書き手の気分によって粒度も構成もばらつき、検索性が失われる。

三つ目は、必要最小限の要素だけを固定し、それ以外は自由に書く案だった。固定する要素を絞ることで、書く際の負担を増やさずに、後から読む際の一貫性を確保できる。今回はこの方向で進めることにした。

## 決定

最終的に固定したのは、背景・選択肢・決定・影響・更新という五つの要素だった。

背景には、その判断が必要になった経緯と、放置した場合に何が困るのかを書く。選択肢には、実際に比較した候補を挙げ、それぞれの利点と欠点を対等に扱う。ここで気をつけたのは、採用しなかった選択肢を悪く書きすぎないことだった。検討した時点では妥当な候補だったからこそ比較の対象になったのであり、後から振り返って矮小化すると、なぜその選択肢が候補に挙がったのかという文脈自体が失われてしまう。

決定には、選んだ結論とその理由だけを簡潔に書く。ここに検討の過程を再掲する必要はない。選択肢の節ですでに書いているので、決定の節は結論に徹する。影響には、この決定によって変わる範囲と、変わらない範囲の両方を書く。変わらない範囲を明示することは、後から誰かが「この決定はここにも及ぶのか」と誤って解釈するのを防ぐために欠かせない。更新には、この決定が見直される可能性のある条件を書く。決定を絶対的なものとして固定するのではなく、どういう状況になったら再検討するべきかをあらかじめ書いておくことで、後から読む人が「これはまだ有効な決定なのか」を自分で判断できるようにする。

この五つ以外の構成は自由とした。表にするか箇条書きにするか、長さをどうするかは、その判断の性質に応じて書き手が選べばよい。固定するのは要素の存在であって、表現の形ではない。

## 影響

この型を採用したことで、まず自分自身の書く速度が上がった。何を書けばよいかを毎回考える必要がなくなり、五つの見出しを埋めていけば自然と過不足のない記録になる。読む側にとっても、決定だけを知りたいときは決定の節だけを、経緯まで知りたいときは背景と選択肢の節も読む、という選び方ができるようになった。

一方で、この型が対象とするのは、後から参照される可能性のある判断に限られる。日々の細かい実装上の工夫や、すぐに変わることが分かっている暫定的な処理には、この型を当てはめる必要はない。型を機械的にすべての記述に強制すると、かえって軽い記録を残すことをためらわせてしまう。どの粒度の判断にこの型を使うかは、今のところ書き手の判断に委ねている。

## 更新

この型自体も、固定した五つの要素で十分かどうかは今後の運用次第で見直す余地がある。特に、複数の決定が互いに関連し合う場面が増えてきた場合、決定同士のつながりをどう記録するかは今回の型には含めていない。今のところは単発の判断を想定した設計であり、判断が連鎖する状況が実際に増えてきた段階で、改めて型を見直すことになる。
