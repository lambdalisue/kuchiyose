# 全文検索をやめて DB だけにした話

検索機能を作るとなると、まず全文検索エンジンの導入が検討に上がります。専用のミドルウェアを立て、インデックスを構築し、アプリケーションとは別のライフサイクルで運用する。それが「検索を真剣にやる」ときの定石だと長らく思っていました。しかし今回のプロジェクトでは、稼働していた全文検索エンジンを外し、PostgreSQL 単体での検索に置き換えました。結果として、精度は多少落ちましたが、運用の負荷が大きく下がり、総合的には満足できる選択になりました。

## なぜ全文検索を導入していたのか

検索対象のデータ量はそれほど多くなく、更新頻度も高くありませんでした。それでも導入当初は「将来的にデータが増えるかもしれない」「検索精度を上げたい」という理由で、全文検索エンジンを採用していました。実際、日本語の形態素解析やあいまい検索、関連度によるスコアリングなど、専用エンジンが提供する機能は魅力的です。

ただし運用を続けるうちに、その恩恵よりもコストのほうが目立ってくるようになりました。エンジンのバージョンアップ対応、インデックスの再構築、アプリケーションのデータとインデックスの同期ずれへの対応など、検索機能そのものの改善ではなく、検索エンジンを維持するための作業に時間を取られる場面が増えていったのです。

## DB だけで検索するという選択

そこで検討したのが、PostgreSQL の LIKE 検索と拡張機能である pg_trgm を組み合わせる方法です。LIKE 検索は前方一致であればインデックスが効きますが、部分一致になるとテーブル全体を走査してしまい、データ量が増えるにつれて性能が劣化します。この弱点を補うのが pg_trgm です。文字列を三文字の断片に分割してインデックスを作る拡張機能で、これを使うと部分一致の LIKE 検索でもインデックスを利用できるようになります。

導入の手順としては、対象のデータベースで pg_trgm 拡張を有効にし、検索対象のカラムに対して GIN インデックスを作成するだけです。既存のテーブル構造を変える必要はなく、通常の SQL クエリの中で LIKE や ILIKE を使えば、そのままインデックスの恩恵を受けられます。専用のミドルウェアを立てる必要も、データを別のストレージに複製して同期を取る必要もありません。アプリケーションのデータベースがそのまま検索エンジンになる、という点が最大の利点でした。

## 検索精度というトレードオフ

もちろん、全文検索エンジンが持っていた機能をすべて代替できるわけではありません。形態素解析による単語単位の検索や、関連度に基づくランキング、あいまいな表記揺れへの対応などは、pg_trgm 単体では実現が難しい領域です。実際に移行後、検索結果の精度がわずかに落ちたという声はありました。

しかし、そのユーザーからの声を実際に聞いてみると、多くのケースでは「検索できないと困る」というほどの深刻な問題ではなく、「以前より少し探しにくくなった」という程度の変化でした。検索が製品の中核機能であり、精度の追求がそのまま事業価値に直結するのであれば、専用エンジンの維持コストを払う判断は正しいはずです。逆に、検索が補助的な機能であり、多少の精度低下と運用の単純化を交換できる場合には、DB だけで済ませる選択が合理的になります。

## 運用負荷から見た結論

今回の判断で最も大きかったのは、監視対象や障害点が一つ減ったことです。全文検索エンジンが落ちても検索機能自体は止まらない、バックアップ対象がデータベース一つに集約される、デプロイ時に同期を気にする必要がない。こうした運用上の単純さは、日々の開発体験に静かに、しかし確実に効いてきます。

検索精度と運用負荷は、常にどちらか一方を選ぶトレードオフというわけではありません。データ量やアクセス頻度、検索が事業においてどの程度の重みを持つ機能かによって、最適な位置は変わります。今回のケースでは、その天秤が「DB だけで十分」という結論に落ち着きました。技術選定は一度決めたら固定されるものではなく、運用実績を踏まえて見直す対象であるべきだと、改めて感じさせられた経験でした。
