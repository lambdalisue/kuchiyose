# Kubernetes をやめてコンテナサービスに移した話

長らく EKS 上で Kubernetes クラスタを運用してきましたが、今年に入ってから主要なワークロードを ECS へ移行しました。この記事では、なぜ Kubernetes を手放す判断をしたのか、移行の過程でどこに苦労したのか、そして移行後に運用負荷とコストがどう変わったのかを振り返ります。

## Kubernetes 運用でどこに負荷が集中していたか

チームの規模はそれほど大きくなく、インフラを専任で見ているメンバーは数名程度でした。サービスの数自体は多くはなかったものの、Kubernetes を運用するために必要な知識量は年々増えていきました。

負荷が集中していたのは主に次のような領域です。

- コントロールプレーンとノードのバージョンアップ対応。マイナーバージョンごとに非推奨 API や挙動の変更があり、アップグレード前には毎回検証環境で動作確認が必要でした
- Ingress コントローラーやサービスメッシュ、モニタリング用のエージェントなど、クラスタに同居させるアドオン群の維持管理
- IAM とサービスアカウントの紐付けなど、AWS の権限モデルと Kubernetes のロールベースアクセス制御を両方理解した上でのアクセス制御設計
- ノードのキャパシティ計画。ポッドのリクエストとリミットの設定が甘いと、ノードのリソースが余っているのに新しいポッドがスケジュールされない、といった事態が起きる

これらはいずれも「動かすこと」自体には直結しない作業です。しかし放置するとセキュリティ上のリスクや障害の火種になるため、誰かが継続的に時間を割く必要がありました。結果として、新機能の開発よりも基盤の維持に時間を使う場面が増えていきました。

## EKS のコストの実態

EKS を使う場合、コストは大きく三つの要素に分かれます。コントロールプレーンの利用料、ワーカーノードの計算リソース費用、そしてロードバランサーやデータ転送などの周辺コストです。

このうちコントロールプレーンの費用自体はクラスタ数が少なければ大きな比重を占めません。むしろ問題だったのはワーカーノードの使い方でした。Kubernetes ではノード単位でリソースを確保するため、複数の小さなサービスを混在させてビンパッキングを効率化しないと、実際のアプリケーションが使う量に対してノードのキャパシティが過剰になりがちです。

また、ノードグループのオートスケーリングと、その上で動くポッドのオートスケーリングという二層構造になっている点も、コストの見通しを悪くしていました。ポッドが増えてもノードに空きがなければ新しいノードが立ち上がるまでの間はスケールアウトが完了しません。逆にノードを余分に確保しておくと、使われていない計算リソースに対して料金を払い続けることになります。この二層のスケーリングをうまく噛み合わせるためのチューニングに、想定以上の時間を使っていました。

## ECS への移行を選んだ理由

移行先の候補としては ECS on Fargate を中心に検討しました。判断の軸になったのは次の点です。

- チームの規模に対して、維持すべき抽象化のレイヤーを減らせること
- AWS のマネージドサービスとの統合が前提になっているため、IAM ロールをタスクに直接割り当てられ、権限設計がシンプルになること
- Fargate を使えばノードという単位そのものを管理対象から外せること

Kubernetes が提供する柔軟性、たとえばカスタムリソースやオペレーターパターンによる拡張性は魅力的ですが、それを使い切るほどの複雑なワークロードを自分たちが持っていたわけではありませんでした。振り返ってみると、将来の拡張性のために今の運用負荷を支払い続けている状態だったと感じます。

一方で、Kubernetes のエコシステムにある監視ツールやデプロイツールをそのまま使えなくなる点は明確なトレードオフでした。移行にあたっては、CI/CD パイプラインを ECS のタスク定義更新に合わせて作り直し、ログ収集の経路も見直す必要がありました。

## オートスケールの設計をどう変えたか

ECS on Fargate に移行した後は、オートスケーリングの構造が一層になりました。タスクの数だけを見ていればよく、その裏でノードのキャパシティを確保できているかを気にする必要がなくなったのは、精神的にも運用の複雑さの面でも大きな違いでした。

具体的には、CPU 使用率やリクエストキューの長さといった指標に基づいてタスク数を増減させる設定に切り替えました。Kubernetes の Horizontal Pod Autoscaler と考え方自体は似ていますが、スケールアウトの判断からタスクが実際に起動して受け付け可能になるまでの経路がシンプルになったため、スケールの反応が読みやすくなりました。ノードのキャパシティ不足でスケールアウトが遅延する、という以前よくあったパターンがなくなったのは大きな収穫です。

急激なアクセス増加に対する挙動を検証する際も、確認すべきレイヤーが一つ減ったことで、想定と実際の動きのズレを追跡しやすくなりました。

## 移行後の運用負荷とコストの変化

移行してから数か月が経ち、実感として次のような変化がありました。

- バージョンアップ対応がほぼなくなった。Fargate のプラットフォームバージョンは AWS 側で管理されるため、クラスタのアップグレード計画そのものが不要になった
- アドオンの維持管理コストが消えた。Ingress コントローラーに相当する部分は Application Load Balancer と ECS の統合機能に置き換わり、自分たちでバージョンを追う対象ではなくなった
- コストの内訳が単純になった。タスクが使う vCPU とメモリに応じた課金なので、ノードの余剰リソース分を払い続けるという状態がなくなり、実際の使用量とコストの対応が取りやすくなった

総額としてのコストが大きく下がったかというと、そこまで単純ではありません。Fargate 自体の単価は、自前で調整したノードグループの単価と比べると割高になる場面もあります。ただし、キャパシティ計画やビンパッキングの調整にかけていた人の時間を含めて考えると、総コストとしては下がったと感じています。運用にかかる人的コストは請求書には出てきませんが、実際には最も大きな費用の一つでした。

## 移行して分かったこと・注意点

今回の移行を通じて感じたのは、Kubernetes が悪かったわけではないということです。マルチクラウド戦略を取っている、あるいは非常に多様なワークロードを抱えていて拡張性が本当に必要な組織であれば、Kubernetes が提供する柔軟性は十分に価値を発揮するはずです。

自分たちのケースでは、その柔軟性を活かせるだけのワークロードの多様さがなく、単一クラウド上で動くサービス群を運用しているだけでした。そうした状況では、抽象化のレイヤーを一枚減らして AWS のマネージドサービスに委ねてしまう方が、チームの限られたリソースを本来の開発業務に振り分けられます。

移行を検討する際は、今使っている Kubernetes の機能のうち、実際にどれだけがコアなビジネス要件に紐づいているのかを一度整理してみることをお勧めします。カスタムリソースやオペレーターに依存した仕組みを多く抱えている場合、移行のコストは高くつきますし、そのままの構成を維持する方が合理的な場合もあります。逆に、大半のワークロードがステートレスなコンテナをデプロイして外部からアクセスを受けるだけのシンプルな構成であれば、ECS のようなマネージドなコンテナサービスに置き換えることで、運用負荷とコストの両面で見通しの良い状態を作れる可能性があります。
