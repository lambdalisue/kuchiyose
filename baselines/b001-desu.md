# GraphQL をやめて REST に戻した話

小規模なチームで運用している社内向け SaaS のバックエンドで、去年導入した GraphQL を今年になって REST に戻しました。導入時には「クライアントが必要な項目だけ取れる」「エンドポイントが 1 つで済む」といった利点に魅力を感じていましたが、運用を続けるうちに、その利点をチームの体力で支えきれていないことがはっきりしてきました。この記事では、何がつらかったのか、どう判断したのかを振り返ります。

## 導入した理由

もともとの REST API は、画面が増えるたびにエンドポイントが増え、フロントエンドが必要とする形にレスポンスを整形するための専用エンドポイントが乱立していました。一覧画面用、詳細画面用、ダッシュボード用と、似たようなデータを微妙に違う形で返すエンドポイントが並び、どれを使えばいいのか新しく入ったメンバーが把握しづらい状態になっていました。

このオーバーフェッチとエンドポイント増殖の問題を解決する手段として GraphQL は理にかなって見えました。クライアントがクエリで必要なフィールドを指定すれば、サーバー側は単一のスキーマを維持するだけでよく、フロントエンドの要求が変わってもバックエンドのエンドポイントを増やさずに対応できる。ドキュメントで読んだ通りの利点が、当時の課題にそのままはまるように思えたのです。

## 実際に起きた問題

### N+1 が至る所に潜んでいた

GraphQL のリゾルバは、フィールドごとに独立して解決されます。一覧を返すクエリの中で関連するオブジェクトのフィールドを辿ると、リゾルバは親の件数分だけ呼び出され、その都度データベースへ問い合わせに行きます。REST であれば一つのエンドポイントの中で JOIN したクエリを書けば済んでいたところが、GraphQL のスキーマ設計に忠実に従うと、素朴に書いただけで N+1 が発生する構造になってしまいます。

これに対処するために DataLoader を導入し、同一リクエスト内で発生した個別の問い合わせをバッチ化してキャッシュする仕組みを組みました。DataLoader 自体はよくできた仕組みで、導入した直後は効果も感じられました。ただ、これを機能させるには、リゾルバごとにバッチ関数を用意し、キーの正規化を揃え、キャッシュのスコープをリクエスト単位で正しく切るという設計上の規律が必要でした。新しいフィールドやリレーションを追加するたびに、担当者が DataLoader の使い方を理解していなければ N+1 が静かに戻ってくる。レビューでその都度指摘するコストが積み重なり、気づけば「DataLoader を正しく使えているかを確認する作業」自体がリリースのたびの儀式になっていました。

### スキーマが肥大化し、誰も全体を把握できなくなった

スキーマは最初、数十行程度のシンプルなものでした。しかし機能が増えるたびに型が追加され、既存の型に新しいフィールドがぶら下がり、あるフィールドが別の機能のためだけに存在するようになっていきます。REST であればエンドポイントごとに責務が分かれていたものが、GraphQL では一枚のスキーマに全部が同居するため、変更の影響範囲が見えにくくなりました。

あるフィールドを非推奨にしたくても、そのフィールドをどのクライアントがどのクエリで使っているかを追跡する仕組みがなければ、安全に消せません。結果として、使われなくなったフィールドがスキーマに残り続け、スキーマを読むこと自体が新しいメンバーにとっての負担になっていきました。オーバーフェッチを解決するために導入した仕組みが、今度はスキーマ全体の見通しの悪さという別の負債を生んでいたわけです。

### 運用面での見えにくさ

REST であれば、パスとメソッドを見ればどのエンドポイントが重いのか、どこでエラーが起きているのかがログやモニタリングにそのまま出てきます。GraphQL では、すべてのリクエストが同じエンドポイントに届くため、クエリの内容を見なければ何が起きているのか分かりません。クエリごとの実行時間を計測する仕組みを別途組み込む必要があり、既存の監視の仕組みをそのまま使えない場面が何度もありました。障害対応の際に「どのクエリが遅いのか」を特定するまでの手間が、REST の頃より確実に増えていたのです。

## 戻す判断をした基準

決定的だったのは、チームの規模に対して GraphQL が要求する運用コストが見合っていなかったという点です。N+1 対策、スキーマの整理、クエリごとの監視、いずれも仕組みとしては解決可能ですが、それを維持し続けるための専任の意識と時間が必要でした。数人規模のチームで、しかも全員が兼務でバックエンドを見ている状況では、その規律を全員に維持してもらうことが現実的ではありませんでした。

一方で、当初 GraphQL で解決したかったオーバーフェッチの問題は、実際には REST の設計を見直すだけでも十分に対応できることが分かってきました。画面ごとに専用のレスポンス形式を用意するのではなく、リソース単位でエンドポイントを整理し、クエリパラメータで含めるフィールドを絞れるようにすれば、多くのケースでは過剰な取得を避けられます。すべての要求に完璧に応える必要はなく、実際に困っていた場面をカバーできれば十分だったのです。

## 戻してからの変化

REST に戻した後、まず感じたのは監視のしやすさの回復でした。エンドポイントごとにレイテンシやエラー率を追えるようになり、障害対応の初動が早くなりました。N+1 についても、エンドポイントの中で必要な JOIN を明示的に書くという、以前からあるやり方に戻ったことで、DataLoader のような別の仕組みを維持する必要がなくなりました。

スキーマという単一の巨大な構造がなくなったことで、機能ごとの責務も再びエンドポイント単位で分かれ、影響範囲を把握しやすくなっています。もちろん、エンドポイントが増えていく問題は再び戻ってきますが、以前ほど乱立させないよう、リソース設計のレビューを丁寧に行う運用に切り替えました。

## まとめ

GraphQL は、クライアントごとに異なる要求が多く、専任でスキーマとリゾルバの運用に投資できる体制がある場合には強力な選択肢だと思います。ただ、今回のチームのように運用体力が限られている状況では、N+1 対策やスキーマ管理にかかる継続的なコストが、オーバーフェッチという当初の問題の深刻さを上回ってしまいました。技術選定は、解決したい問題の大きさと、その解決策を維持するために必要な体力を天秤にかけて決めるべきだという、当たり前でありながら忘れがちな教訓を、今回の一件で改めて実感しました。
