CSS 設計を破棄して書き直した

## 何を捨てたか

以前のプロジェクトでは、BEM の命名規則に沿って CSS Modules でコンポーネントごとにスタイルを分割していました。ブロック・エレメント・モディファイアの三層構造は理屈のうえでは筋が通っていて、クラス名を見ただけで所属や役割がわかるという触れ込みでした。しかし実際に運用してみると、その恩恵よりも負担のほうがずっと大きいと感じるようになりました。

一番の問題は、新しいコンポーネントを作るたびに命名を考える時間がかかることでした。ブロック名をどう区切るか、モディファイアをどこまで細かく分けるか、といった判断に毎回頭を使い、しかもその判断にはチームごとの流儀が入り込むため、レビューのたびに指摘が飛び交いました。CSS Modules 自体はスコープを閉じ込めてくれる点で優秀でしたが、命名の設計コストを解決してくれるわけではなく、むしろファイルが増えるほど「このクラス名は正しいか」を考える機会も増えていきました。

もうひとつの悩みは詳細度でした。CSS Modules を使っていても、コンポーネントの入れ子が深くなると、親から子へスタイルを上書きしたい場面がどうしても出てきます。そのたびに詳細度を意識した書き方が必要になり、時にはグローバルなセレクタとの衝突を避けるための工夫までしなければなりませんでした。設計としては局所化されているはずなのに、詳細度の計算という古典的な悩みから逃れられていなかったのです。

## Tailwind への移行

こうした経緯から、思い切って Tailwind に全面移行することにしました。ユーティリティクラスを組み合わせてスタイルを組み立てるという発想は、最初は抵抗がありました。マークアップにクラスがずらりと並ぶ様子は、以前の教科書的な感覚からすると「関心の分離」に反しているように見えたからです。しかし実際に使ってみると、その懸念はほとんど的外れだったとわかりました。

ユーティリティを使う最大の利点は、命名という工程そのものが消えることでした。パディングや文字色を変えたいときに、意味のあるクラス名を考える必要がなく、そのまま該当するユーティリティを当てはめれば済みます。命名に悩む時間がゼロになったことで、レビューの論点もスタイルの見た目そのものに集中するようになり、命名規則の是非を議論するような不毛なやり取りがなくなりました。

詳細度の問題についても、ユーティリティクラスは基本的に単一のプロパティを担当するため、複数のクラスがぶつかり合う場面がほとんどありません。仮に競合が起きても、どのクラスがどのプロパティを担っているかが一目でわかるため、原因の特定に時間がかかりません。BEM と CSS Modules を組み合わせていた頃のように、詳細度の計算をしながらセレクタを組み立てる必要がなくなったのは、想像していた以上に大きな変化でした。

## 書き直して見えたこと

もちろん、ユーティリティクラスにも欠点はあります。マークアップは以前より冗長になり、同じ組み合わせをあちこちに書き写す場面も出てきます。この点については、繰り返し使う組み合わせをコンポーネント側にまとめることで対処しました。スタイルの重複そのものは残りますが、それを吸収する層をコンポーネントの粒度に寄せたことで、以前のように命名や詳細度で消耗することはなくなりました。

振り返ってみると、BEM も CSS Modules も、それぞれ単体では理にかなった仕組みでした。命名規則によってクラスの意味を保証し、スコープの仕組みによって衝突を防ぐという狙いは間違っていません。ただ、両方を組み合わせて運用すると、命名のコストと詳細度の管理という、本来別々に解決されるべき問題が重なり合ってしまい、開発の速度を落とす要因になっていました。

設計を破棄するという判断は、当初は後ろめたさもありました。せっかく積み上げてきた規約を捨てることになるからです。ですが、実際に書き直してみると、失ったのは規約という名の手続きだけで、スタイルの一貫性や保守性はユーティリティの組み合わせによって別の形で保たれていました。設計を美しく保つことよりも、日々の変更にかかる時間を減らすことのほうが、このプロジェクトにとっては価値が大きかったのだと思います。
