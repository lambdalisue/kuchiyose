# React の状態管理をやめた話

状態管理ライブラリを導入するたびに、私はどこかで「これで解決する」と思い込んでいた。Context を敷けばプロップスドリリングは消え、Zustand を挟めば再レンダリングの悩みから解放される、と。実際にはどちらも導入して、そのどちらもやめた。この記事はその顛末についてのものだ。

## 最初の問題は useState だった

きっかけは単純だった。あるページで、フォームの入力値をいくつかの子コンポーネントに渡す必要が出てきた。最初は親で useState を持ち、props でバケツリレーのように下の階層まで渡していた。コンポーネントが2つや3つのうちは何も問題がない。しかし機能が増えるにつれて、中間のコンポーネントは自分では使わない値をただ右から左へ受け渡すだけの存在になっていった。いわゆるプロップスドリリングで、変更のたびに中間層のコンポーネントの型定義まで書き換える羽目になった。

このとき下した判断が「グローバルな状態置き場を作ろう」だった。今思えば、ここが最初のボタンの掛け違いだったように思う。

## Context を導入して起きたこと

React 標準の Context を使えば、props を経由せずに値を下の階層まで届けられる。実装は素直で、Provider でツリーを包み、useContext で好きな場所から値を取り出すだけだ。プロップスドリリングはたしかに解消された。中間コンポーネントの型定義を書き換える作業からも解放された。

問題はそのあとに出てきた。Context の値を更新すると、その Context を購読しているコンポーネントすべてが再レンダリングされる。最初は値の種類が少なかったのでほとんど気にならなかったが、フォームの状態やUIの開閉状態、選択中のアイテムなど、性質の異なる値を同じ Context にまとめて詰め込むようになると、些細な入力のたびに関係のない箇所まで再レンダリングされるようになった。

対策として Context を値の種類ごとに分割したり、useMemo で値をメモ化したりもした。効果はあったが、そのたびにコードの見通しは悪くなった。Context を経由して値を取り出しているコンポーネントは、どの Provider にぶら下がっているのかをコード上で追わないと分からず、テストを書くときにも Provider でラップする作業が必ず一段挟まるようになった。状態を追うための負担を、プロップスドリリングという分かりやすい形から、Provider の階層という分かりにくい形に付け替えただけだったのかもしれない。

## Zustand に乗り換えた理由と、そこで起きたこと

次に試したのが Zustand だった。Context の再レンダリング問題は、購読の仕組みが「ツリー全体に伝播する」ことに起因していたので、値ごとに購読できるストアライブラリに乗り換えれば解決するだろうという見立てだった。実際、Zustand は使っている値だけを選択的に購読できるので、無関係な再レンダリングはかなり減った。Provider でツリーを包む必要もなく、コンポーネントの外からでもストアの値を読み書きできる手軽さも気に入っていた。

ところがしばらく運用していると、別の種類の問題が顔を出してきた。ストアがアプリケーション全体で共有される単一の存在になった結果、あるコンポーネントが不要になったときに、それが参照していた状態をストアから消してよいのかどうかの判断がつきにくくなった。ストアの定義ファイルはどんどん肥大化し、どの状態がどの画面のためのものかを示す境界が失われていった。あるコンポーネントを削除したのに、そのコンポーネントのために作った状態だけがストアに取り残される、ということが何度か起きた。

そして何より気づいたのは、そもそも多くの状態がグローバルである必要などなかったということだ。フォームの入力値も、モーダルの開閉状態も、選択中のタブも、実際にはそれを使っているコンポーネントの部分木の中でしか参照されていなかった。グローバルなストアという便利な置き場があったせいで、本来ローカルであるべき状態まで気軽にそこへ放り込んでしまっていたのだと思う。

## やめてみて分かったこと

結局、Context も Zustand も使うのをやめて、状態は基本的に useState に戻し、必要な場所だけに置くという方針に落ち着いた。プロップスドリリングを恐れるあまり、状態を実際に必要とする範囲よりも高い位置に引き上げていたことが、そもそもの問題だったと今では思っている。

具体的にやったことは次のようなものだ。

- 状態を使っているコンポーネントの共通の親まで、状態の定義位置を下げ直す
- 複数の子コンポーネントで同じ値が必要な場合は、コンポジションで組み替えて、値を必要としない中間層を経由させないようにする
- 本当にアプリケーション全体で共有すべき値だけを見極める。認証中のユーザー情報のような、ごく少数のものに限られた
- それでも props の受け渡しが煩雑になる箇所は、children を使って構造そのものを見直す

やってみると、プロップスドリリングだと思っていたものの多くは、実はコンポーネントの分割の仕方そのものが不自然だったことのサインだった。状態を必要とする場所の近くにコンポーネントの境界を引き直すと、props はほとんど1階層か2階層しか渡らなくなり、そもそも問題として認識されなくなった。

再レンダリングについても同様だった。状態をグローバルな置き場から個々のコンポーネントに戻したことで、ある値が更新されたときに再レンダリングされる範囲は自然とその値を使っているコンポーネントだけに収まるようになった。Context の分割や Zustand の選択的購読で頑張って再現しようとしていたものは、状態を正しい場所に置きさえすれば最初から手に入る性質だったということになる。

## 状態管理ライブラリが悪いわけではない

誤解のないように書いておくと、Context や Zustand そのものが悪いという話ではない。複数の画面をまたいで本当に共有すべき状態、たとえばログイン中のユーザー情報や、アプリ全体のテーマ設定のようなものには、今でも Zustand を使っている。問題だったのは、状態の置き場所を選ぶ基準を持たないまま、便利そうだからという理由でグローバルな仕組みに頼っていたことだ。

プロップスドリリングや再レンダリングの負荷は、状態管理ライブラリの選定で解決する問題ではなく、多くの場合コンポーネント構成の見直しで解決する問題だったのだと思う。ライブラリを導入する前に、その状態が本当はどの範囲でしか必要とされていないのかを一度疑ってみる価値はある。
