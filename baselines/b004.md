# 全文検索をやめて DB だけにした

検索用に専用の全文検索エンジンを立てるのをやめて、PostgreSQL だけで検索機能をまかなう構成に切り替えた。移行してから半年ほど経つので、そのときの判断と、実際に運用してみてどうだったかを書いておく。

## 何を抱えていたか

もともとの構成では、アプリケーション本体の DB とは別に全文検索エンジンを立てて、記事やコメントのデータを検索用にインデックス化していた。検索クエリはそちらに投げ、結果を DB の ID と突き合わせて返す、という形だった。

検索精度そのものは悪くなかった。形態素解析によるトークナイズや、関連度スコアによる並び替えができるので、雑なキーワード検索でもそれなりの結果が返ってくる。問題は精度ではなく、その周辺にあった。

- DB と検索エンジンのデータを常に同期させておく必要があり、同期が遅延すると「検索結果には出るのに開けない」「更新したのに検索に反映されない」といった不整合が起きる
- 検索エンジン自体のクラスタ運用、バージョンアップ、リソース監視という、アプリケーションのドメインとは無関係な作業が継続的に発生する
- 開発環境やテスト環境でも同じミドルウェアを動かす必要があり、セットアップの手間が増える

検索対象のデータ量は数十万件程度で、いわゆる「全文検索エンジンが本当に必要な規模」には達していなかった。にもかかわらず、専用ミドルウェアを維持するコストだけは規模に関係なく発生し続けていた。この不釣り合いが、やめる判断の一番の理由になった。

## LIKE だけでは足りなかった部分

検索エンジンを外すとなると、まず候補に挙がるのが LIKE 検索だが、これだけでは実用に耐えなかった。前方一致であればインデックスが効くものの、部分一致になると全件スキャンに近い動きになり、データ量が増えるほど遅くなる。加えて、表記ゆれや送り仮名の違いに弱く、ヒットするはずの記事が検索結果から漏れることも多かった。

そこで採用したのが pg_trgm 拡張だ。文字列を 3 文字単位の断片に分解し、その断片の一致度合いで類似度を判定する仕組みで、これを使うと部分一致検索でも GIN インデックスが効くようになる。対象カラムに GIN インデックスを trigram 演算子クラスで作成しておけば、LIKE によるあいまいな部分一致検索でもインデックススキャンが選ばれるようになり、体感できるほど速度が改善した。

類似度のしきい値を調整できるので、単純な部分一致だけでなく「近い文字列」を拾う緩めの検索も同じ仕組みで実現できる。日本語特有の表記ゆれ全般をカバーできるわけではないが、記事タイトルやタグ名といった短めのテキストに対しては十分な精度が出た。

## 検索精度は下がったのか

結論から言うと、体感できるほどの劣化は感じていない。もともとの検索エンジンが持っていた形態素解析による賢いトークナイズや、複数条件を組み合わせた高度なスコアリングは失ったが、実際のアクセスログを見返すと、ユーザーが打ち込む検索語の大半は単純なキーワードの組み合わせで、複雑なクエリはほとんど使われていなかった。

つまり、こちらが想定していた「検索エンジンでなければ実現できない精度」は、実際のユースケースの上では過剰装備だった。むしろ DB 側に検索処理を寄せたことで、検索結果と実データの不整合という、精度以前の信頼性の問題が解消されたことのほうが体感として大きい。

## 運用負荷はどう変わったか

一番効果が大きかったのはここだ。検索エンジンのクラスタを監視する必要がなくなり、障害対応の対象からも外れた。デプロイのステップからインデックス再構築のジョブが消え、環境構築の手順書からもミドルウェアのセットアップ項目が丸ごと消えた。

バックアップの範囲も単純になった。以前は DB と検索エンジンの両方を意識してリストア手順を組む必要があったが、今は DB だけを見ていればよい。障害が起きたときに確認する対象が一つ減るというのは、想像していた以上に精神的な負担を減らしてくれた。

もちろん、この判断がどのプロジェクトでも成り立つわけではない。検索対象が数千万件を超えるような規模や、形態素解析に基づく高度な関連度スコアリングが本当に必要な用途では、専用の検索エンジンを使うほうが理にかなう。今回はデータ規模とユースケースの両方が、DB だけで賄える範囲に収まっていたというだけの話だ。構成を選ぶときは、想定される最大精度ではなく、実際に使われている検索パターンを基準にしたほうがいい、というのが今回得た教訓だった。
