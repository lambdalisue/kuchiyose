フォームのアクセシビリティを直した話

## きっかけ

問い合わせフォームで入力エラーが起きたとき、画面のどこかに赤い文字が出るだけで、次に何をすればいいのか分かりにくいという指摘を受けました。マウスとキーボードを両方使って自分でも試したところ、視覚的には何が起きているか把握できるものの、キーボードだけで操作するとエラーの発生に気づけないことが分かりました。さらにスクリーンリーダーで読み上げさせてみると、エラーメッセージの内容が読み上げられず、フォーム全体が「なぜか送信できない」状態のまま止まっているように聞こえることも確認できました。原因を一つずつ洗い出していくと、根っこにあったのはラベルとエラーメッセージと入力欄の結びつきが弱かったことでした。

## label とフォームコントロールの関係を作り直す

最初に見直したのは label タグと入力欄の対応関係です。見た目にはラベルらしきテキストが入力欄の上に置かれていましたが、実際には単なる装飾用のテキストで、input 要素と構造的に紐づいていませんでした。この状態だと、スクリーンリーダーは「名前」というラベルの文字列を読み上げず、入力欄をただの空欄として扱ってしまいます。目の見えるユーザーには見た目で分かる対応関係が、支援技術を使うユーザーには一切伝わっていなかったわけです。

対処としては、label 要素の for 属性と入力欄の id 属性を対応させることで、両者を明示的に結びつけました。こうすることで、スクリーンリーダーは入力欄にフォーカスが移った瞬間にラベルの文言を読み上げてくれるようになります。加えて、ラベルをクリックしたときにも対応する入力欄へフォーカスが移動するようになるため、クリック領域が広がるという副次的な効果もありました。これはマウス操作でも地味に助かる改善で、特に小さなチェックボックスやラジオボタンでは操作性がはっきり変わります。

## エラーメッセージを入力欄と結びつける

次に手を入れたのはエラーメッセージの扱いです。もともとはエラーが発生すると、入力欄の下に赤文字の説明が挿入される作りになっていました。見た目上は入力欄のすぐ近くに表示されるため、視覚的には十分に伝わります。しかし構造としては、そのエラーメッセージと入力欄との間に何の関連付けもありませんでした。スクリーンリーダーのユーザーが入力欄にフォーカスしても、近くにあるはずのエラー文言は読み上げられず、視覚的な近さだけに頼った設計になっていたのです。

ここで使ったのが aria-describedby です。エラーメッセージの要素に id を振り、入力欄側の aria-describedby にその id を指定することで、支援技術上でも「この入力欄には、このエラー説明が付随している」という関係を明示できます。これにより、入力欄にフォーカスが当たった際に、ラベルに続けてエラーの説明文まで読み上げられるようになりました。エラーが発生していないときは aria-describedby の値を空にしておき、エラーが出たタイミングで id を差し込むという切り替え方にしています。常に同じ id を指し続けると、エラーが解消された後も古い説明を読み上げ続けてしまうことがあるため、この切り替えは意識して行う必要がありました。

## エラー通知のタイミングと afe-live の役割

もう一つ見落としていたのが、エラーメッセージが後から動的に追加される場合の通知です。ページを読み込んだ時点で存在する要素であれば aria-describedby だけでも十分ですが、送信ボタンを押した後にエラーメッセージが新たに挿入されるケースでは、スクリーンリーダーのユーザーがそのタイミングでフォーカスをどこに置いているかによって、エラーの発生自体に気づけないことがあります。フォーカスが送信ボタンに残ったままだと、エラーメッセージの要素は画面に存在していても、ユーザーがそこへ移動しない限り読み上げられません。

そこで、エラーメッセージを表示する領域に、動的な変化を通知する属性を付けました。これにより、内容が更新された際にスクリーンリーダーがその変化を検知し、フォーカスの位置に関わらず新しい内容を読み上げてくれるようになります。ただし、この手の通知は多用すると煩わしく感じられるため、フォーム全体のエラー概要を伝える領域にだけ絞って使うようにしました。個々の入力欄のエラーは aria-describedby による説明に任せ、動的な通知は「送信に失敗した」という全体の事実を伝える一箇所に集中させる、という役割分担です。

## フォーカス管理で気づきを届ける

エラーメッセージが読み上げられるようになっても、まだ課題が残っていました。送信ボタンを押した後、フォーカスがボタンの上に留まったままだと、ユーザーは次に何をすべきか分からないまま取り残されてしまいます。視覚的にページの上部にエラー概要が表示されていても、キーボードやスクリーンリーダーで操作している場合、その情報に自分から気づきに行く手段がなければ意味がありません。

そこで、送信が失敗した際にはエラー概要を表示する領域へ意図的にフォーカスを移動させるようにしました。フォーカスが移動すると、スクリーンリーダーは移動先の内容を自動的に読み上げてくれるため、ユーザーは何もしなくても「送信に失敗し、こういう理由がある」という情報を受け取れます。ここで気をつけたのは、フォーカスを移動させる対象がキーボードで実際にフォーカス可能な要素である必要があるという点です。見出しのような要素はそのままではフォーカスを受け取れないため、プログラム的にフォーカスを当てられるようにする調整も必要でした。また、フォーカスを移動させた後に矢印キーやTabキーで自然に次の要素へ進めるかどうかも確認し、フォーカスが迷子にならないように動線を整えました。

## 直してみて分かったこと

一連の修正を終えて感じたのは、アクセシビリティの問題は個々の要素を直しただけでは終わらないということです。ラベルと入力欄、エラーメッセージと入力欄、エラー発生とフォーカスの移動、それぞれの対応関係が途切れていると、視覚的には十分に見えるフォームでも、スクリーンリーダーを使うユーザーにとっては情報がばらばらに感じられてしまいます。逆に言えば、対応関係さえきちんと結んでおけば、既存の見た目をほとんど変えずに体験を改善できるという手応えもありました。

今回はスクリーンリーダーでの実機確認を毎回の修正のたびに行いましたが、これは想像以上に効果がありました。コードを読んだだけでは気づけない読み上げ順序のずれや、説明が重複して聞こえる箇所などが、実際に耳で聞くことで初めて見えてきます。フォームのような入力を伴うUIでは特に、視覚的な確認だけに頼らず、実際にキーボードとスクリーンリーダーで一通り操作してみる工程を、修正の一部として組み込んでおくべきだと感じました。
