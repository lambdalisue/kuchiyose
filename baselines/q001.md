# E2E テストを減らした

E2E テストは書いた瞬間から負債になる。これは kakiburi の CI を触っていて実感したことで、ある時期からブラウザ操作を経由するテストを意図的に削り、代わりにユニットテストと統合テストの層を厚くする方向に舵を切った。この記事はその判断の経緯と、実際にどう効いたかについての記録である。

## きっかけはフレーキーの蓄積

最初の兆候は CI の赤だった。コードを一切変更していないのに、同じテストが通ったり落ちたりする。原因を追うと、決まって E2E テストのどれかがタイムアウトしているか、要素が見つからずにセレクタが失敗しているかのどちらかだった。

フレーキーなテストの厄介なところは、失敗そのものよりも「信頼を失わせる」ことにある。赤くなっても本当にバグがあるのか、単に不安定なだけなのかを毎回判断しなければならない。何度か再実行して通ればマージする、という運用が定着すると、テストが落ちること自体への感度が鈍る。本来は品質のシグナルであるはずの CI の色が、ただのノイズになってしまう。

この状態を放置すると、いずれ本物のバグが混じったときにも「またいつものやつだろう」と見過ごされる。テストピラミッドの頂点にあるはずの E2E テストが、下の層を守るどころか、テスト全体への信頼を蝕んでいた。

## テストピラミッドを見直す

改めてテストピラミッドの発想に立ち返ると、E2E テストは本来「土台の上に薄く乗る仕上げの層」であるべきものだ。ところが実際のテストスイートを棚卸しすると、ロジックの分岐やエラーハンドリングの検証まで E2E テストに頼っている箇所が少なくなかった。ユニットテストで十分に検証できる内容を、わざわざブラウザを起動してまで確認していたことになる。

なぜそうなったかを振り返ると、理由は単純だった。機能を作った直後は「実際に動く様子を見て確認したい」という気持ちが強く、E2E テストが一番手っ取り早く安心感を得られる手段に見える。だが、その安心感は開発時点のものであって、継続的に回すテストスイートの設計としては別の話だ。書いたときの都合と、維持していく都合を混同していたのが根本の原因だった。

そこで、E2E テストが担うべき役割を絞り込むことにした。

- ユーザーが実際に踏む主要な導線が、画面をまたいで壊れていないかの確認
- 個々のロジックの正しさは、下の層のテストに委ねる
- ブラウザでしか検出できない種類の不具合(レイアウト崩れ、JavaScript の実行時エラーなど)に限定する

この基準に照らすと、既存の E2E テストの多くは対象外だった。個別のバリデーションルールやエラーメッセージの文言まで検証しているものは、対応するユニットテストか、API を直接叩く統合テストに置き換えられる。

## 削減の進め方

一気に書き換えると影響範囲が読めなくなるため、削減は段階的に進めた。まず、直近半年のテスト結果を洗い出し、失敗頻度が高く、かつ検証内容がロジックに閉じているものから手をつけた。フレーキーの温床になっていたテストは、たいてい検証範囲が広すぎるものだった。一つのシナリオの中でログイン、データ入力、保存、表示確認までを一続きに検証しているようなケースは、途中のどこか一箇所が不安定になるだけで全体が落ちる。

こうしたテストを分解し、ログイン処理はユニットテストで、保存後のデータ整合性は API レベルの統合テストで、画面表示の確認だけを E2E テストとして残す、という形に切り分けていった。結果として一本の大きな E2E テストが、粒度の細かい複数のテストに分散し、それぞれが独立して失敗理由を特定できるようになった。

置き換えの際に意識したのは、カバレッジの数字を落とさないことよりも、何を検証しているかを明確にすることだった。E2E テストが担っていた「動作確認」という曖昧な役割を、各層がそれぞれ何を保証するのかというレベルまで分解し直した。

## 実行時間と信頼性の両面で効果があった

削減の効果は、まず実行時間に表れた。ブラウザの起動とページ遷移の待ち時間がテスト実行全体の大半を占めていたため、対象を絞り込んだだけで CI の所要時間は大きく短縮された。開発中に何度もテストを回して確認するサイクルが速くなり、変更のフィードバックを得るまでの待ち時間が減ったことで、開発体験そのものが改善した。

もう一つの効果は、フレーキーの発生率が下がったことだ。検証範囲を絞ったことで、一つのテストが失敗する原因の候補が減り、赤くなったときに何が壊れたのかをすぐに特定できるようになった。再実行すれば通るかもしれない、という曖昧な期待に頼る場面がほとんどなくなり、CI が赤くなった時点でそれを本物の不具合として扱う習慣が戻ってきた。

信頼性という観点では、テストの本数を減らしたにもかかわらず、検出できる不具合の種類はむしろ増えた。E2E テストに寄せていたころは検証が粗く、細かいロジックの誤りは実際の操作を通さないと見つからなかった。層を分けたことで、ロジックの誤りはユニットテストの段階で、画面をまたいだ不整合は統合テストの段階で、レイアウトや表示の崩れだけを E2E テストで捕まえる、という役割分担ができた。

## 振り返って

E2E テストを減らす、という判断は一見するとテストの手を抜いているように見えるかもしれない。しかし実際にやってみると、これはテストの量を減らす話ではなく、どの層で何を検証するかを整理し直す話だった。ブラウザを経由しなければ確認できないことだけを E2E テストに残し、それ以外はより速く安定して実行できる層に移した結果、実行時間は短くなり、フレーキーは減り、CI の結果を素直に信頼できるようになった。

テストピラミッドという言葉は聞き慣れているが、実際に土台と頂点のバランスが崩れている状態に気づくのは、フレーキーが積み重なって信頼を失い始めてからのことが多い。今回の経験から得た教訓は、E2E テストの本数を評価するときは、カバレッジではなく、そのテストでなければ検出できない不具合が何かを基準にするべきだということだった。
