API リファレンスを自動生成にした

## 手作業のリファレンスが抱えていた問題

API のドキュメントを手で書き続けるチームには、共通した悩みがあります。エンドポイントを追加したとき、実装は進んでも、ドキュメントの更新が後回しになりがちだということです。レビューでコードの正しさは厳しく見られますが、リファレンスの記述までは目が届きません。結果として、実装とドキュメントのあいだに少しずつ乖離が積み重なっていきます。

この乖離は、最初のうちは小さなものです。パラメータの説明が古いままだったり、レスポンスに新しく増えたフィールドが載っていなかったりする程度です。しかし放置すると、利用者はドキュメントを信用しなくなり、結局はソースコードを直接読むようになります。そうなってしまうと、ドキュメントを維持するコスト自体が無駄になってしまいます。

この状態を変えるために、私たちは API リファレンスをコードから自動生成する仕組みに切り替えました。

## OpenAPI を単一の情報源にする

最初に決めたのは、API の仕様を OpenAPI のスキーマとして表現し、それを唯一の正とすることでした。エンドポイントのパス、リクエストのパラメータ、レスポンスの構造、認証方式といった情報を、すべて OpenAPI のドキュメントに集約します。

このとき重要だったのは、スキーマを実装から独立した別ファイルとして手で書くのではなく、実装コード自体から抽出する方式を選んだことです。多くの言語には、ルーティングの定義やリクエストハンドラの型情報から OpenAPI のスキーマを組み立てるライブラリが用意されています。こうした仕組みを使えば、エンドポイントの定義とスキーマが同じ場所に存在することになり、片方だけを更新して他方を忘れるという事故が起きにくくなります。

もちろん、この移行には手間がかかりました。既存のエンドポイントすべてに型情報やアノテーションを追加する作業が必要で、当初は数週間分の作業になると見積もっていました。しかし、これは一度きりのコストです。以降に追加されるエンドポイントは、実装を書く時点で自然にスキーマも生まれるようになります。

## コード生成で人の手を減らす

OpenAPI のスキーマが手に入れば、そこから多くのものを自動的に作り出せます。私たちが最初に着手したのは、リファレンスサイトそのものの生成でした。スキーマを読み込んで、エンドポイント一覧、パラメータの表、サンプルのリクエストとレスポンスを含む静的なサイトを組み立てるツールを導入し、ビルドの一工程として組み込みました。

次に取り組んだのは、クライアントライブラリのコード生成です。社内の複数のサービスが同じ API を呼び出しており、それぞれが手書きの HTTP クライアントを持っていました。スキーマから型安全なクライアントコードを生成するようにしたことで、レスポンスの型が変わればコンパイルエラーとしてすぐに気づけるようになりました。これは副次的な効果でしたが、ドキュメントの乖離を防ぐこと以上に、開発者からの評判が良かった部分です。

コード生成を導入して実感したのは、生成物を手で編集してはいけないという当たり前の原則の重要性です。生成されたファイルに手を入れてしまうと、次回の生成で上書きされて変更が消えるか、あるいは生成ロジックとの整合性が取れなくなります。そのため、生成物は必ずビルドの一部として作り直す運用にし、リポジトリにコミットする場合も生成コマンドの実行結果であることが分かるようにしました。

## それでも残る乖離とレビューの役割

自動生成に切り替えたからといって、乖離が完全になくなったわけではありません。スキーマそのものが実際の挙動とずれてしまうことは、依然として起こり得ます。たとえば、エラーレスポンスの型を宣言していても、実装のある分岐だけがその型に沿わない値を返していることがあります。これはスキーマと実装の食い違いであり、コード生成の仕組みだけでは検出できません。

この種の乖離を見つける役割を担うのが、レビューです。私たちは、実際のリクエストとレスポンスをスキーマと突き合わせて検証するミドルウェアをテスト環境に組み込みました。これにより、スキーマに違反するレスポンスが返された場合には、テストの段階で失敗として検出できます。人の目によるレビューは、この機械的な検証をすり抜けるもの、たとえばフィールドの説明文が実態と合っていないといった、意味のレベルでの乖離を拾う役割に絞られました。

振り返ってみると、自動生成がもたらした一番の変化は、ドキュメントを書く手間が減ったことよりも、乖離が生まれる場所を絞り込めたことにあります。以前は実装からドキュメントに至るまでのあらゆる箇所で乖離が起こり得ましたが、いまはスキーマと実装のあいだ、そしてスキーマと実際の挙動のあいだという、限られた箇所を見張ればよくなりました。レビューの労力は減らないかもしれませんが、どこを見ればよいかが明確になったことで、見落としは確実に減りました。
