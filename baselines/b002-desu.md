# 非同期処理をキューに逃がした

サービスが成長してくると、リクエストの中で完結させていた処理がだんだん重くなってきます。画像のリサイズ、外部 API への通知、メール送信、集計処理。最初はリクエストと同じプロセスの中で同期的にこなしていても困りませんが、処理対象が増えるにつれてレスポンスタイムが伸び、やがてタイムアウトやリトライの嵐でユーザー体験を損なうようになります。今回、そうした処理を SQS を使ったキュー構成に逃がした経験を整理します。

## なぜキューに逃がすのか

同期処理の一番の問題は、リクエストを受け付けたプロセスが処理の完了まで責任を持ってしまうことです。外部サービスが遅延すればそのままユーザーを待たせますし、途中でプロセスが落ちれば処理は中途半端なまま失われます。これを解決する定石が、時間のかかる処理をキューに積み、別プロセスのワーカーが非同期に取り出して実行する構成です。

リクエストを受けたアプリケーションは、処理内容をメッセージとして SQS に送信するだけで応答を返せます。実際の処理はワーカーが後から拾って実行するので、外部サービスの遅延やレスポンス生成の重さがユーザーへの応答時間に直結しなくなります。責任の境界がはっきりするのも利点で、アプリケーション側は「キューに積んだこと」に責任を持ち、ワーカー側は「積まれたメッセージを最終的に処理し切ること」に責任を持つ、という分担ができます。

## ワーカーの設計で意識したこと

ワーカーはキューをポーリングし、メッセージを取り出しては処理を実行し、成功したらメッセージを削除する、という単純なループで動きます。ここで重要なのは、ワーカーの台数を独立してスケールできる点です。処理が詰まってきたらワーカーを増やせばよく、アプリケーションサーバー側のスケーリングとは切り離して考えられます。

ただし単純なループの裏には、考慮すべき点がいくつも隠れています。ひとつは可視性タイムアウトです。ワーカーがメッセージを取り出してから処理を終えて削除するまでの間、そのメッセージは他のワーカーから見えなくなりますが、処理に想定以上の時間がかかると可視性タイムアウトが切れ、別のワーカーが同じメッセージを再度取り出してしまうことがあります。つまり、同じ処理が二重に実行される可能性は常にある、という前提で設計する必要があります。

## 冪等性という前提

この二重実行の可能性こそが、キューを使った非同期処理の設計で最も重要な観点だと感じました。SQS は基本的に「少なくとも一度は届ける」という配送保証であり、「ちょうど一度だけ届ける」ことは保証してくれません。ネットワークの瞬断やワーカーの再起動、可視性タイムアウトの超過など、あらゆる理由で同じメッセージが複数回処理される可能性があります。

したがって、ワーカー側の処理は冪等でなければなりません。同じメッセージを二回処理しても結果が変わらないように作る、ということです。具体的には、処理対象のリソースに一意な識別子を持たせ、その識別子をキーにして「すでに処理済みかどうか」を確認してから本処理に入る、という形を取りました。決済のような重い操作ほどこの確認が重要で、二重課金のような致命的な不具合を防ぐには、キュー側の設定をどう調整しても限界があり、最終的には処理そのものを冪等に作り込むしかありません。キューは「一度は届ける」ことしか保証しないのだから、届いた後の振る舞いはアプリケーション側の責任だ、と考えるようになりました。

## リトライとデッドレター

処理の途中で一時的なエラーが起きることは珍しくありません。外部 API が瞬間的に不調だったり、依存しているデータベースが混雑していたり。こうした一時的な失敗に対しては、メッセージを削除せずにキューに残しておけば、可視性タイムアウトが切れた後に自動的に再配信されます。これによって、ワーカー側で複雑なリトライ処理を自前で書かなくても、キューの仕組みに乗るだけで再試行が実現できます。

ただし、際限なく再試行し続けると、根本的に処理できないメッセージが延々とキューに残り続け、正常なメッセージの処理を圧迫してしまいます。そこで役立つのがデッドレターキューです。一定回数の再配信を経てもなお処理に失敗したメッセージは、通常のキューから切り離してデッドレターキューに移動させます。これにより、壊れたメッセージや想定外のデータ形式によって処理が詰まり続けるリスクを、通常の処理経路から隔離できます。

デッドレターキューに溜まったメッセージは、アラートを通じて気づけるようにしておき、内容を確認したうえで手動で再投入するか、破棄するかを判断する運用にしました。ここで大事なのは、デッドレターキューを「失敗の墓場」として放置しないことです。定期的に中身を確認する仕組みがないと、静かに失敗し続ける処理に誰も気づかないまま、ユーザーへの通知が届いていなかった、といった事態を引き起こしかねません。

## 振り返って

キューを導入すること自体は技術的にそれほど難しくありません。難しいのは、非同期処理特有の前提、つまりメッセージは重複して届き得ること、順序は保証されないこと、失敗は必ず起きることを受け入れて、それに耐える処理を設計することです。同期処理をそのままキューの後ろに移しただけでは、重複実行やエラーの蓄積によってかえって障害を複雑にしてしまいます。冪等性を前提にした処理設計と、リトライおよびデッドレターキューによる失敗の可視化をセットで用意して初めて、キューに逃がした非同期処理は安定して運用できるようになったと感じています。
