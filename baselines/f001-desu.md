react の状態管理をやめた話

小さなチームで React アプリを育てていくと、状態管理は必ずどこかで話題に上がります。私たちのプロジェクトでも、初期は useState だけで十分でした。ボタンを押したらモーダルが開く、入力欄の値を保持する、そういった単純な状態はコンポーネントの中に閉じ込めておけば見通しがよく、誰が読んでもすぐに理解できるコードになっていました。

問題が表面化したのは、機能が増えてコンポーネントの階層が深くなってからです。ユーザー情報や選択中のプロジェクト、通知の未読件数といった、アプリ全体で共有したい状態が増えてきました。最初にやったことは多くのチームと同じで、useState をコンポーネントツリーの上のほうに置き、それを props で下の階層まで渡していくというやり方でした。これがいわゆるプロップスドリリングです。

最初のうちは我慢できました。しかし階層が 5 段、6 段と深くなるにつれ、途中のコンポーネントは自分では使わない値をただ中継するためだけに props を受け取るようになりました。あるコンポーネントの引数リストを見ても、それが実際に何を必要としているのか、それとも単に子孫のために運んでいるだけなのか、コードを読むだけでは判断できません。新しい状態を一つ追加するたびに、中継役のコンポーネントすべてに手を入れる必要があり、変更のたびに広い範囲のテストを書き直す羽目になりました。

この痛みを解消するために導入したのが Context です。React 標準の機能で追加のライブラリも要らず、公式ドキュメントにも状態共有の手段として紹介されているので、導入のハードルは低く感じられました。実際、プロップスドリリングはほぼ解消されました。ユーザー情報も選択中のプロジェクトも、Provider の下にあるコンポーネントならどこからでも直接参照できるようになり、中継のためだけの props はコードから消えていきました。

ところが今度は別の問題が姿を現しました。Context の値を更新すると、その Provider の配下にあるコンポーネントすべてが再レンダリングの対象になります。通知の未読件数のような、更新頻度が高く画面の一部でしか使われない値を、ユーザー情報のような更新頻度が低い値と同じ Context にまとめて入れていたのが良くありませんでした。バッジの数字が変わるたびに、関係のない一覧画面やフォームまで再レンダリングされ、体感できるほどの遅延が出るようになったのです。

対策として Context を値の性質ごとに分割し、更新頻度の高いものと低いものを別の Provider に分ける、という定石通りの改善を行いました。効果はありましたが、Context の数が増えるほど、どの値がどの Provider に属しているのかを把握するコストが上がっていきます。加えて、Context 自体には更新の仕組みが用意されていないため、値を書き換えるための関数も一緒に用意してあげる必要があり、単純な状態共有のはずが、独自の小さな仕組みを何個も抱えることになっていきました。

そこで検討したのが Zustand の導入です。Provider でツリーを囲む必要がなく、フックとしてストアの値を取り出すだけで済みます。しかも Zustand は購読しているコンポーネントだけを再レンダリングする仕組みを持っているため、Context で悩まされていた「関係ない画面まで再描画される」問題は構造的に起きにくくなっていました。実際に一部の状態を Zustand のストアに移してみたところ、再レンダリングの範囲は狙った通りに絞れましたし、更新用の関数もストアの定義の中にまとめて書けるので、Context のときのように更新ロジックが呼び出し側に散らばることもなくなりました。

ここまでは順調でした。しかし移行を進めるうちに、私たちのアプリにとって本当に必要だったのは、状態管理ライブラリの機能ではなく、状態そのものの置き場所を見直すことだったのではないか、という疑問が湧いてきました。改めて洗い出してみると、グローバルに置いていた状態の多くは、実はサーバーから取得したデータのキャッシュだったり、URL のクエリパラメータで十分表現できる値だったり、あるいは特定の画面でしか使わない一時的な値だったりしました。それらを無理やり一つのグローバルストアに集約していたことが、そもそもの複雑さの原因だったのです。

そこで方針を転換し、サーバー由来のデータはデータ取得用のライブラリのキャッシュに任せ、画面の表示状態は URL や各コンポーネントのローカルな useState に戻し、複数の離れたコンポーネントで本当に共有する必要がある状態だけを最小限残す、という形に整理しました。結果として Zustand のストアはごく小さくなり、Context もほとんど使わなくなりました。useState、Context、Zustand のどれが正解かという問いの立て方自体が的外れで、正しく問うべきは「この状態はどこに置かれるべきか」だったのだと、今になって思います。

状態管理ライブラリを一つ導入すれば設計の悩みが消えるわけではありません。むしろ道具が増えるほど、どの状態をどこに置くかという判断の基準を自分たちで持っておく必要が出てきます。私たちのチームがたどり着いたのは、状態管理を「やめた」というより、状態管理という言葉でひとまとめにしていた問題を、サーバーの状態、URL の状態、画面ローカルの状態、そして本当にグローバルな状態という具合に分解し、それぞれに合った置き場所を選び直したという結論でした。ライブラリ選びの前に、まずその状態が誰のもので、どこで生まれてどこで消えるべきかを考えることが、遠回りに見えて一番の近道だったように思います。
