# Kubernetes をやめてコンテナサービスに移した話

## きっかけ

うちのプロダクトはこの数年、EKS の上で動いていた。マイクロサービスと呼べるほど数は多くないが、API サーバー、バッチ処理、Webhook の受け口など合わせて十数個のワークロードが載っていて、それぞれが Deployment と Service と Ingress のセットを持っていた。動いている分には特に不満はなかったのだが、運用側の負担が年々重くなっていくのが気になっていた。

きっかけになったのは、バージョンアップ対応に丸一日かかったある週末だった。コントロールプレーンのマイナーバージョンが EOL を迎え、ワーカーノードの AMI を追従させ、非推奨になった API を使っている Helm チャートを一つずつ洗い出して書き換える。作業自体は手順が確立していたので難しくはなかったが、この作業を四半期ごとに繰り返すコストが、チームの規模に見合っていないと感じた。メンバーは四人で、専任の SRE はいない。全員がアプリケーションのコードも書きながら、片手間でクラスタの面倒を見ている状態だった。

そこで、同じワークロードを ECS で動かした場合にどれくらい構成がシンプルになるかを検証し、結果として本番環境を ECS に移すことにした。

## 何が重かったのか

Kubernetes の運用負荷は、機能の豊富さの裏返しだと思っている。うちで実際に負担になっていたのは次のような点だった。

- コントロールプレーンとノードの両方のバージョン追従。EKS はコントロールプレーンのアップデートを代行してくれるが、ノード側の AMI 更新や互換性の確認は自分たちの仕事として残る
- クラスタ内部のネットワーキングの理解が前提になること。CNI プラグインの挙動、Service のロードバランシング、Ingress コントローラーの設定など、レイヤーが多く、障害時の切り分けに時間がかかる
- Helm チャートやマニフェストの肥大化。ワークロードが増えるたびに YAML が増え、共通化しようとして自作のテンプレートや Kustomize のオーバーレイが積み上がっていく
- RBAC やネットワークポリシーなど、セキュリティ面で正しく設定すべき項目が多く、専任がいないと後回しになりがちだったこと

どれも Kubernetes が悪いというより、汎用性の高い基盤を少人数で使いこなすためのコストだった。うちの場合、複数クラウドへの展開や、外部にクラスタを提供するような要件はなく、ただ AWS の上でコンテナを安定して動かしたいだけだった。そう考えると、Kubernetes が持つ抽象化の多くが使われないまま維持コストだけを払っている状態だったと言える。

## ECS に移すときの設計

移行にあたっては、タスク定義とサービスの単位を、それまでの Deployment 単位にほぼそのまま対応させた。サービスディスカバリは Cloud Map を使い、サービス間通信は今までと同じように内部の DNS 名で解決する形にした。Ingress の代わりには Application Load Balancer を使い、パスベースのルーティングはリスナールールで表現した。ここは Ingress コントローラーが担っていた機能の範囲が広くなかったこともあり、素直に置き換えられた。

デプロイのパイプラインも作り直した。それまでは CI から Helm でマニフェストを適用していたが、ECS では新しいタスク定義のリビジョンを登録し、サービスの更新でそれを参照させる流れになる。ローリングアップデートの挙動自体は Kubernetes のときとほぼ同じ体感で、最小ヘルス率と最大率を調整することでカナリア的な出し方もできた。

CPU とメモリの割り当ても見直した。Kubernetes では Pod の requests と limits を個別に設定していたが、ECS のタスク定義でも考え方は同じで、単位が少し違うだけで大きな学習コストはなかった。むしろ、ノードのキャパシティプランニングそのものが不要になった点が大きい。Fargate を使うことで、ワーカーノードのサイジングや空きリソースの管理から解放された。EC2 起動タイプに比べると単価は上がるが、その分の運用時間を差し引くと十分に見合う判断だった。

## オートスケールの違い

Kubernetes では Horizontal Pod Autoscaler と Cluster Autoscaler を組み合わせて、Pod のスケールとノードのスケールを二段階で管理していた。この二段構えが地味に複雑で、Pod は増やせるのにノードのキャパシティが足りずにスケジューリングされない、といった事象がたまに起きていた。

ECS に移してからは、Fargate を使っているのでノード側のスケーリングという概念自体がなくなった。サービスのオートスケーリングは Application Auto Scaling を使い、CPU 使用率やリクエストキュー長を指標にターゲット追跡のポリシーを設定するだけで済む。スケールアウトの反応速度は Kubernetes のときと大差ないが、監視すべきレイヤーが一段減ったことで、スケーリングに関するアラートの数自体が減った。障害対応のときに「Pod は増えているのにノードが足りているか」を確認する手順がなくなったのは、精神的な負担の軽減として大きかった。

## コストの変化

コストについては、単純な計算上は上がる場面と下がる場面が両方あった。Fargate はオンデマンドの EC2 に比べると単価は高めで、常時起動しているワークロードが多いと総額が増えることもある。うちの場合は、ノードの余剰キャパシティを見込んで多めに確保していた分がなくなったこと、そして夜間や休日にスケールインする設定を細かく入れられるようになったことで、月々のコンピュート費用はやや下がった。

ただし、コストを比較するときに見落としがちなのは人件費の側面だと思う。クラスタのアップグレード作業やトラブルシューティングに費やしていた時間を時給換算すると、インフラ費用の差額よりずっと大きな金額になっていた。数字に出にくい部分だが、移行の意思決定をするうえでは、こちらの方が実質的な決め手だった。

## 移行して失ったもの

良いことばかりではなく、失った柔軟性もある。Kubernetes のエコシステムにある、サービスメッシュやカスタムコントローラーのような拡張はもう使えない。将来的にマルチクラウド展開が必要になったり、ワークロードの種類が一気に増えたりした場合には、また Kubernetes に戻る選択肢も残しておくべきだと考えている。今回の判断は、あくまで今のチーム規模とワークロードの複雑さに対しての最適解であって、汎用的にどちらが優れているという話ではない。

## まとめ

Kubernetes をやめて ECS に移したことで、運用にかかる時間は明確に減った。バージョン追従の作業がなくなり、オートスケールの構成もシンプルになり、コストも人件費まで含めれば下がったと言える。一方で、失った拡張性や柔軟性もあり、これはチームの状況次第で評価が変わる部分だと思う。基盤の選択は流行や機能の豊富さで決めるものではなく、今のチームが安定して運用し続けられるかどうかで決めるべきだという、当たり前の結論に落ち着いた移行だった。
