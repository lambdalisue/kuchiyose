# 画像の配信を最適化した

サイトの表示速度を計測していたら、初回描画に一番時間がかかっているのが画像だと分かった。特にファーストビューに大きな画像を置いているページで LCP が悪化していて、Core Web Vitals のレポートでも常に赤信号が点いていた。原因を切り分けると、配信している画像フォーマットが古いこと、レスポンシブ対応をしておらずどの画面サイズでも同じ大きさの画像を送っていたこと、そして画面外の画像まで一括で読み込んでいたことの三つが重なっていた。これらを順番に見直した記録を残しておく。

## フォーマットの見直し

まず着手したのはフォーマットの変更だった。これまでは JPEG と PNG をそのまま配信していたが、WebP に切り替えるだけでファイルサイズがおおむね三割前後小さくなった。さらに対応ブラウザでは AVIF を優先的に配信するようにした。AVIF は WebP よりも圧縮率が高く、特に写真のような複雑な画像で差が出やすい。ただし AVIF はエンコードに時間がかかるため、ビルド時に事前生成しておく方針にした。リクエストのたびに変換していては配信のレイテンシが増えてしまうので、事前生成と CDN でのキャッシュを組み合わせるのが現実的だった。

ブラウザによって対応状況が異なるため、picture 要素でソースを複数指定し、AVIF、WebP、従来形式の順に候補を並べて、ブラウザが対応しているものを自動的に選ぶようにした。この仕組みにしておけば、将来さらに効率の良いフォーマットが登場したときも候補を足すだけで対応できる。

## サイズの出し分け

フォーマットを変えただけでは、スマートフォンの狭い画面にデスクトップ用の大きな画像をそのまま送ってしまう問題は解決しない。そこで srcset を使って、画面幅ごとに複数サイズの画像を用意し、ブラウザ側に適切なものを選ばせるようにした。実際の表示幅に合わせて sizes 属性も細かく指定し、ビューポートの割合に応じて画像がどれだけの幅で表示されるかをブラウザに伝えることで、無駄に大きな画像がダウンロードされることを防いだ。

サイズのバリエーションを増やしすぎると生成コストとストレージが膨らむため、実際のブレークポイントに合わせて数段階に絞り込んだ。多く用意すればするほどキャッシュヒット率が下がるという副作用もあるため、バランスを取る必要があった。

## 読み込みタイミングの制御

画面外にある画像については遅延読み込みを導入した。ブラウザ標準の loading 属性を使うだけで、追加のスクリプトなしに画面に入るタイミングで読み込みが始まるようになる。これにより初期表示時のリクエスト数が大幅に減り、体感速度が改善した。

ただし、ここで一つ失敗をした。ファーストビューに表示される画像にまで遅延読み込みを一律で適用してしまい、かえって LCP が悪化したのだ。遅延読み込みは画面外の画像に対して効果があるものであって、最初に表示される主要な画像には逆効果になる。むしろ優先度を上げて先読みさせるべき対象であり、この違いを見落としていたことに気づくまで少し時間がかかった。最終的には、ページごとに主要な画像を特定し、そこだけ遅延読み込みの対象から外して優先読み込みの指定を加える形に修正した。

## CDN の設定

配信経路についても手を入れた。オリジンサーバーから直接画像を返していた部分を CDN 経由にし、エッジ側でキャッシュされるようにした。あわせて、リクエストヘッダーに含まれる Accept の情報を見て、CDN 側で自動的に最適なフォーマットを選んで返す機能も有効にした。これにより、picture 要素で候補を並べる手間の一部を CDN 側に委譲でき、オリジン側の実装をシンプルに保てた。

キャッシュの有効期限も見直し、画像ファイル名にハッシュを含める運用にしたうえで、長期間キャッシュされるように設定した。ファイルの中身が変われば名前ごと変わるため、キャッシュの無効化を気にせず長い有効期限を設定できるようになった。

## 結果

一連の対応の後、LCP の数値は明確に改善した。特に効果が大きかったのはフォーマットの変更とファーストビュー画像の優先読み込みで、遅延読み込みや CDN の設定は転送量の削減には効いたものの、体感速度への寄与はそれほど大きくなかった。数値だけを見て一律に手を打つのではなく、どの画像がどの指標にどう影響しているかを分けて考える必要があると実感した作業だった。
