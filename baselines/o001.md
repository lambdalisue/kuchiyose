# iOS アプリの起動時間を、計測してから短縮した話

アプリのコールドスタートに 2 秒近くかかっているという社内フィードバックをきっかけに、起動時間の短縮に取り組んだ。感覚で「重そうな処理」を削るのではなく、まず何にどれだけ時間がかかっているのかを計測し、そこから手を入れる範囲を絞り込む進め方にした。結果として、体感できるほどの改善が得られたので、実施した内容を記録しておく。

## 計測から始める

最初に着手したのは Instruments によるプロファイリングだった。App Launch テンプレートを使うと、プロセスが起動してから最初の画面が描画されるまでの流れを、フェーズごとに分けて確認できる。具体的には、実行ファイルの読み込みからダイナミックリンク、`main` 関数の呼び出し、アプリのライフサイクル処理、そして初期画面の表示までが一本のタイムラインに並ぶ。

このタイムラインを見て意外だったのは、自分たちが書いたコードの実行時間よりも、アプリが起動して `main` に到達するまでの区間が思いのほか長いという点だった。ここで初めて、起動時間のボトルネックはアプリロジックではなくもっと手前にあるという見当がついた。

## dyld が起動時間を支配していた

`main` に到達するまでの区間を詳しく見ると、大部分をダイナミックリンカである dyld が占めていた。アプリが起動すると、dyld は実行ファイルが依存しているすべての動的フレームワークをディスクから読み込み、シンボルを解決し、初期化処理を呼び出す。これらはアプリ本体のコードが一行も実行される前に発生する処理であり、アプリ側の最適化ではどうにもならない部分だと思い込んでいたが、実際には依存フレームワークの数と構成次第で大きく変わることが分かった。

調べてみると、社内向けに切り出していた小さな共通ライブラリが、機能ごとに個別のフレームワークとして分割されていた。フレームワークが増えるほど dyld が読み込むべき動的ライブラリの数が増え、読み込みとリンクにかかる時間が線形に伸びていく。そこで、実行時に差し替える必要のないものについては、静的リンクに切り替えるか、関連の深いフレームワーク同士を一つにまとめる整理を行った。フレームワークの数を減らしただけで、dyld が占める区間は目に見えて短くなった。

## 遅延初期化で本体処理を後ろに倒す

dyld の区間を削った後は、アプリ起動時のコード側に目を向けた。起動直後に呼ばれるライフサイクルのメソッドの中身を洗い出すと、実際には起動直後に必要ない処理がいくつも紛れ込んでいた。

- 各種 SDK の初期化を、利用画面に到達する前にまとめて実行していた
- ログイン状態に関わらず、通知やトラッキング関連の設定を毎回行っていた
- 起動時に使わない機能のためのキャッシュ読み込みを事前に済ませていた

これらはいずれも、最初の画面が表示された後、あるいは実際にその機能が使われるタイミングまで遅延させても問題のない処理だった。遅延初期化の方針として、起動直後に必要なものだけを起動経路に残し、それ以外は最初の画面が表示されてから非同期に実行する、もしくは該当機能が呼ばれた瞬間に初めて初期化するという形に整理した。特に外部 SDK の初期化は、実際にその SDK の機能を使う直前まで遅らせられるケースが多く、起動経路から外す効果が大きかった。

## ストーリーボードの初期化コストを削る

もう一つ見落としていたのが、初期画面を構成しているストーリーボードのコストだった。Instruments のタイムラインでは、初期画面の表示区間の中に、ストーリーボードファイルの読み込みと、そこからビュー階層を組み立てる処理がまとまって現れていた。起動直後に表示する画面のストーリーボードには、実際には条件によって出し分けている複数の画面がまとめて定義されており、使わない画面の分まで解析コストを払っていた状態だった。

対応として、起動直後に必ず表示する画面だけを小さなストーリーボードに切り出し、それ以外の画面は遷移が発生した時点で個別に読み込む構成に変更した。あわせて、初期画面自体もビューの階層が深く、ストーリーボード上で多数の制約を組んでいたため、起動直後に見えている範囲だけをコードでシンプルに構築し直し、複雑な部分は画面表示後に段階的に組み立てる形にした。

## 前後の変化とまとめ

一連の変更の結果、Instruments で計測したコールドスタートの時間は、着手前と比べて体感できるレベルで短縮された。内訳で見ると、フレームワーク整理による dyld 区間の短縮と、ストーリーボードの読み込み範囲を絞ったことによる初期画面表示の短縮が特に大きく、遅延初期化による効果はそれよりは小さいものの、起動直後の処理が見通しやすくなったという副次的な利点があった。

今回の取り組みを通じて得た教訓は、起動時間の改善はまず計測でボトルネックの所在を特定することが前提になるという点だった。dyld の区間はアプリコードの外側にあるため見落とされがちだが、依存関係の構成次第で改善の余地が大きい。今後は新しい機能を追加するたびに、依存フレームワークの増加や起動経路への処理の混入がないかを、定期的に Instruments で確認する運用を続けていきたい。
