# フロントエンドのビルドを Vite に移した

フロントエンドのビルド基盤を webpack から Vite に移行した。長らく webpack で組んできた構成だったが、開発サーバーの起動待ちとホットリロードの遅さが日常的な不満として積み重なっていて、いよいよ手を入れることにした。

## 何が問題だったか

webpack を使った開発環境では、コードに変更を加えるたびにモジュールの依存グラフ全体を解決し、バンドルし直す処理が走っていた。プロジェクトの規模が大きくなるにつれてこのバンドル処理の時間は伸び続け、開発サーバーの起動だけで数十秒、ファイルを保存してからブラウザに変更が反映されるまでにも数秒単位の待ち時間が発生するようになっていた。

Hot Module Replacement、いわゆる HMR 自体は機能していたが、その前段にあるバンドル処理がボトルネックになっており、体感としては「速い開発体験」からは程遠い状態だった。特にコンポーネント数が増えてきたここ数ヶ月は、ちょっとした見た目の調整のたびに待たされる感覚が強く、開発のリズムを崩す要因になっていた。

## Vite が採用する仕組み

Vite の設計思想は webpack とは根本的に異なる。開発時にはアプリケーション全体を事前にバンドルせず、ブラウザがネイティブに対応している ESM、つまり ECMAScript Modules の仕組みをそのまま利用する。ブラウザが import 文を解釈してモジュールを要求するたびに、Vite がその場でファイルを変換して返す。これにより、開発サーバーの起動時にアプリケーション全体を解析する必要がなくなり、起動時間が劇的に短縮される。

依存関係の解決についても、Vite は esbuild を使って事前バンドルを行うが、これは npm 経由で入れているサードパーティのライブラリに限った話で、自分たちが書いたソースコードは対象にならない。アプリケーションコードはブラウザからの要求に応じて都度変換されるだけなので、ファイル数が増えても起動時間への影響はほとんど出ない。

HMR についても仕組みが違う。webpack の HMR はバンドル済みのモジュールグラフの中で差分を計算して適用するのに対し、Vite は変更されたモジュールとブラウザの間だけで更新をやり取りする。変更が起きたファイルとその依存先だけを再変換して置き換えるので、プロジェクト全体の規模に関係なく更新は一瞬で終わる。ファイルを保存してから画面に反映されるまでの時間が、体感でほぼゼロになったのは大きな変化だった。

## 移行の実際

移行にあたって最初に取り組んだのは、webpack の設定ファイルに書かれていた内容を Vite の設定に読み替える作業だった。webpack ではローダーやプラグインを介して行っていた処理の多くは、Vite ではプラグインという形で提供されているものの、思想が異なるため単純な一対一の置き換えにはならない部分もあった。特にエイリアスの解決や環境変数の扱い、静的アセットの読み込み方式については、それぞれの挙動を確認しながら書き直す必要があった。

次に手を入れたのは、コード中に残っていた CommonJS 形式の記述だった。Vite は開発時にネイティブ ESM を前提にしているため、require を使った動的な読み込みや、webpack 固有の機能に依存していた箇所は素直には動かない。幸い大半のコードはすでに import/export の形式で書かれていたが、一部のユーティリティやサードパーティ由来のラッパーコードに CommonJS の名残があり、そこを ESM に統一する形で書き換えた。

本番向けのビルドについては、Vite は内部で Rollup を使っており、これは webpack とは別のバンドラーになる。開発時の挙動と本番ビルドの挙動が別のツールに基づいているという点は最初やや不安があったが、実際に移行してみるとビルド成果物の差異は小さく、コード分割やアセットのハッシュ付与といった従来当たり前に行っていた最適化も標準の設定でカバーされていた。むしろ本番ビルドについても、依存解決の効率化によってビルド時間そのものが短縮される結果になった。

## 移行してみて変わったこと

もっとも体感が大きかったのは開発サーバーの起動時間だ。これまで数十秒かかっていた起動が、ほぼ瞬時に済むようになった。ファイルを保存してからブラウザに反映されるまでの時間も同様で、webpack の頃に感じていた「待つのが当たり前」という感覚がなくなった。

ビルド時間についても、開発時だけでなく本番向けのビルドでも短縮が見られた。CI 上でのビルドにかかる時間が縮まったことで、デプロイまでの一連の流れ全体が速くなったのも副次的な効果として大きい。

一方で、移行によって設定ファイルの前提が大きく変わったため、プラグインの選定や細かい挙動の違いを洗い出す作業には相応の時間がかかった。webpack の豊富なエコシステムに慣れていた分、同等の機能を持つ Vite 向けのプラグインを探したり、存在しない場合は自前で吸収したりする調整も必要だった。それでも、日々の開発体験が確実に良くなったことを考えると、移行にかけた手間は十分に見合うものだったと感じている。

ビルドツールの選択は一度決めるとなかなか変えにくい部分だが、開発体験への影響が大きいだけに、こうした形で立ち止まって見直す価値は十分にあると改めて感じた移行だった。
