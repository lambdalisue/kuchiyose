# フロントエンドのビルドを webpack から Vite に移行した記録

長く webpack で運用してきたフロントエンドのビルド環境を、思い切って Vite に切り替えました。きっかけは開発体験の悪化でした。開発サーバーの起動に数十秒かかり、ファイルを保存してからブラウザに反映されるまでの待ち時間も年々長くなっていました。プロジェクトの規模が大きくなるほど、この遅さがチーム全体の生産性に響いてくると感じ、移行を決断しました。

## webpack で感じていた課題

webpack はバンドラとして非常に柔軟で、これまでのプロジェクトを支えてきてくれた道具です。ただ、開発時の体験という点ではいくつかの不満が積み重なっていました。

- 開発サーバーの起動時に、アプリケーション全体を一度バンドルしてから配信するため、規模が大きくなるほど起動が遅くなる
- ホットモジュールリプレースメント（HMR）は導入していたものの、変更のたびに再バンドルの範囲が広がり、反映までのタイムラグが目立つようになっていた
- ビルド時間そのものも徐々に伸びており、CI 上のビルドが開発の足を引く場面が増えていた

これらはいずれも致命的な問題ではありませんでしたが、日々の小さな「待ち時間」が積算されると、無視できない体感の重さになっていました。

## Vite が解決してくれたこと

Vite の最大の特徴は、開発時にはバンドルを行わず、ブラウザが標準でサポートする ESM（ES Modules）をそのまま利用してモジュールを配信する点です。開発サーバーは必要になったモジュールだけをその場で変換して返すため、アプリケーションの規模に関係なく起動がほぼ一瞬で終わります。これまで数十秒かかっていた起動が、数百ミリ秒程度まで短縮されました。

HMR についても仕組みが根本的に異なります。webpack がモジュール依存グラフ全体を意識しながら差分を反映するのに対し、Vite は変更のあったモジュールだけをブラウザに直接送り直す形で更新を行います。そのため、ファイルを保存してから画面に反映されるまでの時間が、規模が大きくなってもほとんど劣化しません。実際に触ってみると、保存した瞬間に反映されている感覚があり、開発時の集中が途切れにくくなりました。

一方で、本番向けのビルドについては Vite は内部で Rollup を使ってバンドルを行います。開発時と本番時で仕組みを切り替えるという設計は、最初は少し意外に感じましたが、開発時は変換の速さを、本番時は配信効率の良い最適化されたバンドルを、それぞれ適した仕組みで実現しているのだと理解すると納得感がありました。

## 移行作業の実際

移行そのものは、想定していたよりも大きな作業にはなりませんでした。エントリーポイントとなる HTML ファイルの位置づけを見直し、webpack の設定ファイルに書かれていたエイリアスや環境変数の定義を、Vite の設定ファイルに書き直していく作業が中心でした。ローダーで処理していた画像や CSS の取り込みも、Vite では標準で対応している範囲が広く、個別に追加していたプラグインの多くを削除できました。

つまずいたのは、webpack 特有の書き方に依存していたコードでした。動的な条件分岐でモジュールを読み込む処理や、ビルド時に特定の環境変数を埋め込む処理など、webpack の内部挙動を前提にしていた箇所は、ESM ベースの解釈に合わせて書き直す必要がありました。ここは事前の想定より手間がかかりましたが、件数自体は限られていたため、数日のうちに片づけることができました。

## 移行後のビルド時間

本番ビルドの時間についても、明確な改善がありました。webpack のときは依存関係の解析とバンドルを直列的に行っていた部分が、Vite では並行して処理される場面が多く、全体のビルド時間が大きく短縮されました。CI 上での実行時間も短くなり、プルリクエストごとの待ち時間が減ったことは、チームからも好意的に受け止められています。

## まとめ

今回の移行を通じて実感したのは、Vite の強みが単なる速度の向上だけではないという点です。ESM を前提にした設計そのものが、開発時の体験を大きく変えていました。ビルドの仕組みを見直すことは腰の重い作業に見えがちですが、日々の開発体験に直結する部分だけに、投資する価値は十分にあったと感じています。今後も webpack との差分で気づいた点があれば、随時共有していきたいと思います。
