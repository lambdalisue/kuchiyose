クロスプラットフォームをやめました。Flutter で書いていたアプリを、iOS 版と Android 版それぞれのネイティブ実装に切り替えたという話です。

## クロスプラットフォームをやめました

個人で開発しているアプリを、Flutter からネイティブ実装に切り替えました。iOS 版は Swift、Android 版は Kotlin で書き直し、共通のロジックだった部分もそれぞれの言語で二重に持つことにしました。行数はほぼ倍になりましたが、後悔はしていません。むしろもっと早くやればよかったと思っています。

### なぜ Flutter を選んでいたか

最初にクロスプラットフォームを選んだ理由は単純で、一人で開発しているアプリを二つのプラットフォーム向けに別々に書く余裕がなかったからです。Flutter であれば UI のコードを一本化でき、ロジックもそのまま共有できます。実際、最初のリリースまでの速度はネイティブで別々に書くよりもずっと速く、狙いどおりの効果はありました。

問題が表面化したのは、リリースしてからしばらく経ち、プラットフォーム固有の機能を足そうとしたあたりからです。通知の細かい挙動、共有シートの見た目、ウィジェットのような OS 標準の仕組みに触れるたびに、Flutter のプラグインに頼るか、自分でネイティブコードを書いて橋渡しするかの二択を迫られるようになりました。

### プラグインという名の賭け

クロスプラットフォームの実態は、共通化された部分と、プラットフォームごとのプラグインの寄せ集めです。カメラやファイル選択のような枯れた機能は問題になりませんでしたが、少し尖った機能を使おうとするとすぐに壁に当たりました。あるプラグインは iOS 側の実装が止まっていて最新の OS バージョンで動かず、別のプラグインは Android 側にだけ重大な不具合があり、修正が半年以上マージされないまま放置されていました。

自分でネイティブコードを書いて足りない部分を埋めることもできますが、それをやり始めると、Flutter の橋渡し層を経由するコードと、素のネイティブコードが同じアプリの中に混在することになります。デバッグの手間は単純に足し算では済まず、掛け算で増えていきました。橋渡し層のどちら側で問題が起きているのかを切り分けるだけで、素のネイティブアプリなら要らなかったはずの時間を使っていました。

### 体験の差はにじみ出る

もう一つ効いたのが、体験の細かな差です。Flutter は自前の描画エンジンで UI を描くため、見た目を両プラットフォームで揃えやすい一方、OS 標準のスクロールの挙動や、キーボードが出てきたときのアニメーション、システムのフォント設定への追従など、細部で「らしさ」が抜け落ちる場面がありました。ユーザーから見れば、それは些細な違和感の積み重ねに過ぎませんが、積み重なった違和感は確実にアプリへの信頼を削っていきます。

一つ一つは直せる問題です。実際、多くは Flutter 側でも力技で寄せることができます。しかし、直すたびにプラットフォームごとの分岐が増え、共通コードのはずの部分がプラットフォーム固有の条件分岐だらけになっていきました。共有できることを前提に設計していたコードベースが、共有できない現実に少しずつ浸食されていく感覚です。

### 分けてわかったこと

ネイティブに分けてみて意外だったのは、当初恐れていたほど二重管理がつらくなかったことです。ロジックの多くはそもそもプラットフォームごとの UI ガイドラインに合わせて書き分ける必要があり、共通化していた部分の恩恵は思っていたより小さいものでした。むしろ、それぞれの OS が提供する標準のコンポーネントをそのまま使えるようになったことで、プラグインの生死を気にする必要がなくなり、体験の細部を作り込む時間に回せるようになりました。

クロスプラットフォームが向いているのは、対応プラットフォームを増やすこと自体が目的で、細部の作り込みよりも展開速度を優先できる場面だと思います。今回のアプリは規模が小さく、プラットフォームごとの体験の質がそのまま評価に直結する種類のものだったので、ネイティブに寄せたことは自分たちの状況に合った選択でした。
