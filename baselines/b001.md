# GraphQL をやめて REST に戻した理由

半年ほど GraphQL を本番運用したのち、私たちのチームは主要な API を REST に戻すという決断をした。導入したときは「オーバーフェッチの解消」「フロントエンドが必要なデータだけを取得できる柔軟性」といった謳い文句に納得していたし、実際に最初の数か月はその恩恵を感じてもいた。それでもなお撤退を選んだのは、運用を重ねるうちに見えてきた負債が、当初期待していた利点を上回ったからだ。

## 導入時に解決したかった問題

もともと REST で運用していた頃、私たちが抱えていた不満はいわゆるオーバーフェッチだった。一覧画面のために一件分のエンドポイントを叩くと、画面には表示しない項目まで含んだ巨大なレスポンスが返ってくる。逆に画面によっては情報が足りず、関連リソースを取得するために追加のリクエストを何度も飛ばす必要があった。エンドポイントごとにレスポンス形状が微妙に異なり、フロントエンドはその都度専用の変換処理を書いていた。

GraphQL はこの問題に対する明快な答えに見えた。クライアントが欲しいフィールドだけをクエリとして指定すれば、サーバーはその形に整形して返す。スキーマという単一の契約がクライアントとサーバーの間に存在し、型が合っているかどうかはクエリの時点で検証できる。ドキュメントとスキーマが乖離するという、REST でよく起きていた悩みからも解放されるはずだった。

## 運用の中で表面化した問題

### N+1 とその対処の複雑さ

GraphQL のリゾルバは、ネストしたフィールドを解決するたびに個別のデータ取得処理を呼び出す構造になりやすい。たとえば投稿一覧とその著者情報を同時に取得するクエリでは、投稿の件数だけ著者取得のクエリが発行されてしまう、いわゆる N+1 問題が起きる。これ自体は GraphQL 特有の新しい問題というより、リゾルバ単位で処理を書くスタイルが引き起こす副作用に近い。

対策として DataLoader を導入し、同一リクエスト内で発生した取得要求をバッチ化してまとめて解決する仕組みを入れた。効果はあったものの、リゾルバを追加するたびに対応する DataLoader を用意し、キャッシュキーの設計やリクエストスコープでのライフサイクル管理を考える必要があり、実装コストは決して小さくなかった。新しく加わったメンバーがリゾルバを書くたびに N+1 を作り込み、レビューで指摘して DataLoader 化するというやり取りが繰り返された。結果として、パフォーマンス上の落とし穴を踏まないための知識が、チーム全体で共有すべき前提知識として積み上がっていった。

### スキーマという単一契約の重さ

スキーマがクライアントとサーバーの契約になるという設計は、当初は安心材料だった。しかし複数のフロントエンドチームが同じスキーマを共有するようになると、あるチームの都合でフィールドを追加・変更するたびに、他のチームへの影響を確認する調整コストが発生した。REST であればエンドポイントを分ければ済んでいた変更が、単一のグラフの中では波及範囲を見積もりにくい。非推奨化のための `deprecated` の運用や、破壊的変更を避けるための段階的な移行手順など、スキーマ管理そのものを専任で見る役割が実質的に必要になっていた。

### キャッシュとインフラ側の扱いにくさ

REST であれば、URL とメソッドの組み合わせに対して CDN やリバースプロキシで素直にキャッシュを効かせられる。GraphQL はほとんどのリクエストが同一のエンドポイントに POST で届くため、この単純なキャッシュ戦略が使えない。永続化クエリの仕組みを導入して GET 化するなど回避策はあるが、それ自体が追加の運用対象になる。監視の面でも、エンドポイント単位でエラー率やレイテンシを見ていた従来のダッシュボードがそのままでは機能せず、クエリの内容ごとに分類し直す仕組みを別途用意する必要があった。

### オーバーフェッチは別の形で再発した

皮肉なことに、当初解消したかったはずのオーバーフェッチに近い問題も別の形で戻ってきた。クライアント側が必要以上に深くネストしたクエリを書き、結果としてサーバー側の負荷が想定を超えるケースが増えた。クエリの複雑さを制限する仕組みを別途組み込む必要があり、これもまた新しい運用項目になった。柔軟にフィールドを選べることの裏側で、何をどれだけ取得してよいかという制約を運用側が別途設計し直す羽目になったわけだ。

## REST に戻す決断

これらの負債を棚卸しした結果、私たちのプロダクトの規模とチーム構成では、GraphQL が提供する柔軟性よりも、REST のエンドポイント単位でのシンプルさのほうが運用コストに見合うという結論に至った。画面ごとに必要なデータをまとめて返す専用エンドポイントを設計し直し、共通で使う関連データの取得はサーバー側でまとめて行うことで、N+1 に相当する問題自体を発生しない設計にした。DataLoader のようなリクエストスコープのバッチ処理を意識する必要もなくなった。

エンドポイントが増えることで多少の重複は生まれたが、それぞれが独立してキャッシュ可能で、監視対象としても扱いやすく、変更の影響範囲も見積もりやすい。スキーマという単一の契約を維持するコストから解放されたことで、チームごとに必要な変更を素早く出せるようになった点も大きかった。

## 振り返って

GraphQL が解決しようとした問題――オーバーフェッチや、エンドポイントの乱立――は実在した課題であり、その解決アプローチ自体が間違っていたとは思わない。ただし、その柔軟性を維持するための運用コストは、スキーマ管理、N+1 対策、キャッシュ戦略の再設計といった形で分散して降りかかってくる。私たちのチーム規模とプロダクトの性質では、そのコストを払い続けるだけの見返りがなかった、というのが今回の結論だ。技術選定は流行や理想論ではなく、実際に運用し続けられるかどうかで判断すべきだと、あらためて感じさせられた移行だった。
