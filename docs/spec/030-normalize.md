# 入力を正規形にする

集めた文章を、[文書の形](020-document.md)が定める形に落とす手順を決める。

[評価](200-extract.md)と[検め](300-revise.md)は、測る前に必ずここを通る。
<strong>片方だけ違う揃え方をすれば、比べたものに意味が無い。</strong>

## 何のためにやるか

<strong>同じ内容が、書式の違いだけで別の値にならないようにする。</strong>

素材は取り込み元がばらばらである。Markdown の方言、HTML。同じ「補足」が、ある場所では
引用の記法で、別の場所では専用の記法で書かれる。

揃えなければ、<strong>測っているのは書き手ではなく取り込み元である。</strong>

<strong>プレーンテキストとチャットの書き出しは、いま扱わない。</strong> どちらも
[対応表](#対応表は取り込み元ごとに持つ)に無いので[断られる](#通らないものは断る)。

扱わないのは、記法が無いからではなく <strong>node の境界が本文から決まらない</strong>からである。
チャットは発言が単位になるが、書き出しの形式ごとに発言者・時刻・引用の付き方が違い、
どこまでが書き手の文かを決定的に切れない。<strong>切り方を間違えると、
[node を跨がない](020-document.md#地の文は-1-本の文字列ではない)はずの bigram と文が
発言をまたいで繋がる。</strong> 足すなら、発言の境界とメタデータの落とし方を対応表と一緒に
決めてから足す。

## 守るべき 4 つ

| | 守ること | 破るとどうなるか |
| --- | --- | --- |
| 1 | [決定的である](#決定的である) | 下流のすべてが揺れる |
| 2 | [意味で認識する](#意味で認識する) | 測っているのが記法になる |
| 3 | [表記を潰さない](#表記を潰さない) | 測る価値の高い層を捨てる |
| 4 | [通らないものは断る](#通らないものは断る) | 値の狂った文書が正常な顔で混ざる |

## 決定的である

<strong>同じ入力からは、いつでも同じ正規形が出る。</strong>

[数える側に LLM を置かない](010-strategy.md#数える側に-llm-を置かない)の言い換えでは
ない。<strong>正規化にも同じ制約が独立にかかる。</strong> ここが揺れれば、指標がどれだけ決定的でも
値は揺れる。

推測を混ぜない。「これはたぶん補足だろう」と判断しない。<strong>書き手が記法で示したものだけ
を認識する。</strong>

## 意味で認識する

[文書の形](020-document.md#文書は-node-でできている)は node を意味で定めている。記法は
取り込み元の事情である。<strong>だから記法から意味への対応表は、ここが持つ。</strong>

### 黙って壊れる場所がある

<strong>ここがいちばん危ない。</strong> GitHub の Alert 記法は、引用の記法の上に建っている。

```markdown
> [!NOTE]
> ここは補足である。
```

<strong>素朴に CommonMark として解釈すると、これは引用になる。</strong> そして——

| | 何が起きるか |
| --- | --- |
| 引用の密度 | <strong>実際より高く出る</strong> |
| 補足の密度 | <strong>0 が並ぶ</strong> |

<strong>エラーにならない。</strong> 値が出て、判定が回り、結果だけが違う。

<strong>Alert 記法を持つ取り込み元では、引用より先に Alert を認識する。</strong> 同じことが脚注、
折りたたみ（`<details>`）、独自の補足記法にも起きる。

### 対応表は取り込み元ごとに持つ

<strong>扱う取り込み元は 4 つである。</strong> 増やすときはここに行を足す。

| | 何の構文か |
| --- | --- |
| `github-markdown` | GitHub Flavored Markdown + Alert 記法 |
| `directive-markdown` | CommonMark + directive 記法（`:::note`） |
| `html` | HTML |
| `plain-markdown` | 素の CommonMark |

#### 標準の名前を名乗らない

<strong>「CommonMark に対応している」とは書かない。</strong> 名乗れば、その標準の構文をすべて認識
する義務が生まれる。<strong>1 つでも取りこぼせば、断られずに地の文へ流れる</strong>——下線
（Setext）で見出しを書いた文書は、見出しが 0 になったうえでその文字列が段落として数え
られる。[取り込み元を間違えたとき](#取り込み元を間違えると0-が並ぶ)と同じ壊れ方が、
正しく申告しても起きる。

<strong>だから 4 つはどれも独自の取り込み元である。</strong> 認識する構文を[下の表](#node-への対応表)が
列挙し、<strong>表に無い構文は[断る](#通らないものは断る)</strong>。

| | 何から取ったか |
| --- | --- |
| `github-markdown` | [GFM 0.29-gfm](https://github.github.com/gfm/) の部分集合 + Alert 記法 |
| `directive-markdown` | [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) の部分集合 + directive 記法（`:::note`） |
| `html` | HTML の部分集合 |
| `plain-markdown` | CommonMark 0.31.2 の部分集合 |

<strong>元にした標準の版も[指紋](200-extract.md#何で測ったかを指紋にする)に出す</strong>——同じ記法の
解釈が版で変わることがある。<strong>HTML には版が無い</strong>ので、参照した日付のスナップショットを
出す。

<strong>Markdown の中の生の HTML は、`<details>` を除いて断る。</strong> CommonMark は HTML block と
raw HTML を構文として通すが、<strong>ここでは通さない</strong>。通せば `plain-markdown` でも
`<aside>` や `<table>` で補足や表が書けることになり、
<strong>[書ける・書けないの升目](#対応表は取り込み元ごとに持つ)が壊れる</strong>——同じ入力が
「node になる」と「測れない」の両方になる。

<strong>`<details>` だけを `github-markdown` の例外にするのは、それしか書きようが無いからで
ある。</strong> GFM に折りたたみの記法は無く、GitHub 自身が `<details>` を案内している。
<strong>例外を認めなければ、この升目は「書けない」になる</strong>——それは事実に反する。

<strong>例外はこの 1 つだけである。</strong> ほかのタグは、`github-markdown` でも断る。

<strong>HTML で書きたいなら `html` として入れればよい。</strong> 混ぜないことが升目を守る。

#### node への対応表

[文書の形](020-document.md#文書は-node-でできている)が挙げた node のすべてに、取り込み元
ごとの記法を与える。<strong>ここに無い記法は対応表に無い記法である。</strong>

| node | Markdown 3 種 | `html` |
| --- | --- | --- |
| 段落 | 空行で区切られた行 | `<p>` |
| 見出し | `#`、Setext の下線 | `<h1>`〜`<h6>` |
| 箇条書き | `-` `*` `+` | `<ul>` |
| 番号リスト | 数字（1〜9 桁）+ `.` または `)` | `<ol>` |
| 項目 | リストの直接の子 | `<li>` |
| 引用 | `>`（Alert・directive に当たらないもの） | `<blockquote>` |
| 表 | GFM の表（`plain-markdown` では認識しない） | <strong>`<table>` 1 つが表 1 つ</strong> |
| セル | 表の升目 | `<td>` `<th>` |
| コードブロック | ``` `` ``` と `~~~` の囲み（記号は 3 つ以上）、4 字下げ | <strong>`<pre>`</strong> |
| インラインコード | `` ` `` の囲み（記号はいくつでも） | <strong>`<pre>` の外の `<code>`</strong> |
| 区切り線 | `---` `***` `___` | `<hr>` |
| 画像 | `![]()`、参照形式 `![][ref]` | `<img>` |
| 強調 | `*` `_` `**` `__` | `<em>` `<strong>` `<b>` `<i>` |
| リンク | `[]()`、参照形式 `[][ref]`、自動リンク | `<a>`（脚注に当たらないもの） |

<strong>`<table>` の中の `<thead>` `<tbody>` `<tfoot>` `<tr>` は node にしない。</strong> 透かして、
`<table>` 1 つが表 node 1 つ、`<td>` `<th>` 1 つがセル node 1 つになる。<strong>行や区分まで表に
数えると、ふつうの表 1 つで表の密度が何倍にもなる。</strong>

<strong>コードブロックは `<pre>` である。</strong>`<pre><code>` は `<pre>` 1 つに畳み、`<code>` を
別の node にしない。<strong>`<pre>` の外の `<code>` だけがインラインコードである</strong>——段落の中の
`<code>` までコードブロックにすると、<strong>インラインコードが永久に 0 になり、コードブロックの
密度は地の文に混ざらない記号のぶんだけ跳ね上がる。</strong>

補足・警告・脚注・折りたたみは記法が族にまとまっているので、次の表が別に決める。

<strong>この 2 つの表に無い構文は、対応表に無い記法である。</strong> 元にした標準の側にあっても
同じ——[断る](#通らないものは断る)。<strong>「知らないから地の文にしておく」を作らない</strong>のが、
この表を全部書く理由である。

<strong>だから表に無いものは、ここで名指ししておく。</strong> GFM の task list と取り消し線、
CommonMark の改行の書き分け、エスケープと文字参照——<strong>どれも認識しない。使われていれば
断る。</strong> 足すときは、[node の表](020-document.md#文書は-node-でできている)に落ちる先が
あるかを先に決める。

<strong>参照定義行（`[ref]: https://…`）は認識するが、node にしない。</strong> 参照形式のリンクと
画像を表に載せた以上、その行を断れば <strong>参照形式が成立しない。</strong> 読んで参照を解き、
<strong>行そのものは地の文にも構造にも残さない</strong>——書き手が本文として書いたものではない。

<strong>[子を持つ node](020-document.md#文書は-node-でできている)の中身は、もう一度 block として
解釈する。</strong> 引用・補足・警告・折りたたみ・脚注・セルの中の段落、リスト、表、コード
ブロックは、そのまま node になる。<strong>中身を 1 本の文字列に畳まない</strong>——畳めば内側の構造が
まるごと消え、<strong>コードブロックの中身が地の文に混ざる。</strong>

<strong>補足と警告は別の node である。</strong> 記法が 1 つの族にまとまっているので、<strong>どれがどちらに
落ちるかを決めておかないと、実装ごとに変わる。</strong>

| 記法 | どの node か |
| --- | --- |
| `[!NOTE]` `[!TIP]` `:::note` `:::tip` <strong>`:::message`</strong> `<aside>` | <strong>補足</strong> |
| `[!WARNING]` `[!CAUTION]` `[!IMPORTANT]` `:::warning` `:::caution` <strong>`:::message alert`</strong> | <strong>警告</strong> |
| `[^1]` と定義行、`:::footnote`、`<sup><a>` | <strong>脚注</strong> |
| `<details>`、`:::details` | <strong>折りたたみ</strong> |
| GFM の表、`<table>` | <strong>表</strong> |

<strong>`IMPORTANT` を警告に入れるのは、書き手が「読み飛ばすな」と示している側だからである。</strong>
補足は本筋から外れることを示す記法で、向きが逆になる。

<strong>名前だけでは決まらない記法がある。</strong> Zenn の `:::message` は補足だが、
`:::message alert` は警告である。<strong>修飾を落とすと警告が補足に化ける。</strong>

<strong>書けない記法は「測れない」になる。</strong>

| 取り込み元 | 補足 | 警告 | 脚注 | 折りたたみ | 表 |
| --- | --- | --- | --- | --- | --- |
| `github-markdown` | 書ける | 書ける | 書ける | 書ける | 書ける |
| `directive-markdown` | 書ける | 書ける | 書ける | 書ける | 書ける |
| `html` | 書ける | <strong>書けない</strong> | 書ける | 書ける | 書ける |
| `plain-markdown` | <strong>書けない</strong> | <strong>書けない</strong> | <strong>書けない</strong> | <strong>書けない</strong> | <strong>書けない</strong> |

<strong>0 と「測れない」を区別する。</strong> 0 を並べれば、その書き手は補足を使わない人だと判定
される。<strong>「書けない」の升目がそのまま「測れない」を返す場所である。</strong>

### 取り込み元を間違えると、0 が並ぶ

<strong>升目の守りは、取り込み元が正しく申告されて初めて効く。</strong>

[取り込み元は内容から判定しない](../design/200-command.md#add)——人が指定する。<strong>だから
間違えられる。</strong> そして間違えたとき、書けるはずの升目が黙って 0 を返す。

実測した。Zenn の記事 12 本を `github-markdown` として読むと——

| | `directive-markdown` | `github-markdown` |
| --- | --- | --- |
| 補足 | <strong>18 箇所</strong> | <strong>0</strong> |
| 警告 | <strong>2 箇所</strong> | <strong>0</strong> |
| 段落（1 本の例） | 52 | 63 |

<strong>書き手は 20 回使っている。</strong> それが「使わない人」として出る。段落の数まで変わる——
補足の中身が段落として数えられるからである。

<strong>だから断る。</strong>[対応表に無い記法](#通らないものは断る)を地の文に流さない。
`:::` を知らない取り込み元で `:::message` を見たら、それは対応表に無い記法である。

> 実装で確かめた。`github-markdown` と申告すると <strong>12 本のうち 6 本が断られる</strong>——
> `:::message` を使っている 6 本である。<strong>黙って 0 を返さない。</strong>

## 表記を潰さない

<strong>正規化と称して、字種を揃えてはいけない。</strong>

全角と半角、`〜` と `～`、`…` と `……`。これらは
[書き手の選択であり、測る価値が高い](020-document.md#表記は残る優先して採る理由がある)。

<strong>潰す側と潰さない側を、はっきり分ける。</strong>

| | 例 |
| --- | --- |
| <strong>潰す</strong>（記法） | 箇条書きの `-` と `*`、見出しの `#` と下線、強調の `**` と `__` |
| <strong>潰さない</strong>（表記） | 字種、字幅、空白の入れ方、改行の位置 |

多くの整形ツールは、頼まなくても表記まで揃える。<strong>既製のフォーマッタを通す前に、何を
書き換えるかを確かめる。</strong> 通したあとでは、潰れたことに気付けない。

## 通らないものは断る

<strong>正規形に落ちない入力がある。</strong> 落ちないまま無理に通さない。

| | どうするか |
| --- | --- |
| 記法が壊れていて解釈できない | <strong>断る</strong> |
| 対応表に無い記法が使われている | <strong>断る。</strong> 対応表を足してから通す |
| 日本語以外が主 | <strong>断る</strong>（[日本語だけ](010-strategy.md#日本語だけ)） |

<strong>「日本語以外が主」に線を引く。</strong> 判定は決定的でなければならないので、言語判定の道具に
頼らない。

> [地の文](020-document.md#地の文)の文字のうち、[日本語の文字](020-document.md#日本語の文字)
> が <strong>3 割に満たなければ</strong>断る。

<strong>約物と空白を分母から外す。</strong> コードの多い技術記事は英数字と記号が増えるが、それは
題材であって言語ではない——[地の文はコードもコードだけのセルも含まない](020-document.md#地の文)
ので、ここで数えるのは散文だけである。

<strong>だから分母は「地の文に残ったもの」である。</strong> 落としたセルはここにも入らない。
記号だけの比較表が大半を占める文書は、<strong>表のぶんが分母から消えたうえで判定される</strong>——
残った散文が日本語なら通る。<strong>それでよい</strong>——断る基準は「日本語で書かれていない文書」で
あって「表が多い文書」ではない。

<strong>3 割は暫定値である</strong>（[指標](100-metrics.md#除外の既定)）。<strong>地の文の作りを変えたら、
この値は導き直しになる</strong>——分母が変わるので、同じ 3 割が同じものを断らない。

黙って一部を落として通せば、<strong>落ちた分だけ値が狂った文書</strong>が、正常な文書と同じ顔で
コーパスに入る。

## 正規形が原本である

[元のファイルは手元に残らない](200-extract.md#3-つに分けて持つ)前提で設計する。

したがって、<strong>正規形から測れないものは、永久に測れない。</strong> 迷ったら残す側に倒す。

<strong>往復は目的ではない。</strong> 正規形から元の書式を復元できる必要は無い。復元性を求めれば
記法の情報を抱えることになり、[潰すと決めたもの](#表記を潰さない)が残ってしまう。

## 変換したことを記録する

<strong>何をどう変換したかを、値と一緒に残す。</strong>

| 残すもの | 形 |
| --- | --- |
| 取り込み元の種類 | <strong>単位ごとに 1 つ。</strong> コーパス全体の集合ではない |
| 名乗った構文の版 | `CommonMark 0.31.2` のような固定した版 |
| 使った変換の実装と版 | 実装の名前と版 |
| <strong>適用した対応表</strong> | <strong>対応表の版と、正規化した中身のハッシュ</strong> |

[指紋](200-extract.md#何で測ったかを指紋にする)に含める。<strong>変換規則が変われば、過去の値
と比べられない。</strong> 記録が無ければ、比べられないことにも気付けない。

<strong>対応表は版だけでは足りない。</strong> 升目の中身を変えても版を上げ忘れれば、指紋が同じまま
別の木が出る。<strong>中身のハッシュを一緒に持つ</strong>——手で上げる版と、機械が出すハッシュの
両方が変わらないときだけ、過去の値と比べてよい。

<strong>取り込み元を単位ごとに残すのは、[升目](#対応表は取り込み元ごとに持つ)が単位ごとに
効くからである。</strong> コーパス全体の集合しか残さないと、混ぜて入れたときに <strong>どの単位に
どの升目が当たったか</strong>が復元できず、「測れない」を返した理由が言えなくなる。

### 変換規則を変えると、戻れない

<strong>指標が増えたときの測り直しとは、性質が違う。</strong> 指標は本文から何度でも計算し直せるが、
<strong>本文そのものは元のファイルが無いので作り直せない。</strong>

したがって変換規則を変えると、コーパスは <strong>古い規則で落とした本文</strong>と <strong>新しい規則で
落とした本文</strong>に割れ、二度と揃わない。

| 変わったもの | 過去の本文 |
| --- | --- |
| 指標の集合 | 測り直せる |
| <strong>変換規則</strong> | <strong>作り直せない。割れたまま残る</strong> |

<strong>だから変換規則を変えるときは、割れることを承知で決める。</strong> 取りうる道は 2 つしかない。

- 素材を集め直して、新しい規則で入れ直す
- 古い規則の本文を別のコーパスとして分け、混ぜて評価しない

<strong>黙って変えない。</strong> 混ざれば、[場面ごとに閉じる](010-strategy.md#場面ごとに閉じる)を
守っていても、規則の差が人の差として出る。
