# 入力を正規形にする

この文書は、集めた文章を[文書の形](020-document.md)が定める形に落とす手順を決める。
この手順を正規化と呼び、落とした結果を正規形と呼ぶ。

[評価](200-extract.md)（本人の[素材](../glossary.md#素材)から目盛りを作る段）と
[検め](300-revise.md)（草稿を測って指摘を出す段）は、測る前に必ずここを通る。片方だけ
違う揃え方をすると、比べた結果に意味が無くなるからである。

## 何のためにやるか

正規化の目的は、同じ内容が書式の違いだけで別の値にならないようにすることである。

素材の[取り込み元](../glossary.md#取り込み元)（文書の書式）はばらばらである。Markdown にも
方言があり、HTML もある。同じ「補足」が、ある場所では引用の記法で、別の場所では専用の
記法で書かれる。揃えなければ、測っているのは書き手ではなく取り込み元になってしまう。

プレーンテキストとチャットの書き出しは、いまは扱わない。どちらも
[対応表](#対応表は取り込み元ごとに持つ)に無いので、入れても[断られる](#通らないものは断る)。

扱わない理由は、記法が無いことではない。本文から node（段落や見出しといった文書の部品。
[文書の形](020-document.md#文書は-node-でできている)が定める）の境界が決まらないことである。
チャットでは発言が単位になるが、発言者・時刻・引用の付き方は書き出しの形式ごとに違う。
そのため、どこまでが書き手の文なのかを決定的に切り分けられない。切り方を間違えると、
[node を跨がない](020-document.md#地の文は-1-本の文字列ではない)はずの bigram や文が、
発言をまたいで繋がってしまう。チャットを足すなら、発言の境界とメタデータの落とし方を、
対応表と一緒に決めてから足す。

## 守ること

正規化は次のことを守る。

| | 守ること | 破るとどうなるか |
| --- | --- | --- |
| 1 | [決定的である](#決定的である) | 下流のすべてが揺れる |
| 2 | [意味で認識する](#意味で認識する) | 測っているのが記法になる |
| 3 | [表記を潰さない](#表記を潰さない) | 測る価値の高い層を捨てる |
| 4 | [通らないものは断る](#通らないものは断る) | 値の狂った文書が正常な顔で混ざる |

## 決定的である

同じ入力からは、いつでも同じ正規形が出るようにする。

これは[数える側に LLM を置かない](010-strategy.md#数える側に-llm-を置かない)という決定の
言い換えではない。正規化にも、同じ制約が別に独立してかかる。正規化の結果が揺れれば、
指標の計算がどれだけ決定的でも、値は揺れる。

そのため、正規化に推測を混ぜない。「これはたぶん補足だろう」とは判断しない。書き手が
記法で示したものだけを認識する。

## 意味で認識する

[文書の形](020-document.md#文書は-node-でできている)は、node を記法ではなく意味で定めて
いる。どの記法で書かれるかは取り込み元の事情である。そのため、記法から意味（node）への
対応表は、この文書が持つ。

### 黙って壊れる場所がある

正規化でいちばん危ないのは、エラーを出さずに誤った node に落ちる場合である。代表例が
GitHub の Alert 記法で、これは引用の記法の上に作られている。

```markdown
> [!NOTE]
> ここは補足である。
```

これを素朴に CommonMark として解釈すると、補足ではなく引用になる。その結果、次のことが
起きる。

| | 何が起きるか |
| --- | --- |
| 引用の密度 | 実際より高く出る |
| 補足の密度 | 0 が並ぶ |

エラーにはならない。値が出て、判定も回り、結果だけが間違っている。

そのため、Alert 記法を持つ取り込み元では、引用より先に Alert を認識する。同じことが脚注、
折りたたみ（`<details>`）、独自の補足記法にも起きる。

### 対応表は取り込み元ごとに持つ

取り込み元は Markdown と HTML である。取り込み元を増やすときは、この表に行を足す。

| | 何の構文か |
| --- | --- |
| `markdown` | Markdown + Alert 記法（`> [!NOTE]`）+ directive 記法（`:::note`） |
| `html` | HTML |

取り込み元はファイルの拡張子で決まる。`.html` と `.htm` は `html`、それ以外は `markdown`
である（[設計](../design/200-command.md#取り込み元は拡張子から決める)）。利用者に取り込み元を
指定させることはしない。

#### Markdown を方言に分けない

Alert 記法と directive 記法は、どちらも `markdown` という 1 つの取り込み元で認識する。
Markdown を方言ごとに別の取り込み元に分けることはしない。

分けない理由は次のとおりである。

| | 理由 |
| --- | --- |
| 分けても測れるものが増えない | 2 つの記法は構文として重ならない。分けていたころも、それぞれで書ける node は同じだった |
| 方言の指定を誤ると黙って壊れる | directive 記法の方言として読んだ `> [!NOTE]` は[引用になってしまう](#黙って壊れる場所がある)。エラーにならない |
| 方言を指定する手間が毎回かかる | 1 本を測るたびに方言を選ばせることになる |

経緯：以前は GitHub の方言と directive の方言を別の取り込み元とし、利用者に名乗らせて
いた。上の理由でやめた。

記法を持たない媒体（たとえば補足も表も書けない素の CommonMark）を、別の取り込み元にする
こともしない。そうすれば、その媒体では補足や表を「書けない」と記録し、「0 だった」と
「測れない」を[区別](#取り込み元を間違えると0-が並ぶ)することはできる。しかし、どの媒体で
書いたかは媒体側の申告であり、文書の中身からも拡張子からも分からない。申告させれば、
指定の手間と指定の誤りが戻ってくる。また、本人の素材と検める草稿は同じ媒体で書かれるので、
どちらも 0 のまま比べても判定は狂わない。

#### 標準の名前を名乗らない

「CommonMark に対応している」とは書かない。どの取り込み元も、kakiburi 独自の取り込み元と
して定義する。認識する構文は[下の対応表](#node-への対応表)に列挙し、表に無い構文は
[断る](#通らないものは断る)。

標準の名前を名乗らないのは、名乗るとその標準の構文をすべて認識する義務が生まれるから
である。1 つでも取りこぼすと、その構文は断られずに地の文へ流れてしまう。たとえば見出しを
下線（Setext）で書いた文書を、その構文を知らずに読むと、見出しが 0 になったうえで、見出しの
文字列が段落として数えられる。これは[取り込み元を間違えたとき](#取り込み元を間違えると0-が並ぶ)
と同じ壊れ方で、それが「正しく読んだつもり」でも起きる。

各取り込み元が何を元にしているかは次のとおりである。

| | 何から取ったか |
| --- | --- |
| `markdown` | [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) の部分集合 + [GFM](https://github.github.com/gfm/) の表 + 脚注 + Alert 記法 + directive 記法（`:::note`） |
| `html` | HTML の部分集合 |

元にした標準の版も[指紋](200-extract.md#何で測ったかを指紋にする)（何で測ったかの記録）に
出す。同じ記法でも、版によって解釈が変わることがあるからである。HTML には版が無いので、
参照した日付のスナップショットを出す。

Markdown の中に書かれた生の HTML は、`<details>` を除いて断る。CommonMark は HTML block と
raw HTML を構文として認めているが、ここでは認めない。認めると、`<aside>` や `<table>` を
使って補足や表を書く道ができ、1 つの取り込み元の中で同じ node に 2 通りの記法があることに
なる。HTML で書きたいなら、そのファイルを `html` として入れればよい。

`<details>` だけを例外にするのは、GitHub で折りたたみを書く方法がそれしか無いからである。
GitHub の Markdown に折りたたみの記法は無く、GitHub 自身が `<details>` を使うよう案内して
いる。例外はこの 1 つだけである。

#### node への対応表

[文書の形](020-document.md#文書は-node-でできている)が挙げたすべての node について、取り込み元
ごとの記法を次の表で定める。ここに無い記法は、対応表に無い記法として扱う。

| node | `markdown` | `html` |
| --- | --- | --- |
| 段落 | 空行で区切られた行 | `<p>` |
| 見出し | `#`、Setext の下線 | `<h1>`〜`<h6>` |
| 箇条書き | `-` `*` `+` | `<ul>` |
| 番号リスト | 数字（1〜9 桁）+ `.` または `)` | `<ol>` |
| 項目 | リストの直接の子 | `<li>` |
| 引用 | `>`（Alert・directive に当たらないもの） | `<blockquote>` |
| 表 | GFM の表 | `<table>` 1 つが表 1 つ |
| セル | 表の升目（行と列が交わる 1 マス） | `<td>` `<th>` |
| コードブロック | ``` `` ``` と `~~~` の囲み（記号は 3 つ以上）、4 字下げ | `<pre>` |
| インラインコード | `` ` `` の囲み（記号はいくつでも） | `<pre>` の外の `<code>` |
| 区切り線 | `---` `***` `___` | `<hr>` |
| 画像 | `![]()`、参照形式 `![][ref]` | `<img>` |
| 強調 | `*` `_` `**` `__` | `<em>` `<strong>` `<b>` `<i>` |
| リンク | `[]()`、参照形式 `[][ref]`、自動リンク | `<a>`（脚注に当たらないもの） |

HTML の表の扱いは次のとおりである。`<table>` の中の `<thead>` `<tbody>` `<tfoot>` `<tr>` は
node にせず、透過させる。`<table>` 1 つが表の node 1 つ、`<td>` `<th>` 1 つがセルの node 1 つ
になる。行や区分まで表として数えると、ふつうの表 1 つで表の密度が何倍にもなってしまう。

HTML のコードは次のように扱う。コードブロックは `<pre>` である。`<pre><code>` は `<pre>` 1 つ
にまとめ、中の `<code>` を別の node にしない。インラインコードになるのは、`<pre>` の外に
ある `<code>` だけである。段落の中の `<code>` までコードブロックにすると、インラインコードは
いつまでも 0 になり、コードブロックの密度は、地の文に入らない記号の分だけ跳ね上がる。

補足・警告・脚注・折りたたみは、記法が族（似た書き方の一群）にまとまっているので、この
あとの別の表で定める。

この 2 つの表に無い構文は、対応表に無い記法として[断る](#通らないものは断る)。元にした
標準の側にある構文でも同じである。表を全部書き出すのは、「知らない記法だから地の文として
通しておく」という扱いを作らないためである。

そのため、表に無いものをここで名指ししておく。GFM の task list と取り消し線、CommonMark の
改行の書き分け、エスケープと文字参照は、どれも認識しない。使われていれば断る。これらを
足すときは、先に[node の表](020-document.md#文書は-node-でできている)に落ちる先があるかを
決める。

参照定義行（`[ref]: https://…`）は認識するが、node にはしない。参照形式のリンクと画像を
表に載せている以上、この行を断ると参照形式が成り立たないからである。行を読んで参照を
解決し、行そのものは地の文にも構造にも残さない。書き手が本文として書いたものではない
からである。

[子を持つ node](020-document.md#文書は-node-でできている)の中身は、もう一度ブロックとして
解釈する。引用・補足・警告・折りたたみ・脚注・セルの中にある段落、リスト、表、コード
ブロックは、そのまま node になる。中身を 1 本の文字列にまとめてはいけない。まとめると
内側の構造がまるごと消え、コードブロックの中身が地の文に混ざってしまう。

補足と警告は別の node である。どちらも同じ族の記法で書かれるので、どの記法がどちらに
落ちるかを決めておかないと、実装ごとに変わってしまう。

| 記法 | どの node か |
| --- | --- |
| `[!NOTE]` `[!TIP]` `:::note` `:::tip` `:::message` `<aside>` | 補足 |
| `[!WARNING]` `[!CAUTION]` `[!IMPORTANT]` `:::warning` `:::caution` `:::message alert` | 警告 |
| `[^1]` と定義行、`:::footnote`、`<sup><a>` | 脚注 |
| `<details>`、`:::details` | 折りたたみ |
| GFM の表、`<table>` | 表 |

`IMPORTANT` を警告に入れるのは、それが書き手が「読み飛ばすな」と示している記法だから
である。補足は本筋から外れることを示す記法で、向きが逆である。

記法の名前だけでは node が決まらないものもある。Zenn の `:::message` は補足だが、
`:::message alert` は警告である。`alert` という修飾を読み落とすと、警告が補足になって
しまう。

取り込み元によっては、そもそも書けない node がある。取り込み元と node の組ごとに、書ける
かどうかを次の表で定める。この表の 1 マスを升目と呼ぶ。

| 取り込み元 | 補足 | 警告 | 脚注 | 折りたたみ | 表 |
| --- | --- | --- | --- | --- | --- |
| `markdown` | 書ける | 書ける | 書ける | 書ける | 書ける |
| `html` | 書ける | 書けない | 書ける | 書ける | 書ける |

升目が「書けない」なら、その取り込み元の文書では、その node の値は 0 ではなく「測れない」
になる。0 と「測れない」は区別しなければならない。0 を並べると、その書き手は補足（や警告）
を使わない人だと判定されてしまう。

### 取り込み元を間違えると、0 が並ぶ

取り込み元はファイルの拡張子だけで決まり、Markdown の方言は 1 つである。そのため、利用者が
取り込み元を[名乗り違える場所は無い](#markdown-を方言に分けない)。残る取り違えは、どれも
断られる。

| 取り違え | どうなるか |
| --- | --- |
| HTML を `.md` で置いた | Markdown の中の生の HTML として[断る](#通らないものは断る) |
| 対応表に無い `:::hint` や `> [!HINT]` | 対応表に無い記法として断る。地の文には流さない |

ここまで間違えようのない形にしたのは、升目による「書けない」の区別が、取り込み元が正しく
決まって初めて効くからである。取り込み元を間違えると、書けるはずの升目が、エラーを出さず
に 0 を返す。

経緯：Markdown を方言に分けていたころ、Zenn の記事 12 本を、directive 記法を持たない方言と
して読んで比べた。

| | directive を持つ読み方 | 持たない読み方 |
| --- | --- | --- |
| 補足 | 18 箇所 | 0 |
| 警告 | 2 箇所 | 0 |
| 段落（1 本の例） | 52 | 63 |

書き手は補足と警告を合わせて 20 回使っているのに、「使わない人」として出た。段落の数まで
変わったのは、補足の中身が段落として数えられたからである。

## 表記を潰さない

正規化で字種や字幅を揃えてはいけない。

全角と半角、`〜` と `～`、`…` と `……` の違いは、
[書き手の選択であり、測る価値が高い](020-document.md#表記は残る優先して採る理由がある)。

正規化で潰すもの（記法）と潰さないもの（表記）を、次のように分ける。

| | 例 |
| --- | --- |
| 潰す（記法） | 箇条書きの `-` と `*`、見出しの `#` と下線、強調の `**` と `__` |
| 潰さない（表記） | 字種、字幅、空白の入れ方、改行の位置 |

既製の整形ツールの多くは、頼まなくても表記まで揃えてしまう。既製のフォーマッタを通すなら、
その前に何を書き換えるかを確かめる。通したあとでは、表記が潰れたことに気付けない。

### 書き手が打っていない空白を作らない

正規化は、書き手が打っていない空白を地の文に入れてはいけない。上の「表記を潰さない」は
書き手が打ったものを残せという規則であり、この節は打たれていないものを足すなという規則
である。

正規化の過程では、書き手が打っていない空白が生まれる。出どころは次の 2 つである。

| | 何が起きるか |
| --- | --- |
| 取り込み元の折り返し | HTML の段落の中の改行は、書き手の改行ではなく書き出し側の折り返しである。表示では 1 個の空白になる |
| 取り除いたインラインコードの跡 | 中身を[地の文に入れない](020-document.md#地の文)ので、`設定は ` + `` `--force` `` + ` である` が `設定は␣␣である` になる |

これらの空白は次のように始末する。

> どちらも、和文どうしのあいだにできたものなら残さない。日本語は分かち書きをしないので、
> そこに空白は表示されないからである。それ以外は空白 1 個にする。表示ではそうなるからである。

書き手が手で打った空白には触れない。`これは 日本語 である` の空白は
[表記](#表記を潰さない)であって、書き出し側の都合でできたものではない。表示だけでは手で
打った空白と区別できないので、折り返しと跡には印を付けて処理の間持ち回り、区切りの両端が
見えたところで始末する。

始末せずに残すと、次の 2 つが壊れる。

| | 何が起きるか |
| --- | --- |
| 取り込み元が値を動かす | 同じ文が、書き出し側の折り返し方だけで別の値になる |
| 題材が値を動かす | インラインコードの多い記事ほど、跡の空白が増える（[題材で判定が覆ってはいけない](100-metrics.md#題材で判定が覆ってはいけない)） |

`<pre>` の中の空白は始末しない。そこの空白は表示されるからである。

実測：はてなの書き出し 27 本には、和文を割る折り返しが 935 箇所あった。始末する前は、
[和文間スペース](metrics/和文間スペース.md)が同じ本人の Markdown で 0.0015、HTML で 0.0225
と出ていた。この差は書きぶりではなく書き出し側によるものである。始末したあとは 0.0032 と
0.0039 になった。

## 通らないものは断る

正規形に落とせない入力は、無理に通さずに断る。

| | どうするか |
| --- | --- |
| 記法が壊れていて解釈できない | 断る |
| 対応表に無い記法が使われている | 断る。対応表を足してから通す |
| 日本語以外が主 | 断る（[日本語だけ](010-strategy.md#日本語だけ)） |

黙って一部を落として通すと、落ちた分だけ値の狂った文書が、正常な文書と見分けのつかない
形でコーパスに入ってしまう。

「日本語以外が主」かどうかは、次の規則で決める。判定は決定的でなければならないので、
言語判定の道具には頼らない。

> [地の文](020-document.md#地の文)の文字のうち、[日本語の文字](020-document.md#日本語の文字)
> が 3 割に満たなければ断る。

この割合の分母からは約物と空白を外す。コードの多い技術記事では英数字と記号が増えるが、
それは題材の違いであって言語の違いではない。
[地の文はコードもコードだけのセルも含まない](020-document.md#地の文)ので、ここで数えるのは
散文だけである。

分母は「地の文に残ったもの」なので、地の文から落としたセルはここにも入らない。記号だけの
比較表が大半を占める文書は、表の分が分母から消えたうえで判定される。残った散文が日本語
なら通る。それでよい。断る基準は「日本語で書かれていない文書」であって、「表が多い文書」
ではない。

3 割は暫定値である（[指標](100-metrics.md#除外の既定)）。地の文の作りを変えたら、この値は
導き直す。分母が変わると、同じ 3 割でも同じ文書を断らなくなるからである。

## 正規形が原本である

元のファイルは手元に残らない（[素材を正本にする](200-extract.md#素材を正本にする)）という
前提で設計する。

したがって、正規形から測れないものは、あとからも測れない。何を正規形に残すか迷ったら、
残す側に倒す。

正規形から元の書式に戻せること（往復）は目的にしない。元の書式を復元できるようにすると、
記法の情報を抱え込むことになり、[潰すと決めたもの](#表記を潰さない)が残ってしまう。

## 変換したことを記録する

何をどう変換したかを、測った値と一緒に残す。

| 残すもの | 形 |
| --- | --- |
| 取り込み元の種類 | 読んだものを全部。複数の取り込み元を混ぜて読んだなら全部を並べる |
| 名乗った構文の版 | `CommonMark 0.31.2` のような固定した版 |
| 使った変換の実装と版 | 実装の名前と版 |
| 適用した対応表 | 対応表の版と、升目の中身そのもの |

これらは[指紋](200-extract.md#何で測ったかを指紋にする)に含める。変換規則が変われば、過去の
値とは比べられない。記録が無ければ、比べられないことにも気付けない。

対応表は版だけでは足りないので、升目の中身も一緒に残す。升目の中身を変えたのに版を上げ
忘れると、指紋は同じなのに別の木（正規形）が出てしまう。手で上げる版と、機械が出す升目の
中身の両方が変わっていないときだけ、過去の値と比べてよい。

升目の中身はハッシュにせず、そのまま置く。升目は取り込み元ごとに書けるかどうかが分かれる
node の組だけなので小さく、そのまま置ける。ハッシュだけでは、どの升目が変わったかが分から
ない。これは[材料を平文で残す](../design/100-cassette.md#指紋は組み立てを型で守る)のと同じ
理由である。

どの[単位](../glossary.md#単位)（測るときのひとまとまり）にどの升目が当たったかは、単位ごとには
残さない。[素材](200-extract.md#素材を正本にする)を読み直せばそのまま分かる。正本が手元に
あるので、控えを持つ理由が無い。

### 変換規則を変えたら、測り直す

変換規則を変えたら、素材から測り直す。指標が増えたときに測り直すのと同じ扱いである。
[素材を正本にした](200-extract.md#素材を正本にする)ので、正規形の本文はいつでも作り直せる。
変換規則を変えたら、素材をもう一度読めばよい。

| 変わったもの | どうするか |
| --- | --- |
| 指標の集合 | 測り直す |
| 変換規則 | 測り直す。素材から同じ手順で作り直す |

それでも、変換規則を黙って変えることはしない。[指紋](200-extract.md#何で測ったかを指紋にする)
に変換規則が入っているので、作り直していない[カセット](../glossary.md#カセット)（`build` が
作る目盛りのファイル）は「環境と合わない」として止まる。止まらなければ、規則の差が人の差
として出てしまう。

> 経緯：kakiburi が本文を持っていたころは、ここが取り返しのつかない場所だった。元の
> ファイルは手元に無いので、変換規則を変えるとコーパスが古い本文と新しい本文に割れ、
> 二度と揃わなかった。素材を正本にしたことで、この危険は無くなった。
