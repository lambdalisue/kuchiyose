# 実装が仕様の穴を見つける

[500 の結論](500-directive-loop.md)を受けて、[仕様を写す](../../crates/)ことを始めた。
<strong>穴が 11 個出た。</strong> どれも 7 回のレビューと 10 周の監査が見つけられなかったものである。

```
nix develop --command cargo test
```

| クレート | 何を独占するか | 試験 |
| --- | --- | --- |
| [`kakiburi-doc`](../../crates/kakiburi-doc/) | 日本語の文字・地の文・文・段落・節・項目・見出しの深さ | 47 |
| [`kakiburi-normalize`](../../crates/kakiburi-normalize/) | 記法から意味への対応表、断る規則。Markdown と HTML | 101 |
| [`kakiburi-metrics`](../../crates/kakiburi-metrics/) | 登録簿・札・系統と層、指標と系統の数え方、形態素解析 | 143 |
| [`kakiburi-scale`](../../crates/kakiburi-scale/) | 分割・対の割り当て・語彙・較正・帯・組み立て | 68 |
| [`kakiburi-review`](../../crates/kakiburi-review/) | 3 段の判定・幅からの外れ・指摘 | 44 |
| [`kakiburi-cassette`](../../crates/kakiburi-cassette/) | 3 つの層・指紋・zip と JSON | 46 |
| [`kakiburi-cli`](../../crates/kakiburi-cli/) | `new` `add` `build` `review` `measure` `metrics` | 21 |

<strong>境界を機械で守る。</strong>[`no_scale_dependency.rs`](../../crates/kakiburi-review/tests/no_scale_dependency.rs)が
`Cargo.toml` を読んで、検めが目盛りを作る側に依存していないことを確かめる。<strong>型では
守れない</strong>——依存を足せば使えてしまう。試しに足すと 2 つの試験が落ちる。

<strong>漏れを型で止めた 3 か所。</strong>

| | どう止めたか |
| --- | --- |
| 検めが重みを作り直す | <strong>依存を持たない。</strong> `Frozen::fit` も `Calibration::fit` も全体を要求する |
| 較正に使った対で目盛りを作る | <strong>対の作り手を 1 つにし、共有していないかを問える</strong>（`shares_pairs`） |
| 測れていないものを 0 として扱う | <strong>`Measured` が 3 値である。</strong> `BelowFloor` から値は取れない |

試験の名前が仕様の主張になっている——`約物は日本語の文字ではない`、`文は_node_を跨がない`、
`alert_を引用より先に認識する`、`取り込み元を間違えたら断る`、`層は系統から引くしかない`。

<strong>登録簿は定義ファイルと突き合わせる。</strong>[`spec_matches.rs`](../../crates/kakiburi-metrics/tests/spec_matches.rs)が
`docs/spec/metrics/*.md` を読んで登録簿を作り、<strong>札が読めなければ落ちる。</strong>
51 本すべてが読め、内訳は指示 39 / 照合 8 / 人らしさ 4——[検査器](../../tools/README.md)の
数と一致する。

<strong>読む道は実装と共有した。</strong> 試験だけが別の読み方をすると、通っているのは試験の
読み方でしかない。[定義ファイルの読み手](../../crates/kakiburi-metrics/src/definitions.rs)を
本体に置き、<strong>指摘の文もそこから引く</strong>——指摘の文を実装に持てば、仕様と食い違ったこと
に誰も気づかない。

<strong>試験そのものを検めた。</strong> 中黒の札の系統名を `読点の打ち方` から `読点` に変えると、
<strong>5 つの試験が落ちる</strong>。綴りが違えば層が引けないことを、機械が止める。

## 1. `・` が日本語の文字に入っていた

<strong>最初に書いた試験が落ちた。</strong>

> `・` を日本語の文字にしてはいけない

`・`（U+30FB）は <strong>Katakana ブロックの中にある。</strong> 仕様は範囲を「Katakana ブロック」と
書いていたので、素直に実装すると約物が[日本語の文字](../spec/020-document.md#日本語の文字)に入る。

そして[文字種](../spec/metrics/文字種.md)は `・` を約物に数えている。<strong>同じ文字が 2 つの
分類に入り、10 分類が排他でなくなる。</strong>

<strong>もっと悪いのは分母である。</strong>[中黒](../spec/metrics/中黒.md)は日本語 1,000 字あたりで
測る。`・` が分母に入れば、中黒の多い書き手ほど分母が膨らんで中黒の率が下がる——
<strong>仕様が読点について名指しで禁じている形が、範囲の書き方だけで起きていた。</strong>

同じ穴が 3 つあった。

| 符号位置 | 何か | ブロック |
| --- | --- | --- |
| U+30FB `・` | 約物 | Katakana |
| U+30A0 `゠` | 約物 | Katakana |
| U+3099〜U+309C | 濁点・半濁点 | Hiragana |

<strong>符号位置で書くしかない。</strong>[020 を直した](../spec/020-document.md#日本語の文字)。

## 2. 無限に回る経路があった

本人の記事 12 本に当てたら、<strong>止まらなくなった。</strong> 2 つのプロセスが 99% の CPU を使い、
メモリが <strong>5.7 GB</strong> まで膨らんだ。

原因は<strong>段落の切れ目と block の振り分けがずれていたこと</strong>である。`:::` で始まる行を、
振り分けは拾わないのに段落は切れる。だから何も消費せず、空の段落を積み続けた。

<strong>エラーにならない。</strong> 走らせるまで気付けない。

不変条件として書いた——<strong>block は必ず入力を進める。</strong> 進まなければ断る。
そして切れ目の判定を振り分けと 1 つの関数にまとめ、ずれられないようにした。

## 3. Zenn の `:::message` が対応表に無かった

本人の記事は <strong>Zenn の `:::message` を 21 箇所</strong>使っている。対応表には
`:::note` `:::tip` `:::warning` `:::caution` しか無かった。

<strong>名前だけでは決まらない。</strong> `:::message` は補足だが `:::message alert` は警告である。
修飾を落とすと警告が補足に化ける。

[対応表に足した](../spec/030-normalize.md#対応表は取り込み元ごとに持つ)。仕様が
「対応表を足してから通す」と言っているとおりの手順である。

## 4. 取り込み元を間違えると 0 が並ぶ

<strong>これがいちばん重い。</strong>

仕様は[「書けない」升目が「測れない」を返す](../spec/030-normalize.md#対応表は取り込み元ごとに持つ)
と決めている。だが<strong>その守りは、取り込み元が正しく申告されて初めて効く。</strong>

Zenn の記事を `github-markdown` として読むと——

| | `directive-markdown` | `github-markdown` |
| --- | --- | --- |
| 補足 | <strong>18 箇所</strong> | <strong>0</strong> |
| 警告 | <strong>2 箇所</strong> | <strong>0</strong> |
| 段落（`b4a31fba` の例） | 52 | 63 |
| 文（同） | 108 | 108 |

<strong>書き手は 20 回使っている。</strong> それが「補足を使わない人」として出る。段落の数まで変わる
——補足の中身が段落として数えられるからである。

<strong>「書ける」升目だからこそ危ない。</strong> `github-markdown` に Alert はあるので、
0 は「使わなかった」と読まれる。<strong>測れないにはならない。</strong>

直した。<strong>`:::` を知らない取り込み元で `:::message` を見たら、対応表に無い記法として断る。</strong>
実装で確かめると、<strong>12 本のうち 6 本が断られる</strong>——`:::message` を使っている 6 本である。

## 5. 強調が永久に 0 だった

指標 33 本を実際の記事に当てたら、<strong>強調が全部 0.000 だった。</strong> 本人は太字を使っている。

原因は<strong>記法を落とすだけで node を作っていなかったこと</strong>である。[強調は node](../spec/020-document.md#文書は-node-でできている)
なので、`**` を消すだけでは[強調の指標](../spec/metrics/強調.md)が数える対象が存在しない。
<strong>エラーにならない。</strong> 0 が並び、「太字を使わない人」と判定される。

直そうとすると、<strong>型が文中の強調を表せない</strong>ことが分かった。`Node` は `text` と
`children` の並び順を持たないので、子の文字列を親に足すと<strong>強調がつねに末尾に来る。</strong>

<strong>子は数えるためだけに置く</strong>ことにした——文字列は親が 1 度だけ持つ。
[020 に書いた](../spec/020-document.md#地の文は-1-本の文字列ではない)。

直すと強調は 0.281 〜 2.947 になった。<strong>途中でもう 1 つ躓いた</strong>——`**` は開きと閉じで
2 度通るので数を 2 で割って畳んだら、1 度しか通らない HTML の `<em>` が消えた。
畳むのをやめて<strong>開閉の切り替えで数える</strong>形にした。

## 6. 「昇順」が決まっていなかった

[指摘の順位付け](../spec/200-extract.md#外れの大きさは幅を-1-とした倍数である)は、
同じ大きさのものを<strong>指標名の昇順</strong>で決めると書いてある。<strong>決定性のためである。</strong>

だが<strong>和名の「昇順」は 3 通りに読める</strong>——符号位置順、五十音順、ロケールの照合順。
後ろの 2 つは実装と環境に依るので、<strong>決定性のために順序を決めているのに、そこが揺れる。</strong>

`感嘆符` `笑い` `絵文字` を並べたら、私の期待と実装が食い違った。<strong>私の期待に根拠が
無かった。</strong> 符号位置順しかありえない——[200 に書いた](../spec/200-extract.md#外れの大きさは幅を-1-とした倍数である)。

読みを使わないのは、<strong>読みを持っていないからでもある。</strong> 指標名に読みを添えれば、
それが[2 か所目の名前](../spec/100-metrics.md#名前は-1-度しか書かない)になる。

## 目盛りと判定も通した

| [系統が欠けたら](../spec/200-extract.md#系統が-1-つでも欠けたら照合値を出さない) | <strong>`Result` で返し、欠けた名前を添える</strong> |

<strong>「判定できない」が「通らない」と混ざらない。</strong> 終了コードが 2 と 1 で分かれ、
3 段目の外れは<strong>通らないではなく判定できない</strong>を返す。

## 終了コードが分かれる

```
kakiburi new    <カセット> --scene 技術記事
kakiburi add    <カセット> <ファイル...> --source directive-markdown --as person
kakiburi build  <カセット>
kakiburi review <ファイル> --cassette <カセット>
```

まず本人 3 本と基準 2 本で回した。

| 何をしたか | 返った |
| --- | --- |
| `new` `add` | `0` |
| <strong>取り込み元を間違えて `add`</strong> | <strong>`65`</strong> 断る。1 本でも断ったら何も入れない |
| `build`（単位が足りない） | <strong>`0`</strong> 目盛りを作らずに成功。止まっても失敗ではない |
| `review` | <strong>`2`</strong> 判定できない。但し書きに暫定値が出る |

<strong>指紋の照合が実際に効いた。</strong> 途中で `add` が取り込み元を指紋に足したため、環境の
指紋と食い違って `66` が返った。<strong>取り込み元はカセットが決めたことなので引き継ぐ</strong>
ように直した——引き継がなければ、正しいカセットがつねに合わなくなる。

## カセットは 3 つの層になった

zip と JSON を外の crate 無しで書いた。<strong>索引があることが zip を選んだ理由</strong>なので、
索引だけを読む経路と 1 つだけ読む経路を持つ。

<strong>時刻を入れない。</strong> 入れると、同じ中身から違うバイトが出て
[作り直しても同じものが出る](../design/300-test.md#作り直せることを試験する)が成り立たない。

<strong>そしてその試験が通った。</strong>`derived/` を丸ごと落として同じ派生物を入れ直すと、
元と同じバイトになる。原本も指紋も残る。

<strong>途中で 1 つ直した。</strong> 単位の並びが正典でなかったので、書き出して読み戻すと順が
変わっていた。役と名前の昇順で持つようにした。

## 形態素解析を実際に繋いだ

<strong>UniDic は nixpkgs に無いが、国語研が配布している。</strong> `unidic-mecab-2.1.2_bin` を落として
MeCab に指した。<strong>辞書の経路は環境変数で渡す</strong>——変数の名前が `KAKIBURI_UNIDIC` である
ことが、そこに UniDic を指すという申告になる。<strong>中身から当てにいかない。</strong>

まず名乗りの規則が効いた。<strong>「鍵が合わない」の実体が見えた</strong>——同じ 8 番目の欄が
IPADic では読み（`コレ`）、UniDic では語彙素（`此れ`）である。<strong>位置は同じで、中身が違う。</strong>

そして<strong>実際に走らせて 3 つ出た。</strong>

### 辞書が出力の形を決めてしまう

UniDic 2.1.2 の `dicrc` は `output-format-type = unidic` を持ち、素性を<strong>並べ替えて
タブ区切りで</strong>出す。<strong>`--node-format` を渡しても、その型が優先されて黙って無視される。</strong>

<strong>「8 番目が語彙素」は素性の配列に対して成り立つ話であって、並べ替えた出力には
成り立たない。</strong> 読み手はそのまま動き、値だけが違うものになる。

設定ファイルを自分で置いて、素性の配列そのものを出させるようにした。

### 知らない語で解析器が死ぬ

知らない語の素性は短い。8 番目を読もうとすると MeCab がそこで止まる
（`given index is out of range`）。<strong>知らない語は実際の記事に必ず出る。</strong>

知らない語の側だけ、語彙素の欄に表層形を置く形にした。UniDic は知らない語に語彙素を
持たないので、それが読み手の当てはめる既定と同じものになる。

### 長い行が黙って分割される

MeCab の入力の緩衝は既定で 8,192 バイトである。<strong>それを超える 1 行は分割される</strong>——
そして行の数で切り分けている側は、1 つずれる。

<strong>これは実際に起きていた。</strong> ある仕様書は 3,266 字あるのに<strong>延べ 0 語</strong>になっていた。
0 語なら除外に掛かるので、<strong>「短すぎて測れない」と見分けられない。</strong>

いちばん長い行に合わせて緩衝を広げるようにした。<strong>そして印を挟まない</strong>——印に選んだ
文字が本文に出れば、そこで切れて静かにずれる。行の数は数えれば分かる。

<strong>node ごとに解析器を起こさない。</strong> 1 文書 1 回にまとめた。node ごとに起こせば
200 MB の辞書を node の数だけ読み直すことになり、[測るのが高ければ周回数が減る](../spec/100-metrics.md#測るのを安くする)。

## 「zlib、水準 6」では値が決まらなかった

[圧縮率](../spec/metrics/圧縮率.md)は器を固定すると書いてある。<strong>だが zlib 形式が決めて
いるのは容器であって、符号化の選び方は実装ごとに違う。</strong>

同じ 106,827 バイトを同じ水準 6 で圧縮して、<strong>zlib 1.2.12 は 31,813 バイト、
miniz_oxide 0.8 は 31,761 バイト</strong>を返した。52 バイト、率で 0.0005 の差である。

<strong>「器が変われば値が変わる」と書きながら、器を名前だけで指していた。</strong> 実装と版まで
名乗るように直した。

## 「語」がどちらか決まっていなかった

[繰り返し](../spec/metrics/繰り返し.md)・[語彙の豊富さ](../spec/metrics/語彙の豊富さ.md)・
[エントロピー](../spec/metrics/エントロピー.md)はどれも「語」で数えると書いてある。
<strong>表層形とも語彙素とも読める。</strong> どちらでも手続きは通り、<strong>値が変わる</strong>——語彙素に
畳めば異なり語が減り、豊富さもエントロピーも下がる。

[数え方の側に 1 度だけ書いた](../spec/100-metrics.md#語を数えるときは表層形である)。
活用の使い分けがそこにあるので表層形を採る。

## 下限の判定が効かない指標が 39 本あった

仕様は[使った割合で見る](../spec/200-extract.md#下限は使った割合で見る)規則を持っている。
<strong>実装が持っていなかった。</strong>

密度の指標は、一度でも使わなかった単位があれば幅の下端が 0 になる。<strong>0 を下回る値は
無いので、下限の判定が永久に効かない。</strong> 毎回使う語が丸ごと消えていても、指摘に出ない。

<strong>どちらの規則を使うかは札の単位から引く。</strong> 指標ごとに書かない——`〜に対する割合`
と `無次元` は幅で見て、`〜あたり`・`個`・`割合` は使った割合で見る。

## 周回が端まで通った

<strong>本人 10 単位・基準 11 単位、実際の日本語、実際の UniDic。</strong> 素材は
[この仕様書そのもの](../spec/)と、[500](500-directive-loop.md)で書いた基準の記事である。

| 段 | 結果 |
| --- | --- |
| 正規化 | 21 本すべて通る。<strong>`<sub>` を使う 1 本は断られた</strong> |
| 除外 | 21 本すべてが 5 系統と 12 次元を測れた |
| 長さの範囲 | 通る |
| 語彙の固定・較正 | 通る |
| <strong>照合値の帯</strong> | <strong>作れた。</strong> 天井 −0.22〜0.74 / 床 −2.67〜−1.84 |
| 人らしさの帯 | <strong>止まった。</strong> 重なりが床の 58% |

<strong>照合の側は分離した。</strong> 5 系統を合算した値で、天井の下端と床の上端のあいだに
1.62 の隙間がある。<strong>これが初めて動いた。</strong>

<strong>そして人らしさの側は正しく止まった。</strong> 天井の点も床の点も −5.2 の周りに固まり、
<strong>本人の側がわずかに低い</strong>。

理由は素材である。<strong>この試しの「本人」は我々が書いた仕様書である</strong>——機械が書いた
ものである。人らしさは人と機械を分ける段なので、<strong>両側とも機械なら分離しないのが
正しい。</strong> 帯はそれを「骨格が通っていない」として返した。

<strong>止まったときに何を言うかを直した。</strong> 割合だけでは、素材を足すべきか系統を見直すべきか
辞書を入れるべきかが分からない。いまは<strong>どちらの帯か・点がどこに来たか・どこまでは
通ったか</strong>を返す。

## 何が言えるか

| | |
| --- | --- |
| <strong>仕様は端まで実装できる</strong> | 逸れるたびに仕様が捕まえた |
| <strong>照合の側は実際に分離した</strong> | 実際の日本語、実際の辞書、5 系統の合算で |
| <strong>読むだけでは足りない</strong> | 穴は 11 個。どれも書いて走らせて初めて出た |
| <strong>外の道具を繋ぐと穴の質が変わる</strong> | 3 つとも「エラーにならず 0 になる」形だった |

<strong>穴のうち 3 つは、外の道具の既定が仕様の前提を裏切る形だった。</strong> 辞書が出力の形を
決める、知らない語で死ぬ、長い行が分割される——<strong>どれも仕様の文章からは出てこない。</strong>

## 何が言えないか

<strong>判定を通しで出していない。</strong> 目盛りが作れる素材が無いので、`review` が実際の目盛りを
読んで 3 値を返すところは<strong>試験の中でしか動いていない</strong>——組み立て・保存・読み戻し・
検めはそれぞれ試験で確かめてあるが、実際の周回では人らしさの帯で止まっている。

<strong>人が書いた素材が要る。</strong> それが無いかぎり、人らしさの段は正しく止まり続ける。

<strong>そして素材が足りないことは変わっていない</strong>（[500](500-directive-loop.md#素材が足りない)）。
延べ 1,000 語の下限は、1,200 字ほどの記事を落とす。<strong>いまの基準の記事のうち 10 本が
そこで落ちた</strong>ので、2,200 字以上のものを 7 本書き足して初めて通った。
