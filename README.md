# kakiburi

LLM に代筆させた日本語の草稿が、あなたの書き方からどこでずれているかを数えて、
直し方を言葉で返すツール。

代筆させた文章は、読めば「自分の文章ではない」と分かる。けれど、どこが違うのかは
言いにくい。kakiburi はそこを数える。あなたが過去に書いた記事から書き方の目盛りを作り、
草稿をそれに当てて、たとえば次のように返す。

```
判定: 通らない
止まった段: 人らしさ値

人らしさの直し方
  - 句読点の密度が本人より足りない（この文章 -0.125 / 本人 1.188）。
    文を繋いで長くし、読点を減らす。
```

AI が書いたことを隠すためのツールではない。見ているのは「AI っぽさが残っていないか」と
「あなたの書き方に寄っているか」であって、検出器をすり抜けられるかではない。

## 仕組み

```
あなたの記事（素材） ─┐
                      ├─ build ─→ カセット（目盛り）
機械の文章（基準）   ─┘                │
                                      ▼
草稿 ─────────────────────────── review ─→ 判定 ＋ 直し方
```

1. `build` が、あなたの記事と、同じ題材を LLM に素で書かせた文章（基準）の両方を数える。
   あなたの記事どうしの近さと、機械の文章との遠さから、目盛りを作ってカセットに保存する。
2. `review` が草稿を同じやり方で数え、目盛りに当てる。あなたの側に寄っていれば「通る」、
   機械の側なら「通らない」、どちらとも言えなければ「判定できない」を返す。
   あわせて、どの指標をどちらへ直せばよいかを返す。

数えるのは語や句読点の頻度、文の長さ、表記の揺れなど、読まずに数えられる量だけである。
LLM に採点させないので、同じ草稿からは毎回同じ結果が出る。

出てくる用語は[用語集](docs/glossary.md)にまとめてある。

## 入れる

```sh
cargo build --release
```

要るのは Rust だけである。形態素解析器（[Lindera](https://github.com/lindera/lindera)）と
辞書（UniDic 2.1.2）は実行ファイルに入っているので、ほかに用意するものは無い。
その分、実行ファイルは 194 MB ある。

## 使う

### 1. 自分の記事を集める

自分で書いた文章を 1 つのフォルダに入れる。目安は 10 本以上で、1 本あたり地の文で
1,000 字以上あるとよい。

同じ種類の文章だけを入れる。技術記事と議事録では書き方が違うので、混ぜると目盛りが
ぼやける。種類を分けたいときは[あとで](#文章の種類ごとに分ける)カセットを分ける。

比べる相手の「機械の文章」は用意しなくてよい。リポジトリの `baselines/` に同梱してある。

### 2. 目盛りを作る

```sh
K=./target/release/kakiburi
$K build ~/articles
```

`~/articles.kb`（カセット）ができる。数十秒かかる。

カセットには目盛りだけが入り、記事の本文は入らない。作り直すときにフォルダを読み直すので、
記事は消さずに置いておく。記事が増えたら同じ `build` をもう一度打てば、目盛りが作り直される。

リポジトリの外で実行するときは、同梱の基準の場所を `KAKIBURI_BASELINES` で渡す
（既定は作業ディレクトリの `baselines`）。

### 3. 草稿を検める

```sh
$K review draft.md --cassette ~/articles.kb
```

数秒で終わる。直して、また `review` する、を繰り返す。

`.html` / `.htm` は HTML として、それ以外は Markdown として読む。Markdown では GitHub の
`> [!NOTE]` も Zenn などの `:::message` も補足として扱う。

## 結果の読み方

判定は 3 つのどれかで、終了コードにも出る。

| 終了コード | 判定 | 意味 |
| --- | --- | --- |
| 0 | 通る | あなたの書き方の範囲に入っている |
| 1 | 通らない | 機械の側に落ちている |
| 2 | 判定できない | 素材が足りないか、どちらとも言えない位置にある |
| 64 以上 | — | 判定の前に止まった（使い方の誤り、読めないファイル、kakiburi の版違いなど） |

「判定できない」は失敗ではない。言い切れないときに無理に言い切らないための答えである。

判定は次の順に見て、最初に止まったところを「止まった段」として返す。

| 段 | 見ていること |
| --- | --- |
| 日本語として壊れていないか | 和文の間の余計な空白など |
| [人らしさ値](docs/glossary.md#人らしさ値) | 機械の癖が残っていないか（同じ言い回しの繰り返し、語彙の狭さ、句読点の密度など） |
| [照合値](docs/glossary.md#照合値) | あなたの書き方に寄っているか（文字の並び、機能語、品詞の並び、読点の打ち方、文字種） |
| [指示できる指標](docs/glossary.md#指示できる指標) | 言葉で直せる項目が、あなたがふだん書く範囲に入っているか（括弧・記号・文末など） |

人らしさ値と照合値は、正ならあなた（人）の側、負なら機械の側を指す。値の大きさそのものより、
符号と止まった段を見ればよい。

出力は 2 つに分かれる。「ここから下は判定に使っていない」という行より上は判定を止めた
理由とその直し方で、下は参考の知らせ（本人が使わない一人称、書き出しの形など）である。
知らせを直すかどうかは書き手が決める。

## うまくいかないとき

エラーの文言には、理由と次にすることが書いてある。分かりにくいものだけ挙げる。

| 言われたこと | どうするか |
| --- | --- |
| `基準が見つからない` | リポジトリの外で実行している。`KAKIBURI_BASELINES` か `--baseline` で `baselines` の場所を渡す |
| `目盛りを作らない: 測れた単位が N 本で、10 本に届かない` | 記事が足りない。短すぎる記事は数えられないので、長い記事を足す。どの記事がなぜ落ちたかも表示される |
| `短い文書ばかりなので、同じものを足しても届かない` | 1 本が地の文 1,000 字に届いていない。短い記事は 1 つのファイルにまとめる |
| `指紋が環境と合わない` | kakiburi の版が変わった。`build` し直す。以前の値とは比べられない |
| `目盛りが書いてあるのに読めない` | カセットが壊れている。`build` し直す |
| `単位の名前が重なっている` | 同じファイル名が 2 つある。名前はファイル名から取るので、どちらかの名前を変える |
| `対応表に無い記法: <!doctype>` など | HTML を `.md` で保存している。拡張子を `.html` にする |
| `日本語以外が主` | 日本語の文章ではない |

カセットの中身や状態は `doctor` で見られる。

## ほかのコマンド

| コマンド | 何をするか |
| --- | --- |
| `build` | 記事のフォルダから目盛りを作る。作り直しも同じコマンド |
| `review` | 草稿を検めて、判定と直し方を返す |
| `measure` | 1 本を数えて値を並べる。判定はしない |
| `compare` | 3 本以上を並べて比べる。直すたびの版を並べて、近づいているかを見る |
| `doctor` | カセットの中身を表示して、壊れていないかを確かめる |
| `decide` | 記事から自動では決められないことを人が書き込む（後述） |
| `metrics` | 数えている指標の一覧を出す |

`kakiburi --help` で全体を、`kakiburi <コマンド> --help` でそのコマンドだけの説明を出せる。
`--json` を付けると機械で読める形で出す。

```sh
# 直すたびの版を並べて比べる。カセットを渡すと目盛りと比べられる
$K compare draft-1.md draft-2.md draft-3.md --cassette ~/articles.kb

# カセットを点検する
$K doctor ~/articles.kb
```

`decide` は 2 つのことを書き込む。

- `boilerplate`：どの記事にも入る決まり文句（「この記事は〜」のような定型）。数える前に
  取り除く。渡した一覧で置き換わる。
- `movement`：指示しても動かなかった指標。以後、その指標を直し方として出さなくなる。

```sh
$K decide ~/articles.kb boilerplate "この記事は Advent Calendar の 1 日目です。"
$K decide ~/articles.kb movement <指標> stuck
```

## 文章の種類ごとに分ける

1 つのカセットが 1 種類の文章（場面）に対応する。技術記事と議事録のように書き方が違う
文章は、フォルダもカセットも分ける。

```sh
$K build ~/articles --cassette 技術記事.kb --scene 技術記事
$K build ~/minutes  --cassette 議事録.kb   --scene 議事録
```

`review` にどのカセットを渡すかが、そのまま「どの種類の文章として見るか」の指定になる。

他人が書いた文章があれば `--other <フォルダ>` で渡せる。人らしさ値の「人の側」の見本が
厚くなる。

## 基準を自分で用意する

同梱の基準は技術記事向けに作ってある。議事録のような別の種類の文章なら、基準も自分で
作ったほうがよい。

作り方は、自分の記事と同じ題材を LLM に書かせるだけである。題材がずれると、目盛りが
書き方ではなく題材の違いを測ってしまう。

```
次の題材で技術記事を書いてください。

題材: Vim のファイラー系プラグインの比較
登場するもの: vim-filer、NERDTree、netrw、:Explore、Vim 8.2
長さ: 3,000 字程度
```

- 記事に出てくる製品名・コマンド名・版番号まで渡す。題名だけだと LLM は固有名詞を
  ほとんど書かず、その差だけで結果が偏る。
- 記事の本文は渡さない。書き方が漏れる。
- 頼む長さは本によって変える。全部同じ長さを頼むと同じ長さの文章ばかりになり、目盛りが
  作れない。地の文 2,000 字以上が使え、LLM は 4,000 字あたりで頭打ちになる。
- コードブロックは書かせない。地の文しか数えないので、字数が足りなくなる。
- 10 本以上作る。

作ったフォルダは、使ったモデルと版を添えて渡す。

```sh
$K build ~/articles --baseline ~/baseline --model claude --version 2026-08
```

規則とその理由は[設計](docs/design/200-command.md#依頼文の作り方は人が守る規則である)に
ある。同梱の基準を作り直す道具は `tools/gen-baseline.sh` と `tools/baseline-topics.txt`。

## 限界

数字があなたの記事に揃っても、読んだ人が「あなたらしい」と感じるかは確かめていない。
測っているのは表に出る統計で、統計が揃うことと読んでそう感じることのあいだは、まだ
つながっていない。
