# kuchiyose

LLM に、あなたの代わりに日本語の文章を書かせるツール。書くのは手元の LLM の道具
（`claude` や `codex`）で、kuchiyose は書かせるためのプロンプトを作り、書かれた文章が
あなたの書き方からどこでずれているかを数えて、直させる。

代筆させた文章は、読めば「自分の文章ではない」と分かる。けれど、どこが違うのかは
言いにくい。kuchiyose はそこを数える。あなたが過去に書いた記事を測って形代（かたしろ）に
し、比べる相手の文章（基準）と合わせて書き方の目盛りを作り、草稿をそれに当てて、たとえば
次のように返す。

```
判定: 通らない
止まった段: 基準との距離
理由: 基準の書きぶりが残っている

人らしさの直し方 1 本
  - 句読点の密度で見た基準との距離が本人より近い（この文章 -0.125 / 本人 1.188）。
    文を繋いで長くし、読点を減らす。基準との距離が +1.140 動く。
```

この結果を LLM の道具に渡して、指摘された表現だけを直させる。通るまで、または決めた回数まで
繰り返す。

AI が書いたことを隠すためのツールではない。見ているのは「基準（既定では素の LLM の文章）の
書きぶりが残っていないか」と「あなたの書き方に寄っているか」であって、検出器をすり抜け
られるかではない。

## 仕組み

```
あなたの記事のフォルダ ── build ─→ あなたの形代（統計値・調整・ペルソナ）
                                           │
何を書きたいか ── write ─→ 代筆のプロンプト ─→ LLM の道具と対話 ─→ 草稿
                                                                      │
                               ┌────────── 表現を寄せる周回 ──────────┘
                               ▼
                        検める ─→ 直させる ─→ 検める ─→ …… ─→ 判定 ＋ 残った指摘
```

1. `build` が、あなたの記事を 1 本ずつ数えて統計値を形代に保存する。記事の本文は保存
   しない。続けて LLM の道具に記事を読ませ、あなたが何を大事にし、誰に向けて、どう話を
   運ぶかを書いたペルソナを下書きさせる。
2. `write` が、ペルソナと、形代から取り出した文体の事実（敬体か常体か、一人称、よく使う
   言い回し、避ける言い回し、長さ）と、あなたの要約でプロンプトを作り、LLM の道具を起動する。
   内容はあなたが道具と対話して詰める。
3. 草稿ができると、kuchiyose が検めて、指摘された表現だけを道具に直させ、また検める。
   良くなった版だけを採り、通るか上限の回数で止める。

ペルソナで寄るのは内容や話の運び方までで、表面の書きぶりは書かせ方を工夫してもほとんど
寄らない。表面は検めて直す周回で寄せる。

検めるところで数えるのは、語や句読点の頻度、文の長さ、表記の揺れなど、読まずに数えられる
量だけである。LLM に採点させないので、同じ草稿からは毎回同じ結果が出る。kuchiyose 自身は
LLM の API を呼ばない。

出てくる用語は[用語集](docs/glossary.md)にまとめてある。

## 入れる

```sh
cargo build --release
```

要るのは Rust だけである。形態素解析器（[Lindera](https://github.com/lindera/lindera)）と
辞書（UniDic 2.1.2）、それに同梱の基準の形代は実行ファイルに入っているので、ほかに
用意するものは無い。その分、実行ファイルは大きい。

代筆させるには、LLM の道具が要る。`claude`（Claude Code）か `codex`（Codex CLI）が `PATH` に
あればそれを使う。ほかの道具は[起動のしかたを書いて](#使う道具を選ぶ)使える。道具が無くても、
プロンプトを出すだけの `--print` と、検めるだけの `review` は使える。

## 使う

### 1. 自分の記事を集める

自分で書いた文章を 1 つのフォルダに入れる。目安は 10 本以上で、1 本あたり地の文で
1,000 字以上あるとよい。

題材は絞らなくてよい。Vim の記事と Rust の記事が混ざっていてかまわない。混ぜないのは、
技術記事と議事録のように書き方そのものが違う文章だけで、混ぜると目盛りがぼやける。
そういう文章は[あとで](#文章の種類ごとに分ける)形代を分ける。

どの記事にも入る決まり文句（「この記事は Advent Calendar の 1 日目です。」のような定型）が
あれば、記事から消しておく。残すと、書き手どうしが実際より似て見える。

比べる相手の「基準」は用意しなくてよい。実行ファイルに同梱してある。

### 2. 形代を作る

```sh
K=./target/release/kuchiyose
$K build ~/articles
```

記事を数えて形代を作り、続けて LLM の道具がペルソナを下書きする。形代は
`~/.local/share/kuchiyose/articles.katashiro` にでき、以後はこれが既定の形代になる。
`-o` で置き場所を変えられる。

ペルソナは形代の隣の `articles.persona.md` にも書かれる。読んで直したら取り込み直す。
項目ごとに付いた記事からの引用は、取り込むときに記事に実在するかが確かめられる。

```sh
$K katashiro persona ~/.local/share/kuchiyose/articles.katashiro articles.persona.md
```

形代には記事ごとの統計値とペルソナが入り、記事の本文は入らない。作り直すときはフォルダを
読み直すので、記事は消さずに置いておく。記事が増えたら同じ `build` をもう一度打てば
作り直される。調整とペルソナは引き継がれる。

ペルソナが要らなければ `--no-persona` を付ける。統計値だけの形代になる。

### 3. 代筆させる

```sh
$K write "Vim の Denops でファイラーを作った話"   # 短ければ引数で
$K write < brief.md                             # メモから
$K write                                        # 何も渡さなければ $EDITOR が開く
```

LLM の道具が対話の画面で起動する。何を書くかを道具と話して詰めると、道具が今のディレクトリの
`draft-<日時>.md` に草稿を保存する（`-o` で変えられる）。対話を終えると、そのまま表現を
寄せる周回に入る。

周回では、kuchiyose が草稿を検め、指摘された表現だけを道具に直させ、また検める。
内容は変えさせない。良くなった版だけを採り、通るか 4 回で止めて、最後の判定と残った指摘を
出す。回数は `--rounds` で変えられる。

最後の版は `draft-<日時>.polished.md` に書かれる。元の草稿は上書きしない。各周の版と
プロンプトは `draft-<日時>.kuchiyose/` に残るので、内容が変わっていないかは差分で確かめる。
kuchiyose は内容までは測れない。

### 4. 手元の文章の表現だけを寄せる

自分で書いた文章や、ほかで書かせた文章の表現だけを寄せるなら、`polish` を使う。
`write` の後半だけを取り出したものである。

```sh
$K polish draft.md
```

### 使う道具を選ぶ

`--agent claude` か `--agent codex` で選ぶ。毎回選ぶのが面倒なら、環境変数
`KUCHIYOSE_AGENT` か、`~/.config/kuchiyose/` の設定ファイルに書いておく。何も決めなければ、
`PATH` にある `claude`、次に `codex` を使う。

ほかの道具は、起動のしかたを書けば使える。プロンプトはファイルで渡す。

```sh
KUCHIYOSE_AGENT_CMD='my-llm --prompt-file {prompt_file}' $K write --agent custom < brief.md
```

道具を起動せず、プロンプトだけを見たいときは `--print` を付ける。好きな場所に貼って使える。

```sh
$K write --print < brief.md
:w !kuchiyose write --print        " Vim のバッファから
```

周回で道具を起動するときは、道具に許す操作を、読む・書くファイルとコマンドの実行に
必要な分だけに絞る。

### 人に代筆を任せる

形代を渡すだけでよい。受け取った人は `--katashiro` で、その形代の持ち主に寄せた代筆が
できる。

```sh
$K write --katashiro alisue.katashiro < brief.md
```

ペルソナは、考え方や経歴に触れる文章である。渡したくなければ、渡す前に外す。

```sh
$K katashiro persona alisue.katashiro --remove
```

形代には、ペルソナのほかにも記事から切り出した言い回しの断片が入っている。記事そのものは
戻らないが、何も漏れないわけではない。渡す相手は、そのつもりで選ぶ。

## 結果の読み方

`write`、`polish`、`review` の判定は 3 つのどれかで、終了コードにも出る。`write` と
`polish` では、最後に採った版の判定である。

| 終了コード | 判定 | 意味 |
| --- | --- | --- |
| 0 | 通る | あなたの書き方の範囲に入っている |
| 1 | 通らない | 基準の側に落ちている |
| 2 | 判定できない | 草稿が短すぎる、素材が足りない、どちらとも言えない位置にある、あなたの書き方を見分ける指標が見つからなかった |
| 64 以上 | — | 判定の前に止まった（使い方の誤り、読めないファイル、kuchiyose の版違いなど） |

「判定できない」は失敗ではない。言い切れないときに無理に言い切らないための答えである。
草稿が 1,000 字に届かないときは「短すぎて測れない（812 字 / 下限 1,000 字）」のように言う。

判定は次の順に見て、最初に止まったところを「止まった段」として返す。

| 段 | 見ていること |
| --- | --- |
| 日本語として壊れていないか | 和文の間の余計な空白など |
| [基準との距離](docs/glossary.md#基準との距離) | 基準の書きぶりが残っていないか（同じ言い回しの繰り返し、語彙の狭さ、句読点の密度など）。既定の基準なら、機械の癖が残っていないかを見ることになる |
| [照合値](docs/glossary.md#照合値) | あなたの書き方に寄っているか（文字の並び、機能語、品詞の並び、読点の打ち方、文字種） |
| [指示できる指標](docs/glossary.md#指示できる指標) | 言葉で直せる項目が、あなたがふだん書く範囲に入っているか（括弧・記号・文末など） |

基準との距離と照合値は、正ならあなたの側、負なら基準の側を指す。値の大きさそのものより、
符号と止まった段を見ればよい。

言葉で直せる項目の段まで来ても、あなたの記事から「あなたを見分ける指標」が 1 本も見つかって
いなければ、「この書き手には効く指標が無い」として判定できないを返す。何も確かめずに
「通る」とは言わない。

出力は 2 つに分かれる。「ここから下は判定に使っていない」という行より上は判定を止めた
理由とその直し方で、下は参考の知らせ（本人が使わない一人称、書き出しの形など）である。
知らせを直すかどうかは書き手が決める。

## 判定と指摘だけを見る

周回を回さず、判定と指摘だけを見たいときは `review` を使う。自分で直すときもこれを使う。

```sh
$K review draft.md
```

数秒で終わる。形代を渡さなければ既定の形代を使う。別の形代は `--katashiro` で渡す。

直すたびの版を並べて渡すと、1 本 1 行で判定と主な値（照合値と基準との距離）を並べる。
近づいているかを見るのに使う。指摘は出ないので、読みたい版は 1 本だけ渡して検め直す。
`polish` が残した各周の版を並べるのにも使える。

```sh
$K review draft.kuchiyose/round-*.md
```

`--values` を付けると、測った値を全部並べる。

読むのは拡張子が `.md` / `.markdown`（Markdown）と `.html` / `.htm`（HTML）のファイルだけで
ある。ほかの拡張子のファイルは、1 本で渡すと断られ、フォルダの中にあれば読まずに飛ばす。
Markdown では GitHub の `> [!NOTE]` も Zenn などの `:::message` も補足として扱う。

形代の中身は `katashiro show` で見られる。測れなかった記事があれば、その理由も出る。
ペルソナを持っているかも出る。

```sh
$K katashiro show ~/.local/share/kuchiyose/articles.katashiro
```

## 指摘の出し方を調整する

何度直しても動かない指標や、気にしなくてよい言い回しは、形代の調整で無効にできる。
無効にしたものは判定と指摘から外れ、代筆のプロンプトにも出なくなる。測った値には
触らないので、作り直しは要らない。あとで戻せる。

`katashiro` の下のコマンドには形代を位置引数で渡す。例では既定の形代を `articles.katashiro`
と書く。

```sh
$K katashiro list articles.katashiro                     # 調整できるものと状態の一覧
$K katashiro mute articles.katashiro 強調                 # 無効にする
$K katashiro unmute articles.katashiro 強調               # 戻す
$K katashiro mute articles.katashiro --kind 基準の型      # 種類ごと無効にする
$K katashiro edit articles.katashiro                     # 対話画面で選ぶ
```

`katashiro list` は 1 行 1 項目で、種類・名前または ID・状態・説明をタブで区切って出す。
長い言い回しには ID が付き、`mute` には ID でも渡せる。fzf と組み合わせる例：

```sh
$K katashiro mute articles.katashiro \
  $($K katashiro list articles.katashiro --kind 基準の型 --state on | fzf -m | cut -f2)
```

一人称と文体は、記事から数えた結果の代わりに申告できる。「昔は『私』だったが今は『僕』で
書く」ような事情は、数えただけでは分からない。

```sh
$K katashiro first-person articles.katashiro 僕          # auto で数えた結果に戻す
$K katashiro register articles.katashiro polite          # polite（です・ます）/ plain（だ・である）/ auto
```

調整は形代の中に入る。形代を人に渡せば、調整も一緒に渡る。

## うまくいかないとき

エラーの文言には、理由と次にすることが書いてある。分かりにくいものだけ挙げる。

| 言われたこと | どうするか |
| --- | --- |
| `短すぎて測れない` | 草稿が地の文 1,000 字に届いていない。この長さでは何も言えない |
| `目盛りを作らない: 測れた単位が N 本で、10 本に届かない` | 記事が足りない。短すぎる記事は数えられないので、長い記事を足す。`katashiro show` でどの記事がなぜ落ちたかが見られる |
| `短い文書ばかりなので、同じものを足しても届かない` | 1 本が地の文 1,000 字に届いていない。kuchiyose はあなたの記事を束ねないので、短い記事は自分で 1 つのファイルにまとめる |
| `本人を基準と見分けられない` | あなたの記事どうしより、基準の文章のほうがあなたに近く出た。記事を足すか、場面の違う記事が混ざっていないか見る |
| `断る: 取り込み元が拡張子から決まらない` | `.md` / `.markdown` / `.html` / `.htm` 以外のファイルを渡した。拡張子を直す。`.txt` は読まない |
| `長さの範囲で断られたので、束ね方を変えて組み立て直す` | エラーではない。基準の束ね方を変えて組み立て直している。全部の束ね方で断られたときだけ止まる |
| `指紋が環境と合わない` | kuchiyose の版が変わった。`build` し直す。以前の値とは比べられない。人からもらった形代なら、作った人に作り直してもらう |
| `2 つの形代の指紋が合わない` | 違う版の kuchiyose で作った形代を組み合わせた。どちらかを作り直す |
| `単位の名前が重なっている` | 同じファイル名が 2 つある。名前はファイル名から取るので、どちらかの名前を変える |
| `対応表に無い記法: <!doctype>` など | HTML を `.md` で保存している。拡張子を `.html` にする |
| `日本語以外が主` | 日本語の文章ではない |
| `既定の形代が無い` | まだ `build` していない。`build` するか、`--katashiro` で形代を渡す |
| `LLM の道具が見つからない` | `claude` も `codex` も `PATH` に無い。入れるか、`--agent custom` と `KUCHIYOSE_AGENT_CMD` で起動のしかたを書く。`--print` ならプロンプトだけを出せる |
| `道具が失敗した` | 道具の出力の末尾が添えてある。それまでに採った版は残っている |
| `ペルソナの見出しが揃っていない` | 直したペルソナの見出しを消したか変えた。見出しは決まった名前と順で残す |
| `解決しない引用` | ペルソナの引用が記事に見つからない。記事の文字列どおりに直すか、項目ごと消す。取り込み自体はされている |
| `別のフォルダから作った形代がある` | 同じ名前の別のフォルダで `build` した。`-o` で形代の置き場所を分ける |

## コマンドの一覧

| コマンド | 何をするか |
| --- | --- |
| `build` | 記事のフォルダから形代を作り、ペルソナを下書きさせ、既定の形代にする |
| `write` | 代筆させる。対話で内容を詰めて書かせ、表現を寄せる周回に入る |
| `polish` | 手元の文章の表現だけを、周回で寄せる |

詳しく使うときのコマンド：

| コマンド | 何をするか |
| --- | --- |
| `review` | 草稿を検めて、判定と直し方を返す。複数渡すと 1 本 1 行で並べる |
| `katashiro build` | 記事のフォルダを測って形代を作る。ペルソナは作らない。作り直しも同じコマンドで、調整とペルソナは引き継ぐ |
| `katashiro show` | 形代の中身を表示して、壊れていないかを確かめる |
| `katashiro diff` | 2 つの形代がどこで違うかを出す。見分けられるか、どの指標で違うか、片方だけが使う言い回し |
| `katashiro list` | 調整できるものと状態を並べる |
| `katashiro mute` / `unmute` | 指標や言い回しを判定と指摘から外す / 戻す |
| `katashiro first-person` / `register` | 一人称 / 文体を申告する |
| `katashiro edit` | 調整を対話画面で行う |
| `katashiro persona` | ペルソナを取り込む・確かめる・出す・外す |

`kuchiyose --help` で全体を、`kuchiyose <コマンド> --help` でそのコマンドだけの説明を出せる。
`--json` を付けると機械で読める形で出す。

## 文章の種類ごとに分ける

1 つの形代が 1 つのフォルダ、1 種類の文章（場面）に対応する。技術記事と議事録のように
書き方が違う文章は、フォルダも形代も分ける。

```sh
$K build ~/articles -o 技術記事.katashiro --scene 技術記事
$K build ~/minutes  -o 議事録.katashiro   --scene 議事録
$K write --katashiro 議事録.katashiro < brief.md
```

`build` は最後に作った形代を既定にする。どの形代を使うかが、そのまま「どの種類の文章として
書き、見るか」の指定になる。
結果にはあなたの形代と基準の形代の場面の名前が並ぶので、取り違えていないかを見る。

## 別の基準と比べる

基準は `--baseline` で替えられる。`write`、`polish`、`review` のどれでも使える。基準も形代で、
あなたの形代と同じ `katashiro build` で作る。道具は基準が機械の文章か人の文章かを区別しない。

誰かの形代を基準に渡せば、その人と比べることになる。「素の LLM より自分に近いか」では
なく「その人より自分に近いか」が分かる。そのとき「基準との距離」の段は、その人の書きぶりが
残っていないかを見る段になる。

```sh
$K review draft.md --katashiro articles.katashiro --baseline james.katashiro
$K katashiro diff articles.katashiro james.katashiro            # 2 人の書き方がどこで違うか
```

判定を後で比べるときは、同じ基準で出したものどうしを比べる。結果には基準の形代の
中身のハッシュが出る。

## 基準を自分で用意する

同梱の基準は技術記事向けに作ってある。議事録のような別の種類の文章なら、基準も自分で
作ったほうがよい。

作り方は、その種類の文章が扱いそうな題材を広く散らして、LLM に書かせるだけである。
自分の記事と同じ題材にする必要は無い。`review` が、あなたの記事と題材の近いものを基準の
中から選んで使うからである。同梱の基準も、題材は特定の人から取らずに広く取ってある。
題材は `tools/baseline-topics.txt` のように並べるとよい。

```
次の題材で議事録を書いてください。です・ます調で書いてください。

題材: 社内勉強会の運営方針を見直す定例
登場するもの: Slack、Google カレンダー、Zoom、参加率、アンケート
長さ: 2,500 字程度
```

- 題材ごとに、登場する製品名・コマンド名・版番号まで渡す。題名だけだと LLM は固有名詞を
  ほとんど書かず、その差だけで結果が偏る。
- 自分の記事の本文は渡さない。書き方が漏れる。名前を渡すときも、自分の記事での表記は
  写さない。
- 文体（です・ます調か、だ・である調か）をあなたの記事に合わせて指定する。指定しないと LLM は
  だ・である調に寄り、です・ます調で書く人では機械の草稿が通りやすくなる。
- 頼む長さは本によって変える。全部同じ長さを頼むと同じ長さの文章ばかりになり、目盛りが
  作れない。地の文 2,000 字以上が使え、LLM は 4,000 字あたりで頭打ちになる。あなたの記事に
  それより長いものがあれば、`review` が基準を何本か束ねて長さを届かせる。
- コードブロックは書かせない。地の文しか数えないので、字数が足りなくなる。
- 10 本以上作る。題材で選ぶ余地が要るので、題材を散らして多めに作る。

作ったフォルダを `katashiro build` で形代にして、`--baseline` で渡す。`build` ではなく
`katashiro build` を使う。`build` はペルソナを作らせ、既定の形代まで書き換える。基準の文書は、
あなたの記事と同じ文体で題材の近いものが 24 本まで選ばれて使われる。どの LLM のどの版で
作ったかは、場面の名前かファイル名に書いておくとよい。

```sh
$K katashiro build ~/baseline -o baseline-claude-2026-08.katashiro --scene "技術記事 claude 2026-08"
$K review draft.md --katashiro articles.katashiro --baseline baseline-claude-2026-08.katashiro
```

規則とその理由は[設計](docs/design/200-command.md#依頼文の作り方は人が守る規則である)に
ある。同梱の基準の文書は `baselines/` にあり、作り直す道具は `tools/gen-baseline.sh` と
`tools/baseline-topics.txt`。

## 限界

数字があなたの記事に揃っても、読んだ人が「あなたらしい」と感じるかは確かめていない。
測っているのは表に出る統計で、統計が揃うことと読んでそう感じることのあいだは、まだ
つながっていない。

確かめたのはまだ 1 人分の記事である。ほかの書き手で同じように働くかは言えない。

ペルソナが内容を本人らしくしたかは測っていない。数えているのは表面の書きぶりだけで、
内容や考え方が本人らしいかは本人が読んで決める。周回で内容が変わっていないかも、
kuchiyose には測れない。直させるプロンプトで内容を変えないよう縛り、最後は差分を読んで
確かめる。

閾値のいくつかは暫定値である。除外の既定、帯の端、語彙の大きさがそうで、どれも 1 人分の
実測か、出どころの無い値で置いている。どれが暫定かは[仕様](docs/spec/200-extract.md)の
それぞれの箇所に書いてある。
