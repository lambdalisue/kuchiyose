# kakiburi

LLM に代筆させた日本語の草稿が、あなたの書き方からどこでずれているかを数えて、
直し方を言葉で返すツール。

代筆させた文章は、読めば「自分の文章ではない」と分かる。けれど、どこが違うのかは
言いにくい。kakiburi はそこを数える。あなたが過去に書いた記事を測ってカセットにし、
比べる相手の文章（基準）と合わせて書き方の目盛りを作り、草稿をそれに当てて、たとえば
次のように返す。

```
判定: 通らない
止まった段: 基準との距離
理由: 基準の書きぶりが残っている

人らしさの直し方 1 本
  - 句読点の密度で見た基準との距離が本人より近い（この文章 -0.125 / 本人 1.188）。
    文を繋いで長くし、読点を減らす。基準との距離が +1.140 動く。
```

AI が書いたことを隠すためのツールではない。見ているのは「基準（既定では素の LLM の文章）の
書きぶりが残っていないか」と「あなたの書き方に寄っているか」であって、検出器をすり抜け
られるかではない。

## 仕組み

```
あなたの記事のフォルダ ── cassette build ─→ あなたのカセット ─┐
                                                              ├─ review ─→ 判定 ＋ 直し方
                                   基準のカセット（同梱）   ───┤
                                                              │
草稿 ──────────────────────────────────────────────────────────┘
```

1. `cassette build` が、あなたの記事を 1 本ずつ数えて、その統計値をカセットに保存する。
   記事の本文は保存しない。
2. `review` が、あなたのカセットと基準のカセットから、その場で目盛りを組み立てる。
   あなたの記事どうしの近さと、基準の文章との遠さから目盛りができる。基準は、広く散らした
   題材を LLM に素で書かせた文章から作ったものが同梱してあり、そのうちあなたの記事と文体が
   同じで題材の近いものが使われる。
3. `review` は草稿を同じやり方で数えて目盛りに当てる。あなたの側に寄っていれば「通る」、
   基準の側なら「通らない」、どちらとも言えなければ「判定できない」を返す。あわせて、
   どの指標をどちらへ直せばよいかを返す。

数えるのは語や句読点の頻度、文の長さ、表記の揺れなど、読まずに数えられる量だけである。
LLM に採点させないので、同じ草稿からは毎回同じ結果が出る。

出てくる用語は[用語集](docs/glossary.md)にまとめてある。

## 入れる

```sh
cargo build --release
```

要るのは Rust だけである。形態素解析器（[Lindera](https://github.com/lindera/lindera)）と
辞書（UniDic 2.1.2）、それに同梱の基準のカセットは実行ファイルに入っているので、ほかに
用意するものは無い。その分、実行ファイルは大きい。

## 使う

### 1. 自分の記事を集める

自分で書いた文章を 1 つのフォルダに入れる。目安は 10 本以上で、1 本あたり地の文で
1,000 字以上あるとよい。

題材は絞らなくてよい。Vim の記事と Rust の記事が混ざっていてかまわない。混ぜないのは、
技術記事と議事録のように書き方そのものが違う文章だけで、混ぜると目盛りがぼやける。
そういう文章は[あとで](#文章の種類ごとに分ける)カセットを分ける。

どの記事にも入る決まり文句（「この記事は Advent Calendar の 1 日目です。」のような定型）が
あれば、記事から消しておく。残すと、書き手どうしが実際より似て見える。

比べる相手の「基準」は用意しなくてよい。実行ファイルに同梱してある。

### 2. カセットを作る

```sh
K=./target/release/kakiburi
$K cassette build ~/articles -o articles.kb
```

`articles.kb`（カセット）ができる。数十秒かかる。

カセットには記事ごとの統計値だけが入り、記事の本文は入らない。作り直すときはフォルダを
読み直すので、記事は消さずに置いておく。記事が増えたら同じ `cassette build` をもう一度
打てば作り直される。あとで書く調整は引き継がれる。

作ったカセットの中身は `cassette show` で見られる。測れなかった記事があれば、その理由も
出る。

```sh
$K cassette show articles.kb
```

### 3. 草稿を検める

```sh
$K review draft.md --cassette articles.kb
```

数秒で終わる。直して、また `review` する、を繰り返す。

直すたびの版を並べて渡すと、1 本 1 行で判定と主な値（照合値と基準との距離）を並べる。
近づいているかを見るのに使う。指摘は出ないので、読みたい版は 1 本だけ渡して検め直す。

```sh
$K review draft-1.md draft-2.md draft-3.md --cassette articles.kb
```

`--values` を付けると、測った値を全部並べる。

読むのは拡張子が `.md` / `.markdown`（Markdown）と `.html` / `.htm`（HTML）のファイルだけで
ある。ほかの拡張子のファイルは、1 本で渡すと断られ、フォルダの中にあれば読まずに飛ばす。
Markdown では GitHub の `> [!NOTE]` も Zenn などの `:::message` も補足として扱う。

## 結果の読み方

判定は 3 つのどれかで、終了コードにも出る。

| 終了コード | 判定 | 意味 |
| --- | --- | --- |
| 0 | 通る | あなたの書き方の範囲に入っている |
| 1 | 通らない | 基準の側に落ちている |
| 2 | 判定できない | 草稿が短すぎる、素材が足りない、どちらとも言えない位置にある、あなたの書き方を見分ける指標が見つからなかった |
| 64 以上 | — | 判定の前に止まった（使い方の誤り、読めないファイル、kakiburi の版違いなど） |

「判定できない」は失敗ではない。言い切れないときに無理に言い切らないための答えである。
草稿が 1,000 字に届かないときは「短すぎて測れない（812 字 / 下限 1,000 字）」のように言う。

判定は次の順に見て、最初に止まったところを「止まった段」として返す。

| 段 | 見ていること |
| --- | --- |
| 日本語として壊れていないか | 和文の間の余計な空白など |
| [基準との距離](docs/glossary.md#基準との距離) | 基準の書きぶりが残っていないか（同じ言い回しの繰り返し、語彙の狭さ、句読点の密度など）。既定の基準なら、機械の癖が残っていないかを見ることになる |
| [照合値](docs/glossary.md#照合値) | あなたの書き方に寄っているか（文字の並び、機能語、品詞の並び、読点の打ち方、文字種） |
| [指示できる指標](docs/glossary.md#指示できる指標) | 言葉で直せる項目が、あなたがふだん書く範囲に入っているか（括弧・記号・文末など） |

基準との距離と照合値は、正ならあなたの側、負なら基準の側を指す。値の大きさそのものより、
符号と止まった段を見ればよい。

言葉で直せる項目の段まで来ても、あなたの記事から「あなたを見分ける指標」が 1 本も見つかって
いなければ、「この書き手には効く指標が無い」として判定できないを返す。何も確かめずに
「通る」とは言わない。

出力は 2 つに分かれる。「ここから下は判定に使っていない」という行より上は判定を止めた
理由とその直し方で、下は参考の知らせ（本人が使わない一人称、書き出しの形など）である。
知らせを直すかどうかは書き手が決める。

## 指摘の出し方を調整する

何度直しても動かない指標や、気にしなくてよい言い回しは、カセットの調整で無効にできる。
無効にしたものは判定と指摘から外れる。測った値には触らないので、作り直しは要らない。
あとで戻せる。

```sh
$K cassette list articles.kb                     # 調整できるものと状態の一覧
$K cassette mute articles.kb 強調                 # 無効にする
$K cassette unmute articles.kb 強調               # 戻す
$K cassette mute articles.kb --kind 基準の型      # 種類ごと無効にする
$K cassette edit articles.kb                     # 対話画面で選ぶ
```

`cassette list` は 1 行 1 項目で、種類・名前または ID・状態・説明をタブで区切って出す。
長い言い回しには ID が付き、`mute` には ID でも渡せる。fzf と組み合わせる例：

```sh
$K cassette mute articles.kb \
  $($K cassette list articles.kb --kind 基準の型 --state on | fzf -m | cut -f2)
```

一人称と文体は、記事から数えた結果の代わりに申告できる。「昔は『私』だったが今は『僕』で
書く」ような事情は、数えただけでは分からない。

```sh
$K cassette first-person articles.kb 僕          # auto で数えた結果に戻す
$K cassette register articles.kb polite          # polite（です・ます）/ plain（だ・である）/ auto
```

調整はカセットの中に入る。カセットを人に渡せば、調整も一緒に渡る。

## うまくいかないとき

エラーの文言には、理由と次にすることが書いてある。分かりにくいものだけ挙げる。

| 言われたこと | どうするか |
| --- | --- |
| `短すぎて測れない` | 草稿が地の文 1,000 字に届いていない。この長さでは何も言えない |
| `目盛りを作らない: 測れた単位が N 本で、10 本に届かない` | 記事が足りない。短すぎる記事は数えられないので、長い記事を足す。`cassette show` でどの記事がなぜ落ちたかが見られる |
| `短い文書ばかりなので、同じものを足しても届かない` | 1 本が地の文 1,000 字に届いていない。kakiburi はあなたの記事を束ねないので、短い記事は自分で 1 つのファイルにまとめる |
| `本人を基準と見分けられない` | あなたの記事どうしより、基準の文章のほうがあなたに近く出た。記事を足すか、場面の違う記事が混ざっていないか見る |
| `断る: 取り込み元が拡張子から決まらない` | `.md` / `.markdown` / `.html` / `.htm` 以外のファイルを渡した。拡張子を直す。`.txt` は読まない |
| `長さの範囲で断られたので、束ね方を変えて組み立て直す` | エラーではない。基準の束ね方を変えて組み立て直している。全部の束ね方で断られたときだけ止まる |
| `指紋が環境と合わない` | kakiburi の版が変わった。`cassette build` し直す。以前の値とは比べられない。人からもらったカセットなら、作った人に作り直してもらう |
| `2 つのカセットの指紋が合わない` | 違う版の kakiburi で作ったカセットを組み合わせた。どちらかを作り直す |
| `単位の名前が重なっている` | 同じファイル名が 2 つある。名前はファイル名から取るので、どちらかの名前を変える |
| `対応表に無い記法: <!doctype>` など | HTML を `.md` で保存している。拡張子を `.html` にする |
| `日本語以外が主` | 日本語の文章ではない |

## コマンドの一覧

| コマンド | 何をするか |
| --- | --- |
| `review` | 草稿を検めて、判定と直し方を返す。複数渡すと 1 本 1 行で並べる |
| `cassette build` | 記事のフォルダを測ってカセットを作る。作り直しも同じコマンドで、調整は引き継ぐ |
| `cassette show` | カセットの中身を表示して、壊れていないかを確かめる |
| `cassette diff` | 2 つのカセットがどこで違うかを出す。見分けられるか、どの指標で違うか、片方だけが使う言い回し |
| `cassette list` | 調整できるものと状態を並べる |
| `cassette mute` / `unmute` | 指標や言い回しを判定と指摘から外す / 戻す |
| `cassette first-person` / `register` | 一人称 / 文体を申告する |
| `cassette edit` | 調整を対話画面で行う |

`kakiburi --help` で全体を、`kakiburi <コマンド> --help` でそのコマンドだけの説明を出せる。
`--json` を付けると機械で読める形で出す。

## 文章の種類ごとに分ける

1 つのカセットが 1 つのフォルダ、1 種類の文章（場面）に対応する。技術記事と議事録のように
書き方が違う文章は、フォルダもカセットも分ける。

```sh
$K cassette build ~/articles -o 技術記事.kb --scene 技術記事
$K cassette build ~/minutes  -o 議事録.kb   --scene 議事録
```

`review` にどのカセットを渡すかが、そのまま「どの種類の文章として見るか」の指定になる。
結果にはあなたのカセットと基準のカセットの場面の名前が並ぶので、取り違えていないかを見る。

## 別の基準と比べる

基準は `--baseline` で替えられる。基準もカセットで、あなたのカセットと同じ
`cassette build` で作る。道具は基準が機械の文章か人の文章かを区別しない。

誰かのカセットを基準に渡せば、その人と比べることになる。「素の LLM より自分に近いか」では
なく「その人より自分に近いか」が分かる。そのとき「基準との距離」の段は、その人の書きぶりが
残っていないかを見る段になる。

```sh
$K review draft.md --cassette articles.kb --baseline james.kb
$K cassette diff articles.kb james.kb            # 2 人の書き方がどこで違うか
```

判定を後で比べるときは、同じ基準で出したものどうしを比べる。結果には基準のカセットの
中身のハッシュが出る。

## 基準を自分で用意する

同梱の基準は技術記事向けに作ってある。議事録のような別の種類の文章なら、基準も自分で
作ったほうがよい。

作り方は、その種類の文章が扱いそうな題材を広く散らして、LLM に書かせるだけである。
自分の記事と同じ題材にする必要は無い。`review` が、あなたの記事と題材の近いものを基準の
中から選んで使うからである。同梱の基準も、題材は特定の人から取らずに広く取ってある。
題材は `tools/baseline-topics.txt` のように並べるとよい。

```
次の題材で議事録を書いてください。です・ます調で書いてください。

題材: 社内勉強会の運営方針を見直す定例
登場するもの: Slack、Google カレンダー、Zoom、参加率、アンケート
長さ: 2,500 字程度
```

- 題材ごとに、登場する製品名・コマンド名・版番号まで渡す。題名だけだと LLM は固有名詞を
  ほとんど書かず、その差だけで結果が偏る。
- 自分の記事の本文は渡さない。書き方が漏れる。名前を渡すときも、自分の記事での表記は
  写さない。
- 文体（です・ます調か、だ・である調か）をあなたの記事に合わせて指定する。指定しないと LLM は
  だ・である調に寄り、です・ます調で書く人では機械の草稿が通りやすくなる。
- 頼む長さは本によって変える。全部同じ長さを頼むと同じ長さの文章ばかりになり、目盛りが
  作れない。地の文 2,000 字以上が使え、LLM は 4,000 字あたりで頭打ちになる。あなたの記事に
  それより長いものがあれば、`review` が基準を何本か束ねて長さを届かせる。
- コードブロックは書かせない。地の文しか数えないので、字数が足りなくなる。
- 10 本以上作る。題材で選ぶ余地が要るので、題材を散らして多めに作る。

作ったフォルダを `cassette build` でカセットにして、`--baseline` で渡す。基準の文書は、
あなたの記事と同じ文体で題材の近いものが 24 本まで選ばれて使われる。どの LLM のどの版で
作ったかは、場面の名前かファイル名に書いておくとよい。

```sh
$K cassette build ~/baseline -o baseline-claude-2026-08.kb --scene "技術記事 claude 2026-08"
$K review draft.md --cassette articles.kb --baseline baseline-claude-2026-08.kb
```

規則とその理由は[設計](docs/design/200-command.md#依頼文の作り方は人が守る規則である)に
ある。同梱の基準の文書は `baselines/` にあり、作り直す道具は `tools/gen-baseline.sh` と
`tools/baseline-topics.txt`。

## 限界

数字があなたの記事に揃っても、読んだ人が「あなたらしい」と感じるかは確かめていない。
測っているのは表に出る統計で、統計が揃うことと読んでそう感じることのあいだは、まだ
つながっていない。

確かめたのはまだ 1 人分の記事である。ほかの書き手で同じように働くかは言えない。

閾値のいくつかは暫定値である。除外の既定、帯の端、語彙の大きさがそうで、どれも 1 人分の
実測か、出どころの無い値で置いている。どれが暫定かは[仕様](docs/spec/200-extract.md)の
それぞれの箇所に書いてある。
